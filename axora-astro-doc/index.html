01 · Overview

Introduction

Everything you need to know before you open your editor — what’s in the box, what it’s built with, and what it expects from your machine.

Welcome

Thanks for picking up Axora, an animated landing page template for project-management and team-collaboration SaaS products. This guide walks through installing the template, understanding how the project is organized, customizing content and styling, and shipping it to production. It’s written for developers who are comfortable with the command line but new to this specific codebase — if you already know Astro well, feel free to skip ahead using the sidebar.

What’s Included

Source files

The full, uncompiled project source — components, pages, data files, scripts, styles, and configuration — plus a README.md and a commercial LICENSE.

Production build

No pre-built dist/ folder is shipped — run npm run build once to generate one (see Build & Preview).

Design assets

Self-hosted Satoshi font files in public/fonts/, light and dark PNG logos, SVG/ICO favicons, and the demo PNG/JPG/SVG artwork in public/images/. No Figma file is included.

This documentation

A single offline HTML file — open it directly in any browser, no server required.

Features

  • Four pages: a long-form home page, sign-in, sign-up, and a custom 404 page
  • Fifteen home page sections — hero, feature cards, feature highlights, feature grid, benefit tabs, integrations marquee, case study, social proof, pricing, FAQ, and a closing call to action
  • Monthly/Yearly pricing tabs, an accordion FAQ, a video lightbox, and animated stat counters
  • GSAP scroll animations (ScrollTrigger + SplitText) that switch off for visitors who prefer reduced motion
  • Sticky header with a mobile slide-out drawer menu
  • All copy, links, and images kept in plain JavaScript data files under src/data/
  • Per-page titles, meta descriptions, canonical URLs, Open Graph tags, and an auto-generated sitemap
  • Zero UI framework — plain Astro components, vanilla scripts, and plain CSS with custom properties

Technology Stack

Axora is a static Astro site with no UI framework. It’s built with:

Astro Vite GSAP Plain CSS

02 · Setup

Getting Started

From a downloaded ZIP to a running dev server in five steps.

Installation & Extraction

  1. Download the template ZIP from your purchase confirmation email or account downloads page.
  2. Extract it to a folder on your machine — avoid folder names with spaces or special characters. The archive contains the axora-astro/ project folder and a documentation.txt file.
  3. Open that folder in your terminal and in your code editor.
bash
# Extract on macOS / Linux
unzip axora-astro-package.zip
cd axora-astro-package/axora-astro

Node.js Setup

Check which version of Node.js is currently active:

bash
node --version
# v22.23.4 or later

If you manage multiple Node versions, tools like nvm or fnm make switching painless:

bash
nvm install 22
nvm use 22

Install Dependencies

From the project root, install packages with your preferred package manager:

npm
npm install
pnpm
pnpm install
yarn
yarn install

This reads package.json and downloads every dependency into a local node_modules/ folder. It only needs to be re-run when dependencies change.

Run the Development Server

npm
npm run dev
pnpm
pnpm dev

This starts Vite’s local dev server with hot module reloading — edits to components, pages, and styles appear in the browser immediately without a manual refresh. By default it’s available at http://localhost:4321; the terminal output will confirm the exact address.

Build for Production & Preview

bash
# Compile an optimized production build into dist/
npm run build

# Serve that build locally to sanity-check it
npm run preview

build renders every page to static HTML, bundles and minifies CSS/JS, copies public/, generates the sitemap, and writes everything to dist/. preview serves that exact output locally so you can verify it before deploying — it does not rebuild automatically, so re-run build after further changes.

Which command do I actually need?

Use dev while you’re customizing the template. Use build, then preview, once before you deploy — it renders every page up front, so it catches issues (like a missing import or a data field a page expects but can’t find) on pages you may not have opened in the dev server.

04 · Reference

Configuration

The files that control how the project builds, and where to set site-wide values.

package.json

Defines the Node version, the four dependencies (Astro, the sitemap integration, the Manrope font package, and GSAP), and the scripts you run from the terminal. Add your own script here if you introduce a new tool.

jsonpackage.json
{
  "name": "axora-astro",
  "type": "module",
  "version": "0.0.1",
  "engines": { "node": ">=22.23.4" },
  "scripts": {
    "dev": "astro dev",
    "build": "astro build",
    "preview": "astro preview",
    "astro": "astro"
  },
  "dependencies": {
    "@astrojs/sitemap": "^3.7.5",
    "@fontsource/manrope": "^5.3.0",
    "astro": "^7.4.12",
    "gsap": "^3.15.1"
  }
}

astro.config.mjs

Controls integrations, the deployed site URL, and build behavior. Axora registers only the sitemap integration and disables Astro’s dev toolbar. Replace site with your real domain before deploying — it’s used for canonical URLs, absolute Open Graph image URLs, and the sitemap.

javascriptastro.config.mjs
import { defineConfig } from 'astro/config';
import sitemap from '@astrojs/sitemap';

export default defineConfig({
  site: 'https://example.com', // replace with your domain
  devToolbar: { enabled: false },
  integrations: [sitemap()],
});

tsconfig.json

Extends Astro’s strict preset. The project’s own code is plain JavaScript (.js data files and .astro components), so this file mainly powers editor autocomplete and error hints. No path aliases are defined — imports use relative paths such as ../data/home.js.

jsontsconfig.json
{
  "extends": "astro/tsconfigs/strict",
  "include": [".astro/types.d.ts", "**/*"],
  "exclude": ["dist"]
}

Environment Variables (.env)

Axora doesn’t read any environment variables out of the box, and no .env file is included. If you add one later (for example, a form endpoint), create a .env file in the project root for values that differ between environments or shouldn’t be committed to Git. Variables must be prefixed PUBLIC_ to be readable in client-side code.

env.env
# Exposed to the browser — never put secrets here
PUBLIC_SITE_URL=https://example.com

# Server-only — safe for secrets, not readable in browser code
API_SECRET_KEY=your_secret_key
Never commit .env

Add .env to .gitignore (it usually is by default). Anything without the PUBLIC_ prefix should stay off the client entirely.

05 · Guide

Pages

How routes are created, and how every page plugs into the shared layout.

Creating a New Page

Astro uses file-based routing: any .astro or .md file placed in src/pages/ automatically becomes a route matching its file path. Axora ships four:

text
src/pages/index.astro    →  /
src/pages/sign-in.astro  →  /sign-in
src/pages/sign-up.astro  →  /sign-up
src/pages/404.astro      →  shown for any unknown URL

To add a page, create a new file in src/pages/, wrap it in Layout, and reuse existing sections or UI components where they fit:

astrosrc/pages/services.astro
---
import Layout from '../layouts/Layout.astro';
import PillButton from '../components/ui/PillButton.astro';
---
<Layout title="Services – Axora" description="What Axora can do for your team.">
  <h1>Our Services</h1>
  <PillButton href="/sign-up" label="Start free trial" />
</Layout>

Editing an Existing Page

Axora’s pages are thin: they import section components and pass them data from src/data/. To change what a page says, edit its data file (see Content Editing). To change how a section looks or is laid out, edit the component in src/components/. To reorder, add, or remove sections, edit the page file itself — for example, src/pages/index.astro lists the home page sections in order.

Dynamic Routes

Axora doesn’t use dynamic routes. If you add a blog or product pages later, files wrapped in square brackets, such as [slug].astro, generate multiple pages from a single template. Astro requires a getStaticPaths() function for these on statically-generated sites:

astrosrc/pages/blog/[slug].astro
---
export async function getStaticPaths() {
  const posts = await import.meta.glob('./posts/*.md');
  return Object.keys(posts).map((path) => ({
    params: { slug: path.split('/').pop().replace('.md', '') },
  }));
}
---

Layouts

Axora has one layout, src/layouts/Layout.astro. It loads the Manrope font and global.css, writes the <head> SEO tags, and renders the header, the page content via a <slot />, and the footer. It accepts five optional props:

astrosrc/layouts/Layout.astro
---
const {
  title = 'Axora – Project Management',
  description = 'Axora is an all-in-one project management template …',
  image = null,       // Open Graph image path, e.g. '/images/og.png'
  showFooter = true,  // the sign-in and sign-up pages pass false
  bodyClass = '',
} = Astro.props;
---
<html lang="en">
  <head>…</head>
  <body class={bodyClass}>
    <Header />
    <main id="main"><slot /></main> <!-- page content is injected here -->
    {showFooter && <Footer />}
  </body>
</html>

Page Metadata & the 404 Page

Pass a title and description into Layout on every page for correct browser tabs and search results (see also SEO). The sign-in, sign-up, and 404 pages read theirs from the seo object in src/data/auth.js and src/data/notFound.js. src/pages/404.astro is served automatically whenever no route matches; its code, heading, text, and button come from notFound.js.

06 · Guide

Components

The building blocks pages are assembled from, and how data flows into them.

Reusable Components

Components live in src/components/ and encapsulate one piece of UI so it can be reused without copy-pasting markup. All of Axora’s components are .astro files:

  • Layout chrome — Header.astro (sticky header and mobile drawer) and Footer.astro.
  • Home sections (sections/home/) — HeroDecor, Hero, WaveDivider, Features, FeatureSplit, SectionHeading, FeatureGrid, CtaRow, BenefitTabs, Integrations, CaseStudy, SocialProof, PricingSection, and ClosingCta, plus their helpers FeatureIcon, TabIcon, TestimonialCard, PricingPlans, and FaqList.
  • Shared sections (sections/shared/) — AuthSection, used by both the sign-in and sign-up pages.
  • UI (ui/) — PillButton, StarRating, UnderlineLink, and WaveTop.

Props

Props are the inputs a component accepts, similar to HTML attributes. Axora’s components are plain JavaScript — they read props from Astro.props and document them in a comment at the top of the file rather than with TypeScript interfaces. The main button, PillButton, is a good example:

astrosrc/components/ui/PillButton.astro
---
// `hover="dark"` swaps the background to the primary color on hover.
// `tone="dark"` starts on the primary color and turns accent on hover.
// `block` stretches it to the full width of its container.
const { href, label, hover, tone, block } = Astro.props;
---
<a class:list={['pill-button', hover === 'dark' && 'pill-button--hover-dark', …]} href={href}>
  <span data-text={label}>{label}</span>
</a>

In plain language: href and label set where the button goes and what it says; hover, tone, and block are optional style switches. Because there’s no type checking, a misspelled prop (like lable) simply renders an empty button — check the comment at the top of a component when something looks blank.

Component Composition

Pages are composed from section components, and larger sections are composed from smaller ones — PricingSection, for instance, renders TestimonialCard, PricingPlans, and FaqList. The home page is just an ordered list of sections:

astrosrc/pages/index.astro
<Layout title="Axora – Project Management">
  <HeroDecor data={heroDecor} />
  <Hero data={hero} />
  <WaveDivider />
  <Features data={features} />
  {highlights.map((item) => <FeatureSplit data={item} />)}
  <!-- …feature grid, benefits, integrations, case study, social proof… -->
  <PricingSection section="home-14" data={pricing} />
  <ClosingCta section="home-15" data={closingCta} />
</Layout>

Passing Data to Components

In Astro, props are passed the same way as HTML attributes and read via Astro.props. Axora’s section components each take a single data object exported from a file in src/data/:

astro
---
import Hero from '../components/sections/home/Hero.astro';
import { hero } from '../data/home.js';
---
<Hero data={hero} />
Interactivity without a framework

Axora ships no React or other UI framework. Interactive pieces — the mobile drawer, benefit tabs, pricing tabs, FAQ accordion, video lightbox, and counters — are small vanilla <script> blocks inside the matching .astro component, with GSAP handling the animation.

07 · Guide

Styling

Where to change colors, type, and spacing without fighting the build.

Global Styles & CSS Variables

Site-wide values — color palette, font families, type scale, container widths — are defined once as CSS custom properties at the top of src/styles/global.css and referenced everywhere else. Change a value here and it updates across the whole site. The brand green is --color-accent.

csssrc/styles/global.css
:root {
  /* Colors */
  --color-primary: #242635;
  --color-secondary: #54595f;
  --color-text: #525468;
  --color-accent: #00b172;
  --color-white: #ffffff;

  /* Families */
  --font-heading: 'Manrope', sans-serif;
  --font-body: 'Satoshi', sans-serif;

  /* Layout */
  --container: 1140px;
  --header-container: 1250px;
}

Component Styles

Axora’s components keep their own CSS in a scoped <style> block — CSS written there only applies to that component, so class names never collide across files. There’s no Tailwind or Sass; it’s plain CSS throughout.

astro
<style>
  .not-found__code { font-family: var(--font-heading); color: var(--color-accent); }
</style>

Responsive Design, Typography & Spacing

The type scale (--text-body-size, --text-display-size, --text-title-size, and so on) is defined alongside the other tokens in global.css, and some values shrink at smaller screens. Media queries use literal widths rather than variables; the breakpoints are 767px (mobile), 880px (mobile landscape), 1024px (tablet), 1200px (tablet landscape), and 1366px (laptop). Prefer adjusting the shared values over overriding sizes on individual elements, so the site keeps a consistent rhythm as you edit it.

Avoid editing dist/

The dist/ folder is generated output — any change made there is overwritten on the next build. Always edit files under src/.

08 · Guide

Images & Assets

Where Axora keeps its images, and how to swap them.

LocationUse forBehavior
public/images/All of Axora’s artwork: auth/ (sign-in/sign-up background), home/ (section images, icons, client logos), and shared/ (the light and dark logos)Copied as-is, no processing; referenced by root-relative paths such as /images/home/chat-laptop.png
public/ (root)Files that need a fixed, predictable URL — favicon.svg, favicon.ico, and the fonts in public/fonts/Copied as-is, no processing

Replacing Images

Image paths live in the data files, not in the components. Either overwrite the file in public/images/ with a new one of the same name and similar dimensions, or drop in a new file and update its src (plus width, height, and alt) in the data file:

javascriptsrc/data/home.js
visual: {
  main: { src: '/images/home/chat-laptop.png', width: 667, height: 400, alt: 'Team chat inbox on a laptop' },
  layer: { src: '/images/home/chat-search-bar.png', width: 641, height: 106 },
},

Supported Formats & SVGs

Images are rendered with plain <img> tags, so any format the browser understands works — the demo uses PNG, JPG, and SVG. Small SVG icons (feature icons, tab icons, social icons) are written inline in the markup instead; see Icon Libraries.

Image Optimization

Axora doesn’t use Astro’s astro:assets image pipeline — files in public/ are served exactly as you add them. Compress and resize images (for example, export WebP at the displayed size) before dropping them in. If you’d rather have the build optimize them, move an image into a new src/assets/ folder, import it, and render it with Astro’s <Image /> component.

Rule of thumb

Keep new artwork in public/images/ next to the image it replaces, and reference it from the matching data file in src/data/. Every path starts with /images/… — never include public in the URL.

09 · Guide

Fonts & Icons

Swapping typefaces and icon sets without touching every component.

Google Fonts

Axora doesn’t load anything from Google’s servers. The heading font, Manrope, is a Google Font self-hosted through the @fontsource/manrope npm package and imported at the top of the layout. To use another Google Font, install its Fontsource package (npm install @fontsource/your-font), swap the imports, then update --font-heading in global.css:

astrosrc/layouts/Layout.astro
import '@fontsource/manrope/400.css';
import '@fontsource/manrope/500.css';
import '@fontsource/manrope/600.css';
import '@fontsource/manrope/700.css';
import '@fontsource/manrope/800.css';

Local Fonts

The body font, Satoshi, is self-hosted: three weights (400, 500, 700) live in public/fonts/ and are declared with @font-face at the top of global.css. Layout.astro also preloads satoshi-500.woff2 — update or remove that <link rel="preload"> if you replace the font:

csssrc/styles/global.css
@font-face {
  font-family: 'Satoshi';
  src: url('/fonts/satoshi-400.woff2') format('woff2');
  font-weight: 400;
  font-style: normal;
  font-display: swap;
}

Icon Libraries

Axora doesn’t use an icon library. Its icons are custom SVGs in three places:

  • src/components/sections/home/FeatureIcon.astro and TabIcon.astro — inline SVGs picked by a name prop.
  • src/data/social.js — the footer’s social icons, stored as SVG path strings next to each link.
  • public/images/ — a few icons used as images, such as home/pricing/check.png, mail.svg, and phone.svg.

Replacing & Adding Icons

To change a feature or tab icon, replace the <svg> markup in the matching {name === '…' && (…)} block of FeatureIcon.astro or TabIcon.astro; to add one, copy a block, give it a new name, and use that name in the data file. For social icons, paste a 24×24 SVG path into the path field in social.js. Image icons are swapped like any other image (see Replacing Images).

10 · Beginner Friendly

Content Editing

The fastest, lowest-risk way to make the site say what you want it to say.

New to code?

Everything in this section is plain text or attribute changes — no logic to break. Save the file, and your dev server (from Getting Started) will refresh the browser automatically so you can see the change right away.

Headings, Paragraphs & Buttons

In Axora, all text lives in the data files in src/data/ — not in the pages. Each home page section has its own exported object in src/data/home.js, in page order. Edit the quoted text and save:

javascriptsrc/data/home.js
// before
export const hero = {
  id: 'home',
  title: { before: 'Reinvent', accent: 'how to manage', after: 'Workflow' },
  cta: { label: 'Try Axora for a month', href: '/sign-up' },
};

// after
export const hero = {
  id: 'home',
  title: { before: 'Run', accent: 'every project', after: 'in one place' },
  cta: { label: 'Start your free trial', href: '/sign-up' },
};

Navigation & Footer

The logo, menu items, and header buttons are in src/data/navigation.js. The footer logo, link columns, and copyright line are in src/data/footer.js, and the social links in src/data/social.js. See Navigation for the full pattern.

Cards, Testimonials & Pricing

Repeating content blocks are driven by data arrays rather than hand-written per card, so adding or removing an item is a matter of editing the list. Pricing plans are built by a small plan() helper in home.js, with one list per Monthly/Yearly tab; the testimonial card and the FAQ items sit in the same pricing object:

javascriptsrc/data/home.js
periods: [
  {
    id: 'monthly',
    label: 'Monthly',
    plans: [plan('Starter', '19'), plan('Agency', '59', { featured: true, badge: 'Recommended' }), plan('Ultimate', '99')],
  },
  {
    id: 'yearly',
    label: 'Yearly',
    plans: [plan('Starter', '199'), plan('Agency', '599', { featured: true, badge: 'Recommended' }), plan('Ultimate', '999')],
  },
],

Blog Content & Contact Information

Axora doesn’t include a blog. The only contact details are the sales email and phone number beside the FAQ, in the pricing.faq.contacts array in src/data/home.js (placeholders: hello@example.com and 123-456-7890). The copyright line appears twice: in src/data/footer.js for the site footer, and in src/data/auth.js for the sign-in and sign-up pages.

11 · Guide

Navigation

Header, mobile menu, and footer links, in one predictable place.

Header Navigation

Primary nav links are defined in the mainNav array, so adding, removing, or reordering a link doesn’t require touching markup. Most items jump to a section of the home page by its id; an optional badge adds a small label like “New”. The Login and Signup buttons are in headerActions in the same file.

javascriptsrc/data/navigation.js
export const mainNav = [
  { label: 'Home', href: '/#home', current: true },
  {
    label: 'Features',
    href: '/#features',
    badge: { text: 'New', color: 'rgb(0, 177, 114)', bg: 'rgb(229, 247, 240)' },
  },
  { label: 'Benefits', href: '/#benefits' },
  { label: 'Integration', href: '/#integration' },
  { label: 'Pricing', href: '/#pricing' },
  { label: 'FAQs', href: '/#faq' },
];

Mobile Menu & Dropdown Menus

On smaller screens a hamburger button opens a slide-out drawer with the same mainNav links plus Login and Sign Up buttons (labels from headerActions). It’s a vanilla <script> inside src/components/Header.astro — no framework — which also makes the header sticky once you scroll past it, and closes the drawer when a link, the overlay, or Escape is used. There are no dropdown menus.

Footer Navigation

Footer link groups follow the same data-driven pattern: the columns array in src/data/footer.js holds the “Quick Links”, “Features”, and “Others” columns, each with a title and a links list. Social links come from src/data/social.js and point to root domains only.

Internal vs. External Links

Internal links should be root-relative (/sign-up or /#pricing, not the full domain) so they keep working across environments — the /#… form also works from the sign-in, sign-up, and 404 pages. External links should open safely in a new tab:

html
<a href="/about">About</a>
<a href="https://partner-site.com" target="_blank" rel="noopener noreferrer">Partner</a>

12 · Guide

Forms

What ships out of the box, and what still needs a backend.

Forms need somewhere to go

Axora’s only forms are the sign-in and sign-up forms. They’re static UI: each posts to an example.com placeholder, and no authentication or form service is wired up. Point them at your own endpoint before going live.

Contact Forms

Axora has no contact form — the FAQ block shows a sales email and phone number instead (see Content Editing). The sign-in and sign-up forms are rendered by AuthSection.astro from the form object in src/data/auth.js. To wire one up, change its action (and method, if needed); the fields list controls which inputs appear:

javascriptsrc/data/auth.js
form: {
  action: 'https://example.com/sign-up', // TODO: replace with your signup endpoint
  method: 'post',
  fields: [
    { name: 'username', type: 'text', placeholder: 'Username', autocomplete: 'username' },
    { name: 'email', type: 'email', placeholder: 'Email', autocomplete: 'email' },
    { name: 'password', type: 'password', placeholder: 'Password', autocomplete: 'new-password' },
  ],
},

Newsletter Forms

Axora doesn’t include a newsletter form, and no email provider is pre-wired. If you add one, the third-party services below or your email provider’s embed form are the quickest options.

Form Validation

Validation uses standard HTML only: every field in the sign-in and sign-up forms is required, and the sign-up email field uses type="email", so the browser blocks empty or malformed submissions. There’s no custom JavaScript validation — anything stricter (password rules, duplicate accounts) belongs on your server.

Third-Party Form Services

If you’d rather not run your own backend, services like Formspree, Getform, or Basin accept form submissions directly from static HTML and forward them to your email — typically a one-line change to the form’s action attribute.

API & Data

Axora fetches no data from any API — all content is static JavaScript in src/data/, baked into the HTML at build time. The notes below only apply if you add an external data source.

API Configuration

If you add an API, read its URL and keys from environment variables (see Configuration) rather than hard-coding them, so the same code can point at a staging or production API depending on environment:

env.env
PUBLIC_API_URL=https://example.com/api
PUBLIC_API_KEY=your_api_key
Never expose real credentials

The values above are placeholders. Keep real API keys out of version control, and prefer server-only variables (without the PUBLIC_ prefix) for anything sensitive.

Fetch Requests

typescript
const res = await fetch(`${import.meta.env.PUBLIC_API_URL}/products`, {
  headers: { Authorization: `Bearer ${import.meta.env.PUBLIC_API_KEY}` },
});
const data = await res.json();

Data Structures

Each data file exports plain objects whose fields match what its component reads. For example, every pricing plan in home.js has name, tagline, currency, price, unit, a features list, a cta (label and href), and optional featured/badge; images are { src, width, height, alt }. If you replace a data file with an API response, map the response into the same shape so the components don’t need to change.

Error Handling

typescript
try {
  const res = await fetch(apiUrl);
  if (!res.ok) throw new Error(`Request failed: ${res.status}`);
  const data = await res.json();
} catch (err) {
  // show a fallback UI state instead of a blank page
  console.error(err);
}

SEO

Per-page metadata, social previews, and the machine-readable files search engines expect.

Page Title & Meta Description

Pass a unique title and description into Layout on every page — these drive both the browser tab and the snippet shown in search results. The home page uses the layout’s default description (edit it in Layout.astro); the sign-in, sign-up, and 404 pages pass theirs from the seo objects in their data files:

astrosrc/pages/sign-in.astro
<Layout title={signIn.seo.title} description={signIn.seo.description} showFooter={false}>
  <AuthSection data={signIn} />
</Layout>

Canonical URL, Open Graph & Twitter/X Cards

Already set inside Layout.astro’s <head>, using the site value from astro.config.mjs to build absolute URLs. No Open Graph image ships with the template — add one to public/images/ and pass its path as the image prop (e.g. image="/images/og.png") to enable the og:image tag:

html
{canonical && <link rel="canonical" href={canonical} />}
<meta property="og:type" content="website" />
<meta property="og:title" content={title} />
<meta property="og:description" content={description} />
{ogImage && <meta property="og:image" content={ogImage} />}
<meta name="twitter:card" content="summary_large_image" />

Sitemap & Robots.txt

Axora includes Astro’s official sitemap integration (@astrojs/sitemap), which generates sitemap-index.xml automatically at build time from the site value. No robots.txt ships with the template — create public/robots.txt to control crawler access and point it to that sitemap:

textpublic/robots.txt
User-agent: *
Allow: /
Sitemap: https://example.com/sitemap-index.xml

Structured Data & Semantic HTML

Use landmark elements (<header>, <nav>, <main>, <article>) and a single <h1> per page so both search engines and screen readers can parse the page’s structure. Axora’s pages already follow this: the layout wraps content in <main id="main">, and each page has exactly one <h1>. No JSON-LD ships with the template; add structured data in the layout’s <head> for rich results (e.g. Organization or Article schema) where relevant to your content.

Deployment

Platform-by-platform steps. Confirm your rendering mode first — it changes the build output you deploy.

Static vs. SSR — check this first

Axora is a fully static Astro build with no adapter: it produces plain HTML/CSS/JS in dist/ that any static host can serve, so follow the static instructions below. If you later switch to server-side rendering (SSR via an adapter), you’ll need a Node-capable host or the platform’s matching adapter instead. Using the wrong instructions for your rendering mode is the most common deployment mistake.

Vercel

  1. Push the project to a GitHub, GitLab, or Bitbucket repository.
  2. In Vercel, choose Add New → Project and import that repository.
  3. Build command: npm run build · Output directory: dist (Astro static) — Vercel’s Astro preset detects this automatically in most cases.
  4. Add any environment variables from your .env file under Project Settings → Environment Variables (Axora needs none by default).
  5. Click Deploy.

Netlify

tomlnetlify.toml
[build]
  command = "npm run build"
  publish = "dist"

Connect the repository in the Netlify dashboard, confirm these build settings, add environment variables under Site configuration → Environment variables, and deploy.

Cloudflare Pages

Connect the repository, set the build command to npm run build and the output directory to dist. For SSR Astro sites, use the official @astrojs/cloudflare adapter instead of the static preset.

GitHub Pages

Set site and base in astro.config.mjs to match your repository URL, then build and publish the dist/ folder to the gh-pages branch (via the official astro build + a deploy action, or manually). GitHub Pages only serves static output — it cannot run an SSR adapter.

Traditional Hosting

For a static build, upload the contents of dist/ to your host’s public web root via FTP/SFTP or your host’s file manager. If you later switch to an SSR build that needs a Node process, the host must support running node continuously (a VPS or a Node-compatible host) — plain shared hosting without Node support cannot run it.

Build & Production

What happens when you run build, and a checklist before you ship.

bash
npm run build     # render pages, bundle assets, and write dist/
npm run preview   # serve dist/ locally, exactly as it will run in production

Build Output

The build writes static HTML for each page, hashed CSS/JS bundles (including GSAP), the Manrope font files, a copy of everything in public/, and sitemap-index.xml to dist/. This folder is disposable and regenerated by every build — it’s conventional to keep it out of Git via .gitignore.

Environment Variables in Production

Axora uses no environment variables out of the box, so there’s nothing to set unless you’ve added some. Variables from your local .env are not deployed automatically — each hosting platform requires you to set them again in its dashboard (see Deployment). A missing production variable is one of the most common causes of a build that works locally but fails, or behaves unexpectedly, once deployed.

Production Checklist

  • Run npm run build locally and confirm it completes with no errors.
  • Run npm run preview and click through the main pages.
  • Confirm the site URL in astro.config.mjs matches your real domain.
  • Set every environment variable from .env in your hosting platform’s dashboard.
  • Replace the example.com form action URLs in src/data/auth.js with your real endpoints.
  • Replace placeholder content: the sales email and phone in src/data/home.js, the demo video URL in the case study, and the copyright line in footer.js and auth.js.
  • Verify the favicons, logos, Open Graph image, and meta descriptions are your own, not the template defaults.

Troubleshooting

The most common problems, in the order you’re likely to hit them.

npm install fails

Cause
Node.js version too old, a corrupted local cache, or a stale lockfile from a different package manager.
Solution
Confirm node --version meets the requirement in Requirements, then run rm -rf node_modules package-lock.json && npm install.

Port already in use

Cause
Another process (often a previous dev server that didn’t shut down cleanly) is already listening on the default port.
Solution
Stop the other process, or start this one on a different port: npm run dev -- --port 4322.

Module not found

Cause
A missing dependency (for example gsap or @fontsource/manrope), or a typo in a relative import path.
Solution
Re-run npm install; check the import path casing and the number of ../ segments match the file’s real location (Axora uses relative imports, no path aliases).

Images not loading

Cause
The src in a data file doesn’t match the file’s real location or name in public/images/, or it includes public in the path.
Solution
Use a root-relative URL that starts at /images/ (e.g. /images/home/chat-laptop.png) and check the filename’s casing exactly — many hosts are case-sensitive. See Images & Assets.

Styles not loading

Cause
A new page isn’t wrapped in Layout (which imports global.css and the fonts), or a scoped <style> rule targets markup that lives in a different component.
Solution
Wrap every page in Layout from src/layouts/Layout.astro. Scoped styles only apply inside their own component — move the rule into that component, or into global.css if it should apply site-wide.

“Cannot read properties of undefined” or a blank section

Cause
A data object in src/data/ is missing a field its component reads (for example, a deleted cta or title), or a prop name is misspelled. Axora is plain JavaScript, so this isn’t caught until the page renders.
Solution
Read the error’s file and line number, compare the data object against the original fields the component uses (see Props and Data Structures), and restore or rename the missing field.

Build fails (but dev server works)

Cause
The dev server only renders the pages you open, while build renders every page — an error on a page you didn’t visit (or in a data file only that page uses) only appears at build time.
Solution
Read the full terminal output for the first error (later errors are often side effects of it); fix issues top to bottom and re-run.

Environment variables not working

Cause
Only relevant if you’ve added variables (Axora uses none by default): missing the PUBLIC_ prefix for a client-side value, or the dev server wasn’t restarted after editing .env.
Solution
Rename the variable with the PUBLIC_ prefix if it’s used in browser code, then stop and restart npm run dev — env changes aren’t hot-reloaded.

Deployment problems

Cause
Wrong output directory configured on the host, or environment variables set locally but not in the platform’s dashboard.
Solution
Re-check the build command and output folder against Deployment for your platform, and confirm every variable from .env is duplicated there.

FAQ

Quick answers to the questions we hear most.

How do I install the template?

Extract axora-astro-package.zip, open the axora-astro folder, run npm install, then start the dev server with npm run dev. The full walkthrough is in Getting Started.

Which Node.js version should I use?

Node 22.23.4 or later, as set in package.json — see Requirements. Astro 7 doesn’t run on older Node versions.

Can I use JavaScript instead of TypeScript?

Axora already is plain JavaScript — the data files and scripts are .js and the components are .astro with untyped props. tsconfig.json is only there for editor support. If you prefer TypeScript, you can rename files to .ts and add types gradually.

How do I change colors?

Update the color custom properties at the top of src/styles/global.css — --color-accent is the brand green. A few colors (the nav badges, feature icons, and the sign-in/sign-up background) are set in the data files or inline SVGs instead — see Styling.

How do I change fonts?

Swap the Manrope imports in Layout.astro or the Satoshi files and @font-face rules, then update --font-heading or --font-body — see Fonts & Icons.

How do I replace images?

Overwrite the file in public/images/ or update its src in the matching data file — see Images & Assets.

How do I add a new page?

Add a file to src/pages/ and wrap it in Layout; the route is created automatically — see Pages.

How do I deploy the template?

Platform-specific steps for Vercel, Netlify, Cloudflare Pages, GitHub Pages, and traditional hosts are in Deployment.

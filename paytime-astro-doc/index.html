01 · Overview

Introduction

Everything you need to know before you open your editor — what’s in the box, what it’s built with, and what it expects from your machine.

Welcome

Thanks for picking up Paytime, a fintech / payments app landing page template built with Astro, plain CSS, and vanilla JavaScript (scroll animations run on GSAP, the testimonial carousel on Swiper). This guide walks through installing the template, understanding how the project is organized, customizing content and styling, and shipping it to production. It’s written for developers who are comfortable with the command line but new to this specific codebase — if you already know Astro well, feel free to skip ahead using the sidebar.

  • GSAP-powered scroll-in animations across every section

02 · Setup

Getting Started

From a downloaded ZIP to a running dev server in five steps.

Installation & Extraction

  1. Download the template ZIP from your purchase confirmation email or account downloads page.
  2. Extract it to a folder on your machine — avoid folder names with spaces or special characters.
  3. Open that folder in your terminal and in your code editor.
bash
# Extract on macOS / Linux
unzip paytime-astro.zip -d paytime-astro
cd paytime-astro

Node.js Setup

Check which version of Node.js is currently active:

bash
node --version
# v22.12.0 or later

If you manage multiple Node versions, tools like nvm or fnm make switching painless:

bash
nvm install 22
nvm use 22

Install Dependencies

From the project root, install packages with your preferred package manager:

npm
npm install
pnpm
pnpm install
yarn
yarn install

This reads package.json and downloads every dependency into a local node_modules/ folder. It only needs to be re-run when dependencies change.

Run the Development Server

npm
npm run dev
pnpm
pnpm dev

This starts Astro’s local dev server (built on Vite) with hot module reloading — edits to components, pages, and styles appear in the browser immediately without a manual refresh. By default it’s available at http://localhost:4321; the terminal output will confirm the exact address.

Build for Production & Preview

bash
# Compile an optimized production build into dist/
npm run build

# Serve that build locally to sanity-check it
npm run preview

build type-checks the project, bundles and minifies assets, and writes static output to dist/. preview serves that exact output locally so you can verify it before deploying — it does not rebuild automatically, so re-run build after further changes.

Which command do I actually need?

Use dev while you’re customizing the template. Use build, then preview, once before you deploy — it catches issues (like a broken import or a typo’d file path) that the dev server tolerates but production won’t.

04 · Reference

Configuration

The files that control how the project builds, and where to set site-wide values.

package.json

Defines dependencies and the scripts you run from the terminal (dev, build, preview). Add your own script here if you introduce a new tool.

jsonpackage.json
{
  "name": "paytime-astro",
  "version": "1.0.0",
  "engines": { "node": ">=22.12.0" },
  "scripts": {
    "dev": "astro dev",
    "build": "astro build",
    "preview": "astro preview",
    "astro": "astro"
  }
}

astro.config.mjs

Controls integrations, the deployed site URL, and build behavior. The only integration this template registers is @astrojs/sitemap, which generates sitemap-index.xml at build time.

javascriptastro.config.mjs
import { defineConfig } from 'astro/config';
import sitemap from '@astrojs/sitemap';

export default defineConfig({
  site: 'https://example.com', // used to build absolute URLs for SEO tags
  integrations: [sitemap()],
});
Update the site URL before deploying

site still points at the placeholder https://example.com. Change it to your real domain before running npm run build — the sitemap, canonical URLs, and Open Graph tags all depend on it.

tsconfig.json

This template has no .ts/.tsx source files and no path aliases — every import is a relative path (e.g. ../components/Navbar.astro). tsconfig.json still exists because Astro uses it to power editor type-checking and autocomplete inside each component’s frontmatter script:

jsontsconfig.json
{
  "extends": "astro/tsconfigs/strict",
  "include": [".astro/types.d.ts", "**/*"],
  "exclude": ["dist"]
}

There’s no astro check script wired into package.json, so type errors won’t fail a build or a CI run on their own — add one ("typecheck": "astro check") if you want that enforced.

Environment Variables (.env)

Paytime doesn’t read any environment variables out of the box — it’s a fully static site with no API calls (see API & Data). If you add one later, create a .env file in the project root for values that differ between environments (API URLs, keys) or shouldn’t be committed to Git. Variables must be prefixed PUBLIC_ to be readable in client-side code.

env.env
# Exposed to the browser — never put secrets here
PUBLIC_SITE_URL=https://example.com

# Server-only — safe for secrets, not readable in browser code
API_SECRET_KEY=your_secret_key
Never commit .env

Add .env to .gitignore (it usually is by default). Anything without the PUBLIC_ prefix should stay off the client entirely.

05 · Guide

Pages

How routes are created, and the real routes this template ships.

Creating a New Page

Astro uses file-based routing: any .astro or .md file placed in src/pages/ automatically becomes a route matching its file path. This template currently ships four routes:

text
src/pages/index.astro                       →  /
src/pages/components.astro                  →  /components
src/pages/template-info/style-guide.astro   →  /template-info/style-guide
src/pages/404.astro                         →  served automatically for unmatched routes

To add a page, create a new file in src/pages/, import the shared layout, and (unless it’s a bare utility page) add the Navbar and Footer yourself — Layout.astro only supplies the <head> and document shell, not page chrome:

astrosrc/pages/services.astro
---
import Layout from '../layouts/Layout.astro';
import Navbar from '../components/Navbar.astro';
import Footer from '../components/Footer.astro';
---
<Layout title="Services - Paytime" description="...">
  <Navbar page="services" />
  <h1>Our Services</h1>
  <Footer page="services" />
</Layout>

Editing an Existing Page

Open the relevant file under src/pages/ and edit the markup directly. Anything imported from src/components/ lives elsewhere — edit the component file itself to change content that repeats across multiple pages (like a shared call-to-action block).

Dynamic Routes

Not used in this template

Paytime is a single-page marketing site with no blog or product listings, so it ships no [param].astro files. The pattern below is included for reference if you add one (e.g. a blog).

Files wrapped in square brackets, such as [slug].astro, generate multiple pages from a single template — commonly used for blog posts or product pages. Astro requires a getStaticPaths() function for these on statically-generated sites:

astrosrc/pages/blog/[slug].astro
---
export async function getStaticPaths() {
  const posts = await import.meta.glob('./posts/*.md');
  return Object.keys(posts).map((path) => ({
    params: { slug: path.split('/').pop().replace('.md', '') },
  }));
}
---

Layouts

There is exactly one layout, src/layouts/Layout.astro. It supplies the <html> shell and all <head> metadata (title, description, canonical URL, Open Graph/Twitter tags, favicon, the Google Fonts link), but — unlike a typical Astro starter — it does not render a header or footer itself. Every page renders through it via <slot />:

astrosrc/layouts/Layout.astro
---
import "../styles/normalize.css";
import "../styles/webflow-base.css";
import "../styles/theme.css";

const {
  title = "RNN Studio - Astro website template",
  description = "Fastest way to make payment anywhere.",
  ogImage = "/images/love-paytime.webp",
  noindex = false,
} = Astro.props;
---
<html lang="en">
  <head><title>{title}</title></head>
  <body class="main-body">
    <slot /> <!-- page content, including Navbar/Footer if the page wants them, goes here -->
  </body>
</html>

Page Metadata & the 404 Page

Pass title and description (and optionally ogImage or noindex) into Layout on every page for correct browser tabs and search results (see also SEO). src/pages/404.astro is served automatically whenever no route matches, and passes noindex so it’s excluded from search engines.

06 · Guide

Components

The building blocks pages are assembled from, and how data flows into them.

Reusable Components

Components live in src/components/ and encapsulate one page section — Hero, Pricing, FAQ, Footer, and so on. Every component in this template is a plain .astro file — there’s no React and nothing under src/components/ ends in .tsx.

Props

Props are the inputs a component accepts, similar to HTML attributes, read inside the component’s frontmatter via Astro.props. This template doesn’t declare TypeScript interfaces for them — props are destructured directly with a default value, which is what most of its components (most of which take none at all) look like. Navbar and Footer are the two that do, both taking a single page string used to highlight the current nav link and to scope in-page anchor links:

astrosrc/components/Navbar.astro
---
const { page = "home" } = Astro.props;
---

In plain language: page is optional and defaults to "home" if the caller doesn’t pass it. <Navbar page="components" /> tells the component it’s rendering on the /components route, so its nav link builds an absolute /#Feature-style href instead of a same-page #Feature anchor, and marks the “Components” link current.

Component Composition

A component can import and render another component directly — Hero.astro renders Navbar internally so every page that includes Hero gets the nav for free:

astrosrc/components/Hero.astro
---
import Navbar from './Navbar.astro';
---
<section class="hero-section">
  <Navbar page="home" />
  ...
</section>

Pages that don’t use Hero (like /components or the style guide) import and render Navbar themselves instead.

Passing Data to Components

In Astro, props are passed the same way as HTML attributes. Content that repeats — FAQ questions, testimonial quotes, pricing tiers — isn’t passed in as props from a parent, though: each component declares its own array as a local const in its frontmatter (there’s no separate src/data/ folder in this template):

astrosrc/components/Pricing.astro
---
const plans = {
  monthly: [
    { name: 'Starter', price: '19', suffix: '/mo', cta: 'secondary-btn' },
    { name: 'Economy', price: '59', suffix: '/mo', cta: 'primary-btn' },
  ],
};
---

See Content Editing for where to make these changes in practice.

No UI framework, by design

Interactivity (the mobile nav drawer, tabs, the FAQ accordion, the testimonial slider) is handled with small vanilla-JS files in src/scripts/, imported via an inline <script> in the component that needs them — not with React or another client-side framework.

07 · Guide

Styling

Where to change colors, type, and spacing without fighting the build.

Global Styles & CSS Variables

Three stylesheets are imported globally in Layout.astro, in this order: normalize.css (a browser reset), webflow-base.css (the utility classes and component styles carried over from the original Webflow export — class names like .hero-section or .primary-btn come from here), and theme.css (this template’s own tokens, font declarations, and overrides). The color palette and a few shared values live as CSS custom properties at the top of theme.css:

csssrc/styles/theme.css
:root {
  --primary: #502ff5;
  --light-low: #f3f1ff;
  --heading-color: #0f0840;
  --body: #54506f;
  --white: white;
  --orange: #ffb459;
}

These same swatches are previewed on the /template-info/style-guide page.

Component Styles

No component in this template uses Astro’s scoped <style> blocks. Instead, every element is styled through the utility/component classes defined globally in webflow-base.css and theme.css (the Webflow-derived naming convention, e.g. hero-section, nav-container, primary-btn). To restyle something, find its class in webflow-base.css and edit the rule there — changes apply everywhere that class is used.

Responsive Design, Typography & Spacing

Type sizes (.h1–.h6, .body and its variants) and responsive breakpoints are defined in webflow-base.css, with color and font-family tokens layered on top in theme.css. Prefer adjusting these shared classes over overriding sizes on individual elements, so the site keeps a consistent rhythm as you edit it.

Avoid editing dist/

The dist/ folder is generated output — any change made there is overwritten on the next build. Always edit files under src/.

Images & Assets

This template keeps everything in one place — there’s no src/assets/ folder.

LocationUse forBehavior
public/images/Every image and icon the site uses (referenced as plain <img src="/images/...">)Copied as-is, no processing
public/fonts/The self-hosted Satoshi .otf filesCopied as-is, no processing
public/videos/The background video used in the components showcaseCopied as-is, no processing
No astro:assets / <Image> here

Nothing in this template imports from astro:assets or the built-in optimized <Image /> component — every image is a plain <img> tag pointing at a file in public/images/, so nothing is resized, re-encoded, or hashed at build time.

Replacing Images

Swap the file in public/images/ in place (keeping the same filename), or update the src attribute to point at your new file:

astrosrc/components/Hero.astro
<img
  class="hero-image"
  src="/images/phone.webp"
  alt="Phone frame showing the app"
  sizes="(max-width: 479px) 83vw, (max-width: 767px) 47vw, 378px"
  loading="lazy"
  srcset="/images/phone-p-500.png 500w, /images/phone.webp 757w"
/>

Supported Formats & SVGs

The template ships WebP, PNG, and JPG photos alongside plain SVG icons and illustrations, all referenced with ordinary <img> tags — there’s no SVG-as-component pattern here.

Image Optimization

Because images live in public/, none of them are resized or re-encoded by Astro at build time. Several images (the phone mockup, the review photos) already ship with multiple pre-sized variants — e.g. phone-p-500.png alongside phone.webp — wired up manually with native srcset/sizes attributes, as shown above. If you add a new image, either generate your own size variants the same way, or move the file into a new src/assets/ folder and switch that reference to Astro’s <Image /> component if you want automatic optimization going forward.

Rule of thumb

Add every new image to public/images/ to match how this template already works. Compress large source photos yourself before adding them — nothing does it for you at build time.

09 · Guide

Fonts & Icons

Swapping typefaces and icon sets without touching every component.

Google Fonts

The body typeface, Outfit, loads from Google Fonts via a <link> tag in Layout.astro’s <head>. Replace it with your chosen font’s embed code, then update the font-family on body in theme.css:

htmlsrc/layouts/Layout.astro
<link rel="preconnect" href="https://fonts.googleapis.com">
<link rel="preconnect" href="https://fonts.gstatic.com" crossorigin>
<link href="https://fonts.googleapis.com/css2?family=Outfit:wght@100;200;300;400;500;600;700;800;900&display=swap" rel="stylesheet">

Local Fonts

The display typeface, Satoshi, is self-hosted — five weights of .otf files in public/fonts/, declared with @font-face at the top of theme.css:

csssrc/styles/theme.css
@font-face {
  font-family: Satoshi;
  src: url('/fonts/Satoshi-Bold.otf') format("opentype");
  font-weight: 700;
  font-style: normal;
  font-display: swap;
}
/* repeated for Black (900), Medium (500), Regular (400), and Light (300) */

Icon Libraries

This template doesn’t use an icon library or sprite system. Icons (the rating stars, the accordion arrow, the app store badges, the social links, etc.) are individual SVG files in public/images/, referenced with plain <img> tags.

Replacing & Adding Icons

To swap an icon, replace the SVG file in public/images/ (keeping the same filename) or update the src it’s referenced by. To add a new one, drop an SVG into public/images/ and reference it the same way — <img src="/images/your-icon.svg" alt="..." />. There’s no icon component wrapper, so there are no size/color/strokeWidth props to set; size and color come from CSS on the <img> or, for inline social icons, from the SVG’s own fill/currentColor.

Content Editing

The fastest, lowest-risk way to make the site say what you want it to say.

New to code?

Everything in this section is plain text or attribute changes — no logic to break. Save the file, and your dev server (from Getting Started) will refresh the browser automatically so you can see the change right away.

Headings, Paragraphs & Buttons

Find the relevant page in src/pages/, locate the text between the tags, and edit it directly:

astrosrc/components/Hero.astro
<!-- before -->
<h1 class="display-title semi-bold">Fastest way to make payment anywhere.</h1>
...
<div>Play Store</div>

<!-- after -->
<h1 class="display-title semi-bold">Get paid in seconds, anywhere.</h1>
...
<div>Download the app</div>

There’s no separate Button component — every call-to-action is a plain <a> styled with the primary-btn/secondary-btn classes from webflow-base.css, e.g. <a href="/contact" class="primary-btn w-button">Get Started</a>.

Navigation & Footer

Nav links live directly inside Navbar.astro; footer content lives directly inside Footer.astro — there’s no shared src/data/ file. See Navigation for the full pattern.

Cards, Testimonials & Pricing

Repeating content blocks are driven by a local array at the top of the component that renders them, so adding or removing an item is a matter of editing the list in that one file:

astrosrc/components/ReviewSlider.astro
---
const reviews = [
  { image: '/images/IMG-2.webp', name: 'Smith Grey' },
  { image: '/images/IMG.webp', name: 'Smith Grey' },
];
---

Pricing.astro (the plans object), FAQ.astro (the columnOne/columnTwo arrays), and AppPointsTabs.astro (the tabs array) follow the same pattern — open the relevant component and edit its array.

Contact & Social Links

This template has no blog. The footer copyright line and the three social icons (LinkedIn, Facebook, Twitter/X) are hardcoded directly in src/components/Footer.astro — edit the placeholder https://linkedin.com / https://facebook.com / https://twitter.com hrefs there to point at your real profiles, and update the “RNN Studio” name in the copyright line.

11 · Guide

Navigation

Header, mobile menu, and footer links, in one predictable place.

Header Navigation

Nav links live as an array directly inside Navbar.astro itself (not a separate data file), so adding, removing, or relabeling a link is a one-file edit:

astrosrc/components/Navbar.astro
---
const links = [
  { hash: "Home", label: "Home" },
  { hash: "Feature", label: "Features " },
  { hash: "Review", label: "Reviews" },
  { hash: "Pricing", label: "Pricing" },
  { hash: "Faqs", label: "Faqs" },
];
---

Each entry links to an in-page section by its id (e.g. #Feature matches the AppFeatures section’s wrapper id). On the homepage the link becomes #Feature; on any other page it becomes /#Feature so it still resolves back to the homepage section. A fixed “Components” link to /components is appended separately below the array, since it’s a real route rather than an in-page anchor.

Mobile Menu

The mobile menu toggle is a small vanilla-JS file, src/scripts/nav-menu.js, imported via an inline <script> at the bottom of Navbar.astro — not a React island. It toggles the .w-nav-menu panel open/closed and also drives the scroll-spy behavior that highlights the current section’s nav link. There are no dropdown submenus in this template.

Footer Navigation

Footer.astro doesn’t repeat the header’s nav links — it only has the “Get Started” CTA, the copyright line, and the three social icons. See Content Editing for where to change those.

Internal vs. External Links

Internal links should be root-relative (/about, not the full domain) so they keep working across environments. External links should open safely in a new tab:

html
<a href="/about">About</a>
<a href="https://partner-site.com" target="_blank" rel="noopener noreferrer">Partner</a>

12 · Guide

Forms

This template doesn’t include any forms.

No contact, newsletter, or search form ships with this template

There isn’t a single <form> or <input> element anywhere in src/. Every call to action (“Get Started”, “Play Store”) is a plain link (<a>), pointing at an app-store URL, an in-page section, or a placeholder href you’ll want to fill in — not a submission endpoint.

Adding a Contact Form

If you need one, the simplest approach with this stack is a plain HTML <form> inside an .astro component, posted to a third-party form service so you don’t need to run your own backend:

html
<form action="https://formspree.io/f/your-form-id" method="POST">
  <input type="email" name="email" required />
  <button type="submit" class="primary-btn w-button">Send</button>
</form>

Newsletter Forms

Not included — there is no email capture anywhere in this template.

Form Validation

If you add a form, browser-native validation (required, type="email", minlength) gives users immediate feedback without any JavaScript. This template doesn’t include a validation library.

Third-Party Form Services

Since there’s no backend in this template, services like Formspree, Getform, or Basin are the fastest way to accept a form submission directly from the static HTML — point the form’s action at the endpoint they give you.

13 · Guide

API & Data

Paytime is fully static and fetches nothing at build or run time.

No API calls in this template

There’s no fetch(), no external data source, and no .env variable in use anywhere in src/ (see Configuration). Every piece of content — pricing tiers, testimonials, FAQ copy — is a hardcoded array inside the component that renders it. The reference below is only relevant if you extend the template to pull in real data.

API Configuration

API URLs and keys are read from environment variables (see Configuration) rather than hard-coded, so the same code can point at a staging or production API depending on environment:

env.env
PUBLIC_API_URL=https://example.com/api
PUBLIC_API_KEY=your_api_key
Never expose real credentials

The values above are placeholders. Keep real API keys out of version control, and prefer server-only variables (without the PUBLIC_ prefix) for anything sensitive.

Fetch Requests

typescript
const res = await fetch(`${import.meta.env.PUBLIC_API_URL}/products`, {
  headers: { Authorization: `Bearer ${import.meta.env.PUBLIC_API_KEY}` },
});
const data = await res.json();

Data Structures

Since this template has no API integration, there’s no response shape to document. If you add a data source, the existing hardcoded arrays (e.g. Pricing.astro’s plans object, or ReviewSlider.astro’s reviews array — see Components) show the field names each component currently expects, which is a reasonable starting shape for a real API response.

Error Handling

typescript
try {
  const res = await fetch(apiUrl);
  if (!res.ok) throw new Error(`Request failed: ${res.status}`);
  const data = await res.json();
} catch (err) {
  // show a fallback UI state instead of a blank page
  console.error(err);
}

SEO

Per-page metadata, social previews, and the machine-readable files search engines expect.

Page Title & Meta Description

Pass a unique title and description into Layout on every page — these drive both the browser tab and the snippet shown in search results:

astrosrc/pages/components.astro
<Layout
  title="Components - RNN Studio"
  description="Slightly domed and divided by arches into stiff"
>

Canonical URL, Open Graph & Twitter/X Cards

All handled automatically inside Layout.astro, using the site value from astro.config.mjs to build absolute URLs — you don’t need to add these tags per page, only pass title/description/ogImage:

<link rel="canonical" href={canonicalURL} />

Deployment

Platform-by-platform steps. Confirm your rendering mode first — it changes the build output you deploy.

This template builds static output

Paytime uses Astro’s default static output — astro.config.mjs registers no SSR adapter, so npm run build produces plain HTML/CSS/JS in dist/ that any static host can serve, with no Node process required at runtime.

Vercel

  1. Push the project to a GitHub, GitLab, or Bitbucket repository.
  2. In Vercel, choose Add New → Project and import that repository.
  3. Build command: npm run build · Output directory: dist (Astro static) — Vercel’s Astro preset detects this automatically in most cases.
  4. Add any environment variables from your .env file under Project Settings → Environment Variables.
  5. Click Deploy.

Netlify

tomlnetlify.toml
[build]
  command = "npm run build"
  publish = "dist"

Connect the repository in the Netlify dashboard, confirm these build settings, add environment variables under Site configuration → Environment variables, and deploy.

Cloudflare Pages

Connect the repository, set the build command to npm run build and the output directory to dist. For SSR Astro sites, use the official @astrojs/cloudflare adapter instead of the static preset.

GitHub Pages

Set site and base in astro.config.mjs to match your repository URL, then build and publish the dist/ folder to the gh-pages branch (via the official astro build + a deploy action, or manually). GitHub Pages only serves static output — it cannot run an SSR adapter.

Traditional Hosting

For a static build, upload the contents of dist/ to your host’s public web root via FTP/SFTP or your host’s file manager. For an SSR build or a React/Vite app that needs a Node process, the host must support running node continuously (a VPS or a Node-compatible host) — plain shared hosting without Node support cannot run it.

Build & Production

What happens when you run build, and a checklist before you ship.

bash
npm run build     # type-check, bundle, and write dist/
npm run preview   # serve dist/ locally, exactly as it will run in production

Build Output

The build writes static HTML, hashed CSS/JS bundles, and optimized images to dist/ (or build/, for some Vite/React setups). This folder is disposable and regenerated by every build — it’s conventional to keep it out of Git via .gitignore.

Environment Variables in Production

Variables from your local .env are not deployed automatically — each hosting platform requires you to set them again in its dashboard (see Deployment). A missing production variable is one of the most common causes of a build that works locally but fails, or behaves unexpectedly, once deployed.

Production Checklist

  • Run npm run build locally and confirm it completes with no errors.
  • Run npm run preview and click through the main pages.
  • Confirm the site URL in astro.config.mjs matches your real domain.
  • Set every environment variable from .env in your hosting platform’s dashboard.
  • Check that forms, if any, point at a real endpoint rather than a placeholder.
  • Verify favicon, Open Graph image, and meta descriptions are your own, not the template defaults.

Troubleshooting

The most common problems, in the order you’re likely to hit them.

npm install fails

Cause
Node.js version too old, a corrupted local cache, or a stale lockfile from a different package manager.
Solution
Confirm node --version meets the requirement in Requirements, then run rm -rf node_modules package-lock.json && npm install.

Port already in use

Cause
Another process (often a previous dev server that didn’t shut down cleanly) is already listening on the default port.
Solution
Stop the other process, or start this one on a different port: npm run dev -- --port 4322.

Module not found

Cause
A missing dependency, or a typo in a relative import path. This template has no path aliases configured (see Configuration), so every import must be a correct relative path.
Solution
Re-run npm install; check the import path and file casing match exactly, e.g. ../components/Navbar.astro.

Images not loading

Cause
A typo in the file path, or the file is missing from public/images/. All images in this template are referenced as root-relative URLs, e.g. /images/logo.svg.
Solution
Confirm the file actually exists at that path under public/ (case-sensitive on most hosts), and review Images & Assets.

Styles not loading

Cause
One of the three global stylesheets isn’t imported, or a class name typo means webflow-base.css has no matching rule.
Solution
Confirm normalize.css, webflow-base.css, and theme.css are all still imported at the top of Layout.astro’s frontmatter; check the element’s class name against Styling.

Editor red squiggles in a component’s frontmatter

Cause
Astro’s strict tsconfig.json preset still type-checks plain JS in the frontmatter script, even though this template writes no explicit types (see Components).
Solution
Read the error’s file and line number and adjust the code it’s pointing at. These are editor-only warnings here — there’s no astro check script wired in, so they won’t fail npm run build.

Build fails (but dev server works)

Cause
The dev server is more forgiving than build, which fully type-checks the project — an issue tolerated in dev can fail the build.
Solution
Read the full terminal output for the first error (later errors are often side effects of it); fix issues top to bottom and re-run.

Environment variables not working

Cause
Missing the PUBLIC_ prefix for a client-side value, or the dev server wasn’t restarted after editing .env.
Solution
Rename the variable with the PUBLIC_ prefix if it’s used in browser code, then stop and restart npm run dev — env changes aren’t hot-reloaded.

Deployment problems

Cause
Wrong output directory configured on the host, or environment variables set locally but not in the platform’s dashboard.
Solution
Re-check the build command and output folder against Deployment for your platform, and confirm every variable from .env is duplicated there.

FAQ

Quick answers to the questions we hear most.

How do I install the template?

Extract the ZIP, run your package manager’s install command, then start the dev server. The full walkthrough is in Getting Started.

Which Node.js version should I use?

Node 22.12.0 or later, matching engines.node in package.json — see Requirements.

Does this template use TypeScript?

Not in the sense of written type annotations — every component is plain .astro with untyped JS in its frontmatter. The tsconfig.json that ships with it only powers editor autocomplete and type-checking; see Configuration.

How do I change colors?

Update the CSS custom properties at the top of src/styles/theme.css — see Styling.

How do I change fonts?

Swap the font import and update the corresponding --font-* variable — see Fonts & Icons.

How do I replace images?

Swap the file or update the import path — see Images & Assets.

How do I add a new page?

Add a file to src/pages/; the route is created automatically — see Pages.

How do I deploy the template?

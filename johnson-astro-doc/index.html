01 · Overview

Introduction

Everything you need to know before you open your editor — what’s in the box, what it’s built with, and what it expects from your machine.

Welcome

Thanks for picking up Johnson, a bold, single-person portfolio theme for designers and creatives, built with Astro. It pairs oversized display type with soft pastel colour, playful GSAP motion and a case-study layout that lets your work carry the page. This guide walks through installing the template, understanding how the project is organized, customizing content and styling, and shipping it to production. It’s written for developers who are comfortable with the command line but new to this specific codebase — if you already know Astro well, feel free to skip ahead using the sidebar.

What’s Included

Source files

The full, uncompiled project source — components, pages, styles, and configuration.

Production build

Run npm run build to generate a static dist/ folder you can deploy anywhere. dist/ is generated output and is not included in the download.

Design assets

Placeholder portfolio imagery in src/assets/, the logo and SVG UI icons in public/images/, and the self-hosted General Sans variable font in public/fonts/. No Figma or other design source files are included.

This documentation

A single self-contained HTML file — open it directly in any browser, no server required.

Features

  • Six page types: home (hero + selected work), work index, about (bio, experience, certifications, skills marquee, process), contact, a generated case-study page per project, and a 404 page.
  • Projects as an Astro content collection — each case study is one JSON file in src/content/work/, validated by a schema; case-study pages and prev/next links are generated automatically.
  • GSAP motion: a magnetic nav with a slide-in overlay menu, a scroll-driven colour shift behind the work list, stacked process cards, a looping word ticker, skill marquees, and hover micro-interactions. Decorative loops respect prefers-reduced-motion.
  • Optimized, responsive images through Astro’s built-in astro:assets.
  • SEO on every page: title and description, Open Graph and Twitter tags, canonical URLs, and a sitemap via @astrojs/sitemap.
  • Accessible by default: real buttons for the menu, focus management, Esc closes the menu and lightbox, visible focus styles, and labelled form fields.
  • Plain JavaScript and CSS — no TypeScript, UI framework, or CSS framework. The only runtime dependency is GSAP.

Technology Stack

Johnson is a static Astro site written in plain JavaScript and CSS, with GSAP for animation:

Astro 7 Vite GSAP @astrojs/sitemap Plain CSS JavaScript

02 · Setup

Getting Started

From a downloaded ZIP to a running dev server in five steps.

Installation & Extraction

  1. Download the template ZIP from your purchase confirmation email or account downloads page.
  2. Extract it to a folder on your machine — avoid folder names with spaces or special characters.
  3. Open that folder in your terminal and in your code editor.
bash
# Extract on macOS / Linux
unzip johnson-astro-package.zip
cd johnson-astro-package/johnson-astro

Node.js Setup

Check which version of Node.js is currently active:

bash
node --version
# v22.12.0 or later

If you manage multiple Node versions, tools like nvm or fnm make switching painless:

bash
nvm install 22
nvm use 22

Install Dependencies

From the project root, install packages with your preferred package manager:

npm
npm install
pnpm
pnpm install
yarn
yarn install

This reads package.json and downloads every dependency into a local node_modules/ folder. It only needs to be re-run when dependencies change.

Run the Development Server

npm
npm run dev
pnpm
pnpm dev

This starts Vite’s local dev server with hot module reloading — edits to components, pages, and styles appear in the browser immediately without a manual refresh. By default it’s available at http://localhost:4321; the terminal output will confirm the exact address.

Build for Production & Preview

bash
# Compile an optimized production build into dist/
npm run build

# Serve that build locally to sanity-check it
npm run preview

build validates the work content collection, optimizes images, bundles and minifies CSS/JS, and writes static output to dist/. preview serves that exact output locally so you can verify it before deploying — it does not rebuild automatically, so re-run build after further changes.

Which command do I actually need?

Use dev while you’re customizing the template. Use build, then preview, once before you deploy — it catches issues (like a missing import or an image that only fails to resolve during the full build) before they reach production.

04 · Reference

Configuration

The files that control how the project builds, and where to set site-wide values.

package.json

Defines dependencies and the scripts you run from the terminal (dev, build, preview). Add your own script here if you introduce a new tool.

jsonpackage.json
{
  "name": "johnson-astro",
  "type": "module",
  "version": "0.0.1",
  "engines": { "node": ">=22.12.0" },
  "scripts": {
    "dev": "astro dev",
    "build": "astro build",
    "preview": "astro preview",
    "astro": "astro"
  },
  "dependencies": {
    "@astrojs/sitemap": "^3.7.4",
    "astro": "^7.3.4",
    "gsap": "^3.15.0"
  }
}

astro.config.mjs

Controls integrations, the deployed site URL, and build behavior. Johnson registers only the sitemap integration. Replace the placeholder site value with your real domain before deploying — it’s used for canonical URLs, Open Graph image URLs, and the sitemap.

javascriptastro.config.mjs
import { defineConfig } from 'astro/config';
import sitemap from '@astrojs/sitemap';

export default defineConfig({
  // Replace with your deployed URL — used for canonical URLs, OG images and the sitemap.
  site: 'https://example.com',
  integrations: [sitemap()],
});

tsconfig.json

Johnson is written in plain JavaScript — there are no .ts files. This file only extends Astro’s strict preset so your editor (via the Astro extension) can offer autocomplete and hints. No path aliases are defined; all imports use relative paths such as ../components/Navbar.astro.

jsontsconfig.json
{
  "extends": "astro/tsconfigs/strict",
  "include": [".astro/types.d.ts", "**/*"],
  "exclude": ["dist"]
}

Environment Variables (.env)

Johnson doesn’t read any environment variables out of the box, so no .env file is needed to run it. If you add one later (for a form endpoint or API, say), create a .env file in the project root for values that differ between environments or shouldn’t be committed to Git. Variables must be prefixed PUBLIC_ to be readable in client-side code.

env.env
# Exposed to the browser — never put secrets here
PUBLIC_SITE_URL=https://example.com

# Server-only — safe for secrets, not readable in browser code
API_SECRET_KEY=your_secret_key
Never commit .env

Add .env to .gitignore (it usually is by default). Anything without the PUBLIC_ prefix should stay off the client entirely.

05 · Guide

Pages

How routes are created, and how a page is generated for every case study.

Creating a New Page

Astro uses file-based routing: any .astro or .md file placed in src/pages/ automatically becomes a route matching its file path.

text
src/pages/index.astro          →  /          (hero + first five projects)
src/pages/work.astro           →  /work      (every project + process)
src/pages/about.astro          →  /about
src/pages/contact.astro        →  /contact
src/pages/project/[slug].astro →  /project/:slug  (one per case study)
src/pages/404.astro            →  shown for any unknown URL

To add a page, create a new file in src/pages/ using the layout and structure of an existing, similar page as a starting point:

astrosrc/pages/services.astro
---
import BaseLayout from '../layouts/BaseLayout.astro';
---
<BaseLayout title="Services" description="Design services I offer.">
  <h1>Services</h1>
</BaseLayout>

Editing an Existing Page

Open the relevant file under src/pages/ and edit the markup directly. Anything imported from src/components/ lives elsewhere — edit the component file itself to change content that repeats across multiple pages (like a shared call-to-action block).

Dynamic Routes

Files wrapped in square brackets, such as [slug].astro, generate multiple pages from a single template. Johnson uses src/pages/project/[slug].astro to build one case-study page per JSON file in src/content/work/; the file name becomes the slug (e.g. beyond-energy.json → /project/beyond-energy/). Its getStaticPaths() also passes the previous and next project, wrapping around at the ends:

astrosrc/pages/project/[slug].astro
---
export async function getStaticPaths() {
  const projects = (await getCollection('work')).sort((a, b) => a.data.order - b.data.order);
  return projects.map((project, index) => ({
    params: { slug: project.id },
    props: {
      project,
      prev: projects[(index - 1 + projects.length) % projects.length],
      next: projects[(index + 1) % projects.length],
    },
  }));
}
---

Layouts

Layouts (in src/layouts/) wrap page content with shared structure — the <html> shell, <head> metadata, header, and footer. Johnson has one, BaseLayout.astro, and every page renders inside it via a <slot />. It accepts title, description (defaults to site.description), image (the Open Graph image), footer (set false to hide the footer, as the contact and 404 pages do), and chrome (set false to hide the navbar, footer, scroll indicator, and mail button). Simplified:

astrosrc/layouts/BaseLayout.astro
---
import '../styles/global.css'; // plus normalize, base-framework, overrides
import Navbar from '../components/Navbar.astro';
import Footer from '../components/Footer.astro';
import { site } from '../data/site.js';

const { title, description = site.description, image, footer = true, chrome = true } = Astro.props;
const pageTitle = title ? `${title} | ${site.name}` : `${site.name} — ${site.tagline}`;
---
<html lang="en">
  <head><title>{pageTitle}</title> <!-- + description, canonical, OG/Twitter tags --></head>
  <body>
    {chrome && <Navbar />}
    <main><slot /></main> <!-- page content is injected here -->
    {chrome && footer && <Footer />}
  </body>
</html>

Page Metadata & the 404 Page

Pass a title and description into your layout’s props on every page for correct browser tabs and search results (see also SEO). A file named 404.astro in src/pages/ is served automatically whenever no route matches — Johnson’s shows a large “404”, a short message, and a “Back home” link.

Components

The building blocks pages are assembled from, and how data flows into them.

Reusable Components

Components live in src/components/ and encapsulate one piece of UI — a link, a project card, the navigation bar — so it can be reused across pages without copy-pasting markup. All of Johnson’s components are .astro files; the animated ones carry their own <script> that imports GSAP.

ComponentUsed for
NavbarLogo, desktop links, and the round menu button with the slide-in overlay menu
Footer, FooterMetaSite footer; FooterMeta holds the copyright line and the About/Contact links
SocialLinks, SocialIconEmail link plus social icons from socialLinks in site.js
MailButton, ScrollIndicatorFloating mail button and page-scroll indicator (rendered by the layout)
HeroHome-page hero with the spinning looped-text badge
AboutHeroHero with a looping word ticker (About and Work pages)
AboutMe, AboutTable, SkillMarqueeAbout-page bio, experience/certification tables, and skill marquees
ProcessStepsStacked, sticky process cards (About and Work pages)
WorkList, WorkCardProject list with the scroll-driven background colour shift, and each project card
ProjectHero, ProjectBody, ProjectNav, LightboxCase-study page: header and live-site link, overview/problem/solution content, prev/next links, and the image lightbox
ContactFormContact page form (see Forms)
ArrowLinkText link with the animated arrow, used across pages

Props

Props are the inputs a component accepts, similar to HTML attributes. Johnson is plain JavaScript, so props are simply destructured from Astro.props at the top of each component, with default values where a prop is optional. Here is ArrowLink, used for most text links in the theme:

astrosrc/components/ArrowLink.astro
---
const { href, label } = Astro.props;
---

<a href={href} class="link w-inline-block" data-arrow-link>
  <span class="button">{label}</span>
  <span class="link-arrow-wrapper">
    <img src="/images/Link-arrow.svg" alt="" class="link-arrow" width="7" height="8" />
  </span>
</a>

In plain language: href is where the link goes and label is its visible text; both should always be passed. Other components with optional props include WorkList (projects, heading, headingTag, moreLink) and AboutHero (intro, introAccent, lead, words). Because there’s no type checking, a misspelled prop name is silently ignored — check the component’s frontmatter if something doesn’t render as expected.

Component Composition

Larger sections are usually composed from smaller components rather than written as one long block of markup:

astrosrc/pages/work.astro
<BaseLayout title="Work" description="Selected case studies — branding, web and mobile app design projects.">
  <AboutHero intro="Case studies & projects" lead="Selected" words={['Branding', 'Websites', 'Mobile Apps']} />
  <WorkList projects={projects} heading="My work.." moreLink={{ href: '/contact/', label: 'Start a project' }} />
  <ProcessSteps />
</BaseLayout>

Passing Data to Components

In Astro, props are passed the same way as HTML attributes and read via Astro.props:

astro
---
import ArrowLink from '../components/ArrowLink.astro';
---
<ArrowLink href="/" label="Back home" />
Where the interactivity lives

Johnson uses no UI framework or client: directives. Interactive behaviour — the menu, hovers, marquees, scroll effects, lightbox — is plain JavaScript in each component’s <script> tag, which Astro bundles automatically. Edit an animation in the component that owns it.

07 · Guide

Styling

Where to change colors, type, and spacing without fighting the build.

Global Styles & CSS Variables

Johnson’s colour palette is defined once as CSS custom properties at the top of src/styles/global.css and referenced everywhere else. Change a value here and it updates across the whole site. The four stylesheets are imported by BaseLayout.astro in this order: normalize.css → base-framework.css → global.css → overrides.css. Put your own additions in overrides.css so global.css stays easy to compare with the original design.

csssrc/styles/global.css
:root {
  --orange-light: #ffe8e7; /* page background */
  --heading: #181b2e;      /* headings & default text */
  --body: #3a3d53;         /* body copy */
  --white: white;
  --orange: #fe5621;       /* accent, focus outlines */
}

Component Styles

Astro components support scoped <style> blocks — CSS written there only applies to that component, so class names never collide across files (404.astro uses one). Several of Johnson’s components use <style is:global> instead, because they style classes that come from global.css. Each case study’s accent colour (set in its JSON file) is applied inline as the case-study hero’s background, and WorkList animates between the accents as you scroll.

astro
<style>
  .card { color: var(--heading); border-radius: 0.5rem; }
</style>

Responsive Design, Typography & Spacing

Breakpoints and the type scale live in global.css. It is written desktop-first, with max-width media queries at 991px (tablet), 767px (landscape phone), and 479px (phone). Type sizes are set on h1–h6 and reusable classes such as .display, .h2, .h4, .paragraph, and .paragraph-big. Prefer adjusting these shared rules over overriding sizes on individual elements, so the site keeps a consistent rhythm as you edit it.

Avoid editing dist/

The dist/ folder is generated output — any change made there is overwritten on the next build. Always edit files under src/.

08 · Guide

Images & Assets

Two homes for static files, and when to use each.

LocationUse forBehavior
src/assets/Images referenced inside components or pagesOptimized, resized, and content-hashed automatically by the build
public/Files that need a fixed, predictable URL (favicons, the logo and SVG icons in public/images/, the font file)Copied as-is, no processing

Replacing Images

Swap the file in place (keeping the same filename) or update the import/path to point at your new file. Page artwork (hero, portrait, process steps) lives in src/assets/images/ and is imported in the component that uses it:

astro
---
import { Image } from 'astro:assets';
import heroImage from '../assets/images/Hero-Image.webp';
---
<Image src={heroImage} alt="" class="contact-image" width={360} loading="eager" />

Case-study images live in src/assets/work/ and are referenced from each project’s JSON file by a path relative to that JSON file, e.g. "thumbnail": "../../assets/work/thumb-2.webp". The schema’s image() helper turns these into optimized images automatically.

Supported Formats & SVGs

JPEG, PNG, WebP, AVIF, and GIF are supported through the optimized Image component. Johnson’s SVGs are either referenced as plain <img> sources from public/images/ (logo, arrows, looped text) or inlined as markup (the social icons in SocialIcon.astro) so they inherit colour via currentColor.

Image Optimization

Images imported from src/assets/ are automatically resized and re-encoded at build time based on the width/height (or densities/widths) you specify — you generally don’t need a separate compression step before adding an image to the project.

Rule of thumb

If an image is part of the design (hero photos, thumbnails, icons), put it in src/assets/. If a URL needs to work regardless of the build (a favicon, a file linked from an email), put it in public/. Small UI SVGs are fine in public/images/, as Johnson does — SVGs gain nothing from raster optimization.

09 · Guide

Fonts & Icons

Swapping typefaces and icon sets without touching every component.

Google Fonts

Johnson uses two typefaces: General Sans (self-hosted, used for body text and most headings) and Outfit (weight 500, from Google Fonts, used for some display and label styles). Outfit’s <link> tag lives in BaseLayout.astro’s <head>. To change it, replace the embed code, then update the font-family: Outfit, sans-serif declarations in global.css (there are no --font-* variables):

htmlsrc/layouts/BaseLayout.astro
<link rel="preconnect" href="https://fonts.googleapis.com">
<link rel="preconnect" href="https://fonts.gstatic.com" crossorigin>
<link href="https://fonts.googleapis.com/css2?family=Outfit:wght@500&display=swap" rel="stylesheet">

Local Fonts

General Sans is self-hosted as a single variable font file, public/fonts/GeneralSans-Variable.ttf, declared with @font-face at the top of global.css and preloaded in BaseLayout.astro. To swap it, replace the file, update both the @font-face rule and the <link rel="preload"> path, and update the font-family on body in global.css:

css
@font-face {
  font-family: Generalsans Variable;
  src: url('/fonts/GeneralSans-Variable.ttf') format("truetype");
  font-weight: 200 700;
  font-style: normal;
  font-display: swap;
}

Icon Libraries

Johnson doesn’t use an icon library. Its icons are the original design’s own SVGs: the social icons (Dribbble, Facebook, X, Skype) are inline SVG strings in src/components/SocialIcon.astro, and the logo, arrows, hero icon, and looped-text badge are SVG files in public/images/. (base-framework.css also embeds a tiny johnson-icons glyph font carried over from the base CSS framework; you won’t normally need to touch it.)

Replacing & Adding Icons

To add a social network, paste its SVG markup as a new entry in the icons object in SocialIcon.astro (use fill="currentColor" so it picks up the link colour), then add a matching item to socialLinks in src/data/site.js with icon set to that key. To replace a file-based icon, overwrite the SVG in public/images/ with the same filename.

10 · Beginner Friendly

Content Editing

The fastest, lowest-risk way to make the site say what you want it to say.

New to code?

Everything in this section is plain text or attribute changes — no logic to break. Save the file, and your dev server (from Getting Started) will refresh the browser automatically so you can see the change right away.

Headings, Paragraphs & Buttons

Page copy lives in the section components in src/components/ (for example Hero.astro for the home-page headline) or directly in the page in src/pages/. Locate the text between the tags and edit it directly — here, the 404 page:

astro
<!-- before -->
<h1 class="h3">Page Not Found</h1>
<p class="paragraph">The page you are looking for doesn’t exist or has been moved.</p>
<ArrowLink href="/" label="Back home" />

<!-- after -->
<h1 class="h3">Nothing here</h1>
<p class="paragraph">That page has moved — try my latest work instead.</p>
<ArrowLink href="/work" label="See my work" />

Navigation & Footer

Menu links are the navLinks array in src/data/site.js, and social links are socialLinks in the same file, so you edit each label and URL once. The footer’s copyright line and its About/Contact links are written directly in src/components/FooterMeta.astro — replace the placeholder studio name there. See Navigation for the full pattern.

Experience, Skills & Process Steps

The About page’s repeating blocks are driven by arrays in src/data/about.js rather than hand-written per row — experience, certifications, skills (two marquee rows), and steps (the process cards, also shown on the Work page) — so adding or removing an item is a matter of editing the list:

javascriptsrc/data/about.js
export const experience = [
  { period: 'Jan 2019 — Present', role: 'Product Designer', company: 'Example Studio', href: 'https://example.com' },
  { period: 'Jan 2017 — Dec 2018', role: 'Creative Designer', company: 'Example Agency', href: 'https://example.com' },
  // …
];

Case Studies & Contact Information

Johnson has no blog. Its main content is the case studies: one JSON file per project in src/content/work/. To add a project, copy an existing file, rename it (the file name becomes the URL slug), change the fields, and point the image paths at your own files in src/assets/work/. order sets its position in every list (the home page shows the first five); accent is the case-study hero’s background colour (also used by the work list’s colour shift). dividerImages must contain exactly two images.

jsonsrc/content/work/beyond-energy.json
{

11 · Guide

Navigation

Header, mobile menu, and footer links, in one predictable place.

Header Navigation

Primary nav links are defined as a small array in src/data/site.js, so adding, removing, or reordering a link doesn’t require touching markup. Navbar.astro renders it twice: as the inline desktop links, and inside the overlay menu. Items with mobileOnly: true appear only in the overlay menu (on desktop the logo already links home). The current page gets aria-current="page" automatically.

javascriptsrc/data/site.js
export const navLinks = [
  { label: 'Home', href: '/', mobileOnly: true },
  { label: 'Work', href: '/work' },
  { label: 'About', href: '/about' },
  { label: 'Contact', href: '/contact' },
];

Mobile Menu & Dropdown Menus

The menu toggle requires client-side JavaScript. In Johnson it’s a vanilla <script> using GSAP inside src/components/Navbar.astro — there’s no React island and no dropdown menus. Below 992px the round menu button opens a full-screen overlay menu; on desktop the inline links shrink away as soon as the page scrolls and the same menu button pops in. The menu closes with the close button, a click on the backdrop, or Esc, and focus moves to and from the menu for keyboard users.

Footer Navigation

The footer’s social icons come from the socialLinks array in src/data/site.js (edit each href to point at your own profiles). Its small About/Contact links and the copyright line are written directly in src/components/FooterMeta.astro, which is shared by the footer and the contact page.

Internal vs. External Links

Internal links should be root-relative (/about, not the full domain) so they keep working across environments. External links should open safely in a new tab — Johnson’s social, experience, and live-project links already use target="_blank" rel="noopener":

html
<a href="/about">About</a>
<a href="https://partner-site.com" target="_blank" rel="noopener noreferrer">Partner</a>

Forms

What ships out of the box, and what still needs a backend.

Forms need somewhere to go

A contact or newsletter form in this template captures input in the browser, but submitting it to an email inbox, database, or mailing list requires a backend endpoint or a third-party service — this is not included by default. Johnson’s contact form is not wired to any service: it ships with action="#" and a small demo script that just shows the “Thank you!” message.

Contact Forms

The form lives in src/components/ContactForm.astro (rendered by /contact) and posts three fields: name, email, and message. To make it work, set the form’s action to your form service’s endpoint, then delete the demo <script> at the bottom of the file:

astrosrc/components/ContactForm.astro
<!-- before -->
<form name="contact" method="post" action="#" class="contact-form" data-contact-form>

<!-- after (example: Formspree) -->
<form name="contact" method="post" action="https://formspree.io/f/your-form-id" class="contact-form" data-contact-form>

Newsletter Forms

Johnson doesn’t include a newsletter form. If you add one, embed the signup form from your email provider (Mailchimp, ConvertKit, etc.) in a new component.

Form Validation

Validation uses standard HTML attributes only, giving users immediate feedback without a round trip to a server: name and email are required, email uses type="email", and maxlength caps each field (256 characters for name and email, 5000 for the message). The message field is optional as shipped — add required to its <textarea> if you want it mandatory. There is no custom JavaScript validation.

Third-Party Form Services

If you’d rather not run your own backend, services like Formspree, Getform, or Basin accept form submissions directly from static HTML and forward them to your email — typically a one-line change to the form’s action attribute. On Netlify, Netlify Forms can capture it instead (follow Netlify’s setup for static forms; the form already has name="contact").

API & Data

Johnson fetches no data from any external API. All content is local and read at build time.

No external data out of the box

Site details come from src/data/site.js and src/data/about.js, and case studies from the local work content collection. There are no API calls, keys, or environment variables to configure. The fetch and error-handling notes below only apply if you add an external data source yourself.

API Configuration

If you add an API, read its URL and keys from environment variables (see Configuration) rather than hard-coding them, so the same code can point at a staging or production API depending on environment:

env.env
PUBLIC_API_URL=https://example.com/api
PUBLIC_API_KEY=your_api_key
Never expose real credentials

The values above are placeholders. Keep real API keys out of version control, and prefer server-only variables (without the PUBLIC_ prefix) for anything sensitive.

Fetch Requests

javascript
const res = await fetch(`${import.meta.env.PUBLIC_API_URL}/products`, {
  headers: { Authorization: `Bearer ${import.meta.env.PUBLIC_API_KEY}` },
});
const data = await res.json();

Data Structures

The one structured data source Johnson has is the work content collection. Its schema, defined with Zod in src/content.config.js, lists every field a project JSON file must provide — the build stops with a clear error if a file is missing one or has the wrong type:

javascriptsrc/content.config.js
const work = defineCollection({
  loader: glob({ pattern: '**/*.json', base: './src/content/work' }),
  schema: ({ image }) =>
    z.object({
      title: z.string(),
      order: z.number(),
      summary: z.string(),
      category: z.string(),
      role: z.string(),
      year: z.string(),
      accent: z.string().default('#d6f0ff'),
      liveUrl: z.string().default('https://example.com'),
      thumbnail: image(),
      mainImage: image(),
      overview: z.string(),
      problem: z.string(),
      solution: z.string(),
      dividerImages: z.array(image()).length(2),
      problemImages: z.array(image()),
      solutionImages: z.array(image()),
    }),
});

Error Handling

javascript
try {
  const res = await fetch(apiUrl);
  if (!res.ok) throw new Error(`Request failed: ${res.status}`);
  const data = await res.json();
} catch (err) {
  // show a fallback UI state instead of a blank page
  console.error(err);
}

SEO

Per-page metadata, social previews, and the machine-readable files search engines expect.

Page Title & Meta Description

Pass a unique title and description into BaseLayout on every page — these drive both the browser tab and the snippet shown in search results. The layout appends the site name, so title="Work" becomes “Work | Johnson”; a page with no title (the home page) gets “Johnson — Creative Designer”. Case-study pages use the project’s title and summary automatically.

astro
<BaseLayout
  title="Work"
  description="Selected case studies — branding, web and mobile app design projects."
>

Canonical URL, Open Graph & Twitter/X Cards

Set inside BaseLayout.astro’s <head>, using the site value from astro.config.mjs to build absolute URLs. The Open Graph image defaults to the About-page portrait (src/assets/images/About-Me-Image.webp), resized to a 1200px JPEG at build time; case-study pages use the project’s mainImage, and any page can pass its own via the image prop:

html
<link rel="canonical" href={canonical} />
<meta property="og:title" content={title} />
<meta property="og:description" content={description} />
<meta property="og:image" content={ogImage} />
<meta property="og:url" content={canonical} />
<meta name="twitter:card" content="summary_large_image" />
<meta name="twitter:image" content={ogImage} />

Sitemap & Robots.txt

Johnson includes Astro’s official sitemap integration (@astrojs/sitemap), which generates sitemap-index.xml automatically at build time from the site value; the layout also links it with <link rel="sitemap">. No robots.txt ships with the template — if you want one, create public/robots.txt pointing to the sitemap on your real domain:

textpublic/robots.txt
User-agent: *
Allow: /
Sitemap: https://example.com/sitemap-index.xml

Structured Data & Semantic HTML

Use landmark elements (<header>, <nav>, <main>, <article>) and a single <h1> per page so both search engines and screen readers can parse the page’s structure. Johnson’s pages already follow this, with one <h1> each. The template does not include JSON-LD structured data; if you want rich results, add it in BaseLayout.astro’s <head> (for a portfolio, Person schema is a natural fit).

Deployment

Platform-by-platform steps. Confirm your rendering mode first — it changes the build output you deploy.

Static vs. SSR — check this first

A static Astro build (the default) produces plain HTML/CSS/JS in dist/ that any static host can serve. An Astro site using server-side rendering (SSR via an adapter) needs a Node-capable host or the platform’s matching adapter. Using the wrong instructions for your rendering mode is the most common deployment mistake. Johnson is fully static (no adapter is installed), so use the static instructions below.

Vercel

  1. Push the project to a GitHub, GitLab, or Bitbucket repository.
  2. In Vercel, choose Add New → Project and import that repository.
  3. Build command: npm run build · Output directory: dist (Astro static) — Vercel’s Astro preset detects this automatically in most cases.
  4. If you’ve added a .env file, add its variables under Project Settings → Environment Variables (Johnson needs none by default).
  5. Click Deploy.

Netlify

tomlnetlify.toml
[build]
  command = "npm run build"
  publish = "dist"

Connect the repository in the Netlify dashboard, confirm these build settings, add any environment variables you’ve introduced under Site configuration → Environment variables, and deploy.

Cloudflare Pages

Connect the repository, set the build command to npm run build and the output directory to dist. For SSR Astro sites, use the official @astrojs/cloudflare adapter instead of the static preset.

GitHub Pages

Set site and base in astro.config.mjs to match your repository URL, then build and publish the dist/ folder to the gh-pages branch (via the official astro build + a deploy action, or manually). GitHub Pages only serves static output — it cannot run an SSR adapter.

Traditional Hosting

For a static build, upload the contents of dist/ to your host’s public web root via FTP/SFTP or your host’s file manager. For an SSR build (only if you later add an adapter) that needs a Node process, the host must support running node continuously (a VPS or a Node-compatible host) — plain shared hosting without Node support cannot run it.

Build & Production

What happens when you run build, and a checklist before you ship.

bash
npm run build     # validate content, optimize images, bundle, and write dist/
npm run preview   # serve dist/ locally, exactly as it will run in production

Build Output

The build writes static HTML (one folder per route, plus one per case study), hashed CSS/JS bundles, optimized images, and sitemap-index.xml to dist/. This folder is disposable and regenerated by every build — Johnson’s .gitignore already keeps it out of Git.

Environment Variables in Production

Johnson uses no environment variables by default. If you add some, remember that variables from your local .env are not deployed automatically — each hosting platform requires you to set them again in its dashboard (see Deployment). A missing production variable is one of the most common causes of a build that works locally but fails, or behaves unexpectedly, once deployed.

Production Checklist

  • Run npm run build locally and confirm it completes with no errors.
  • Run npm run preview and click through the main pages.
  • Confirm the site URL in astro.config.mjs matches your real domain (it ships as https://example.com).
  • Replace the placeholder name, email, and social links in src/data/site.js, the résumé content in src/data/about.js, and the studio name in FooterMeta.astro.
  • Replace the sample case studies and imagery — they are placeholder content only.
  • If you added environment variables, set each one in your hosting platform’s dashboard.
  • Point the contact form’s action at a real endpoint and remove its demo script.
  • Verify favicon, Open Graph image, and meta descriptions are your own, not the template defaults.

Troubleshooting

The most common problems, in the order you’re likely to hit them.

npm install fails

Cause
Node.js version too old, a corrupted local cache, or a stale lockfile from a different package manager.
Solution
Confirm node --version meets the requirement in Requirements, then run rm -rf node_modules package-lock.json && npm install.

Port already in use

Cause
Another process (often a previous dev server that didn’t shut down cleanly) is already listening on the default port.
Solution
Stop the other process, or start this one on a different port: npm run dev -- --port 4322.

Module not found

Cause
A missing dependency (e.g. gsap) or a typo in a relative import path. Johnson defines no path aliases.
Solution
Re-run npm install; check the relative path (../ levels) and that its casing matches the file exactly — Linux build servers are case-sensitive even when your machine isn’t.

Images not loading

Cause
An incorrect relative path (common in project JSON files), or an image placed in src/assets/ but referenced with a public/-style absolute path (or vice versa).
Solution
Review Images & Assets — imported assets need an import statement; image paths in src/content/work/*.json are relative to the JSON file (../../assets/work/…); public/ files need a root-relative URL like /images/Logo.svg.

Styles not loading

Cause
A stylesheet import was removed from the layout, a page doesn’t render inside BaseLayout, or a scoped <style> block is targeting markup that lives in another component.
Solution
Confirm BaseLayout.astro still imports all four stylesheets (normalize, base-framework, global, overrides) and that your page is wrapped in <BaseLayout>; move cross-component rules into overrides.css or use <style is:global>.

Content collection errors

Cause
A project JSON file in src/content/work/ is missing a required field, has a field of the wrong type (e.g. "order": "2" instead of 2), is invalid JSON, or doesn’t list exactly two dividerImages.
Solution
The error names the file and field — compare it against the schema in API & Data and an existing project file, and fix whichever side is wrong.

Build fails (but dev server works)

Cause
The dev server only processes pages as you visit them, while build renders every route and optimizes every image — so a problem on a page you never opened in dev (or a filename casing mismatch) can fail the build.
Solution
Read the full terminal output for the first error (later errors are often side effects of it); fix issues top to bottom and re-run.

Environment variables not working

Cause
Missing the PUBLIC_ prefix for a client-side value, or the dev server wasn’t restarted after editing .env.
Solution
Rename the variable with the PUBLIC_ prefix if it’s used in browser code, then stop and restart npm run dev — env changes aren’t hot-reloaded.

Deployment problems

Cause
Wrong output directory configured on the host, or environment variables set locally but not in the platform’s dashboard.
Solution
Re-check the build command and output folder against Deployment for your platform, and confirm every variable from .env is duplicated there.

FAQ

Quick answers to the questions we hear most.

How do I install the template?

Extract the ZIP, run your package manager’s install command, then start the dev server. The full walkthrough is in Getting Started.

Which Node.js version should I use?

Node 22.12.0 or later — see Requirements. Astro 7 won’t install on older versions.

Can I use JavaScript instead of TypeScript?

Johnson already is plain JavaScript — there are no .ts or .tsx files. tsconfig.json is only there for editor hints. You can add TypeScript later if you want it; Astro supports it without extra setup.

How do I change colors?

Update the CSS custom properties at the top of src/styles/global.css (--orange, --orange-light, --heading, --body), and each case study’s accent in its JSON file — see Styling.

How do I change fonts?

Swap the Google Fonts link or the self-hosted font file, then update the matching font-family declarations in global.css — see Fonts & Icons.

How do I replace images?

Swap the file or update the import path — see Images & Assets.

How do I add a new page?

Add a file to src/pages/; the route is created automatically — see Pages. To add a case study instead, add a JSON file to src/content/work/ — see Content Editing.

How do I deploy the template?

Platform-specific steps for Vercel, Netlify, Cloudflare Pages, GitHub Pages, and traditional hosts are in Deployment.

Can I use the template commercially?

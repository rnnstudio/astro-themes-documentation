01 · Overview

Introduction

Everything you need to know before you open your editor — what’s in the box, what it’s built with, and what it expects from your machine.

Welcome

Thanks for picking up Orchid. This guide walks through installing the template, understanding how the project is organized, customizing content and styling, and shipping it to production. It’s written for developers who are comfortable with the command line but new to this specific codebase — if you already know Astro well, feel free to skip ahead using the sidebar.

Orchid is a fitness and wellness marketing template built with Astro. It includes a one-page home page (hero, feature overview, category accordion, testimonials, pricing, trusted-by logos, FAQ, and app download links) plus standalone login and signup pages. It’s styled with hand-written CSS and needs no UI framework or CSS framework.

What’s Included

Source files

The full, uncompiled project source — 3 pages, 13 components, 1 layout, the GSAP animation helpers, stylesheets, and configuration.

Build it yourself

No pre-built dist/ folder ships. Run npm run build to generate one (see Build & Preview).

Design assets

All imagery is self-hosted in public/images/ as SVG, WebP, and PNG, and the General Sans font is in public/fonts/. No Figma or other design source files are included.

This documentation

Hosted online. The download includes a documentation.txt file with the link, and the project README.md has a quick-start summary.

Features

  • A one-page home page with 10 sections and smooth-scrolling nav links to each one
  • Standalone login and signup pages with styled, validated forms
  • GSAP + ScrollTrigger scroll-reveal animations and two infinite marquee loops (testimonials and trusted-by logos)
  • Sticky header with a slide-over mobile menu, accordions, and a YouTube video lightbox, all in small inline scripts with no UI framework
  • SEO-ready layout with per-page title and description, canonical URL, Open Graph and Twitter/X card tags, plus an automatic sitemap
  • Fully responsive, with breakpoints at 991px, 767px, and 479px

Technology Stack

Orchid is plain Astro with vanilla JavaScript and hand-written CSS. It doesn’t use React, TypeScript, Tailwind, or Sass.

Astro 7 Vite Plain CSS GSAP + ScrollTrigger @astrojs/sitemap

02 · Setup

Getting Started

From a downloaded ZIP to a running dev server in five steps.

Installation & Extraction

  1. Download the template ZIP from your purchase confirmation email or account downloads page.
  2. Extract it to a folder on your machine — avoid folder names with spaces or special characters.
  3. Open that folder in your terminal and in your code editor.
bash
# Extract on macOS / Linux
unzip orchid-astro-package.zip -d orchid-astro-package
cd orchid-astro-package/orchid-astro

Node.js Setup

Check which version of Node.js is currently active:

bash
node --version
# v22.12.0 or later

If you manage multiple Node versions, tools like nvm or fnm make switching painless:

bash
nvm install 22
nvm use 22

Install Dependencies

From the project root, install packages with your preferred package manager:

npm
npm install
pnpm
pnpm install
yarn
yarn install

This reads package.json and downloads every dependency into a local node_modules/ folder. It only needs to be re-run when dependencies change.

Run the Development Server

npm
npm run dev
pnpm
pnpm dev

This starts Vite’s local dev server with hot module reloading — edits to components, pages, and styles appear in the browser immediately without a manual refresh. By default it’s available at http://localhost:4321; the terminal output will confirm the exact address.

Build for Production & Preview

bash
# Compile an optimized production build into dist/
npm run build

# Serve that build locally to sanity-check it
npm run preview

build renders every page to static HTML, bundles and minifies the CSS and JavaScript, generates the sitemap, and writes the output to dist/. preview serves that exact output locally so you can verify it before deploying — it does not rebuild automatically, so re-run build after further changes.

Which command do I actually need?

Use dev while you’re customizing the template. Use build, then preview, once before you deploy — it renders every page at once, so it catches issues (like a missing import on a page you never opened in the browser) that a dev session can miss.

Project Structure

A tour of the folders you’ll actually touch, and the ones you generally shouldn’t.

PathPurpose

There is no src/data/ or src/assets/ folder. Repeating content (nav links, pricing plans, reviews, FAQs) is defined as small arrays in the frontmatter of the component that renders it. See Content Editing. Also at the root: .gitignore and .vscode/ (the recommended Astro editor extension).

04 · Reference

Configuration

The files that control how the project builds, and where to set site-wide values.

package.json

Defines dependencies and the scripts you run from the terminal (dev, build, preview). Add your own script here if you introduce a new tool.

jsonpackage.json
{
  "name": "orchid-astro",
  "type": "module",
  "version": "0.0.1",
  "engines": { "node": ">=22.12.0" },
  "scripts": {
    "dev": "astro dev",
    "build": "astro build",
    "preview": "astro preview",
    "astro": "astro"
  },
  "dependencies": {
    "@astrojs/sitemap": "^3.7.4",
    "astro": "^7.3.3",
    "gsap": "^3.15.0",
    "lottie-web": "^5.13.0"
  }
}

gsap powers the scroll animations and marquees. lottie-web is listed as a dependency but isn’t imported anywhere in the current source, so you can remove it with npm uninstall lottie-web if you don’t plan to add a Lottie animation.

astro.config.mjs

Controls integrations, the deployed site URL, and build behavior. Orchid registers a single integration, @astrojs/sitemap, and builds as a fully static site (Astro’s default output).

javascriptastro.config.mjs
// @ts-check
import { defineConfig } from 'astro/config';

import sitemap from '@astrojs/sitemap';

// https://astro.build/config
export default defineConfig({
  site: 'https://example.com',
  integrations: [sitemap()]
});
Replace the placeholder site URL

site is set to https://example.com. Change it to your real domain before deploying. The layout uses it to build the canonical URL and the absolute Open Graph and Twitter image URLs, and the sitemap integration uses it for every URL in sitemap-index.xml.

tsconfig.json

Orchid is written in plain JavaScript and has no .ts files. tsconfig.json only extends Astro’s base preset so the Astro editor extension can offer autocomplete. It defines no path aliases, so all imports use relative paths like ../components/Nav.astro.

jsontsconfig.json
{
  "extends": "astro/tsconfigs/base",
  "include": [".astro/types.d.ts", "**/*"],
  "exclude": ["dist"]
}

Environment Variables (.env)

Orchid doesn’t read any environment variables and ships no .env file. If you add an integration that needs one, create a .env file in the project root for values that differ between environments (API URLs, keys) or shouldn’t be committed to Git. Variables must be prefixed PUBLIC_ to be readable in client-side code.

env.env
# Exposed to the browser — never put secrets here
PUBLIC_SITE_URL=https://example.com

# Server-only — safe for secrets, not readable in browser code
API_SECRET_KEY=your_secret_key
Never commit .env

Orchid’s .gitignore already excludes .env and .env.production. Anything without the PUBLIC_ prefix should stay off the client entirely.

05 · Guide

Pages

How routes are created, and how Orchid’s three pages are put together.

Creating a New Page

Astro uses file-based routing: any .astro or .md file placed in src/pages/ automatically becomes a route matching its file path. Orchid ships three routes:

text
src/pages/index.astro   →  /        (home page with every marketing section)
src/pages/login.astro   →  /login   (login form)
src/pages/signup.astro  →  /signup  (signup form)

To add a page, create a new file in src/pages/ using the layout and structure of an existing, similar page as a starting point. Pages render their own Nav and Footer, so include them explicitly:

astrosrc/pages/about.astro
---
import Layout from '../layouts/Layout.astro';
import Nav from '../components/Nav.astro';
import Footer from '../components/Footer.astro';
---
<Layout title="About — Orchid" description="About our fitness platform.">
  <Nav />
  <h1>About Orchid</h1>
  <Footer />
</Layout>

Editing an Existing Page

Open the relevant file under src/pages/. index.astro is just a list of section components (Hero, Overview, Pricing, and so on), so to change the home page’s content, edit the matching file in src/components/. To reorder or remove a section, move or delete its tag in index.astro. The login and signup pages keep their form markup inline in the page file.

Dynamic Routes

Orchid has no dynamic routes. If you add one, note that files wrapped in square brackets, such as [slug].astro, generate multiple pages from a single template — commonly used for blog posts or product pages. Astro requires a getStaticPaths() function for these on statically-generated sites:

astrosrc/pages/blog/[slug].astro
---
export async function getStaticPaths() {
  const posts = await import.meta.glob('./posts/*.md');
  return Object.keys(posts).map((path) => ({
    params: { slug: path.split('/').pop().replace('.md', '') },
  }));
}
---

Layouts

Orchid has one layout, src/layouts/Layout.astro. It renders the <html> shell and every <head> tag (title, description, canonical, Open Graph and Twitter/X meta, Google Fonts, favicons), imports global.css, and injects the page into <body> via a <slot />. It doesn’t add a header or footer, so each page includes Nav and Footer itself. It accepts five optional props:

astrosrc/layouts/Layout.astro
---
import '../styles/global.css';

const {
  title = 'Orchid — Fitness & Wellness Astro Template',
  description = "The Hassle-free world of fitness. …",
  ogImage = '/images/Hero-Image-with-shadow_1.webp',
  bodyClass = '',      // extra class on <body> (login uses "with-body-color")
  noindex = false,     // true adds <meta name="robots" content="noindex">
} = Astro.props;
---
<html lang="en">
  <head><title>{title}</title> <!-- …plus SEO meta, fonts, favicons --></head>
  <body class={bodyClass}>
    <slot /> <!-- page content is injected here -->
  </body>
</html>

Page Metadata & the 404 Page

Pass a title and description into Layout on every page for correct browser tabs and search results (see also SEO). Orchid doesn’t ship a custom 404 page. Add a file named 404.astro in src/pages/ and it will be served automatically whenever no route matches.

Components

The building blocks pages are assembled from, and how data flows into them.

Reusable Components

Components live in src/components/ and encapsulate one piece of UI so it can be reused across pages without copy-pasting markup. All of Orchid’s components are .astro files. Most are self-contained page sections with no props:

ComponentWhat it renders
AnnouncementBarTop promo strip (“Signup now and get 50% flat discount…”), used on every page
NavLogo, section links, Login/Signup buttons, and the mobile slide-over menu
HeroHeadline, rating badges, hero image, and the YouTube video lightbox
OverviewFeature overview rows with slide-in images
CtaBand“Discover how Orchid can help you to grow” call-to-action band
CategoryFour category cards plus a tabbed accordion
ReviewsTestimonial cards in an infinite marquee
PricingStarter and Premium membership plans
TrustedByPartner logo row (marquee on desktop only)
FaqTwo columns of accordion questions
AppLinksApp Store / Google Play download section
FooterLogo, copyright, quick links, and social icons
UtilityHeroSimple gradient page-title banner (title, description props). Not used by any page yet, but available for new inner pages

Props

Props are the inputs a component accepts, similar to HTML attributes. Orchid is plain JavaScript, so props are read by destructuring Astro.props with default values rather than through TypeScript interfaces. Nav is the main example:

astrosrc/components/Nav.astro
---
const { current = '' } = Astro.props;

const isHome = current === 'home';
const anchor = (hash) => (isHome ? `#${hash}` : `/#${hash}`);
---

In plain language: current is optional and tells the nav which page it’s on. With "home", the section links point at in-page anchors (#Overview), and anywhere else they point back to the home page (/#Overview). With "login" or "signup", the matching button gets aria-current="page". UtilityHero accepts title and description, and Layout’s props are listed under Layouts.

Component Composition

Larger pages are composed from smaller components rather than written as one long block of markup. This is the whole body of the home page:

astrosrc/pages/index.astro
<Layout title="Orchid — Fitness & Wellness Astro Template" description="…">
  <AnnouncementBar />
  <Nav current="home" />
  <Hero />
  <Overview />
  <CtaBand />
  <Category />
  <Reviews />
  <Pricing />
  <TrustedBy />
  <Faq />
  <AppLinks />
  <Footer />
</Layout>

Passing Data to Components

In Astro, props are passed the same way as HTML attributes and read via Astro.props:

astro
---
import UtilityHero from '../components/UtilityHero.astro';
---
<UtilityHero title="About Orchid" description="The all-in-one fitness platform." />
Interactivity without a UI framework

Orchid doesn’t use React or any client-side framework. Interactive pieces (the mobile menu in Nav, the accordions in Category and Faq, the video lightbox in Hero, and the marquees and scroll reveals) are each a small <script> tag at the bottom of their component. Astro bundles and optimizes these automatically.

Styling

Where to change colors, type, and spacing without fighting the build.

Global Styles & CSS Variables

Orchid uses plain CSS with no preprocessor or utility framework. Layout.astro imports src/styles/global.css, which pulls in the other stylesheets in order:

FileContains
normalize.cssCross-browser reset
base-framework.cssBase layout and utility classes the design relies on (containers, grid, buttons, form fields)
orchid.cssThe template’s design system: color and font tokens, typography, and every section’s styles
global.cssSmall additions for the reimplemented behaviors: sticky nav, mobile menu, accordions, marquees, custom checkbox, video lightbox

Brand colors and font families are CSS custom properties at the top of src/styles/orchid.css. Change a value here and it updates across the whole site:

csssrc/styles/orchid.css
:root {
  --font--body: var(--font-family--general-sans);
  --font-color--body: var(--color--slate-blue);
  --font--heading: var(--font-family--figtree);
  --font-color--heading: var(--color--midnight-blue);
  --font-color--text-highlight: var(--color--green);
  --color--white: white;
  --color--green: #00b172;
  --color--light-pink: #faeaf0;
  --color--yellow: #f2c94c;
  --color--light-green: #e6f7f1;
  --radius--radius-1: 20px;
  --radius--radius-2: 10px;
  --color--pink: #8e2690;
  --color--black: black;
  --color--midnight-blue: #2b2e45;
  --color--slate-blue: #555777;
  --font-family--general-sans: "Generalsans Variable", sans-serif;
  --font-family--figtree: Figtree, sans-serif;
}

Component Styles

Astro components support scoped <style> blocks, where CSS only applies to that component so class names never collide across files. Orchid’s components don’t use them. All styling lives in the shared stylesheets above, keyed off class names like .pricing-section or .footer-link, so search orchid.css for a class to find its rules. You’re free to add a scoped block to any new component:

astro
<style>
  .card { padding: 20px; border-radius: var(--radius--radius-1); }
</style>

Responsive Design, Typography & Spacing

Responsive rules use three max-width breakpoints throughout orchid.css and global.css: 991px (tablet, where the nav switches to the slide-over menu), 767px (large phone), and 479px (small phone). Headings use Figtree and body text uses General Sans, via the --font--heading and --font--body tokens. Prefer adjusting these shared values over overriding sizes on individual elements, so the site keeps a consistent rhythm as you edit it.

Avoid editing dist/

The dist/ folder is generated output — any change made there is overwritten on the next build. Always edit files under src/.

Images & Assets

Two homes for static files, and when to use each.

LocationUse forBehavior
public/Where Orchid keeps all its imagery (public/images/), the General Sans font (public/fonts/), and the faviconsCopied as-is, no processing. Referenced by root-relative URLs like /images/Logo.svg
src/assets/Not present in Orchid. Create it if you want Astro to optimize new imagesOptimized, resized, and content-hashed automatically by the build

Replacing Images

Images are plain <img> tags pointing into public/images/. Either swap the file in place (keeping the same filename), or drop in your new file and update the src:

astrosrc/components/Nav.astro
<img src="/images/Logo.svg" loading="lazy" alt="logo" class="logo" />

Some images are set in data arrays instead of markup: review avatars in Reviews.astro, category icons in Category.astro, and partner logos in TrustedBy.astro. The logo appears in Nav.astro (twice, for desktop and mobile) and Footer.astro. The default social-share image is the ogImage prop in Layout.astro.

Supported Formats & SVGs

Orchid ships WebP photos, a few PNGs, and SVGs for logos, icons, and section backgrounds. Any format a browser can display works from public/. Small UI icons (arrows, social icons) are inline <svg> elements using fill="currentColor", so they inherit the surrounding text color.

Image Optimization

Because everything lives in public/, Astro serves Orchid’s images exactly as they are, with no build-time resizing. The bundled photos are already compressed WebP files. Compress your replacements before adding them (WebP at roughly the same dimensions is a good target). If you’d rather have Astro optimize images, move them into src/assets/ and render them with the Image component from astro:assets:

astro
---
import { Image } from 'astro:assets';
import hero from '../assets/hero.webp';
---
<Image src={hero} alt="Woman doing yoga" width={1200} height={630} />
Image credits

Some bundled photos come from Unsplash, Pexels, and Freepik. Four Freepik images require attribution if you keep them. The links are listed under Credits in the project’s README.md.

09 · Guide

Fonts & Icons

Swapping typefaces and icon sets without touching every component.

Google Fonts

The heading font, Figtree (weights 300–900), loads from Google Fonts via a <link> tag in Layout.astro’s <head>. To change it, replace that tag with your chosen font’s embed code, then update --font-family--figtree (or point --font--heading at a new variable) in orchid.css:

htmlsrc/layouts/Layout.astro
<link rel="preconnect" href="https://fonts.googleapis.com" />
<link rel="preconnect" href="https://fonts.gstatic.com" crossorigin />
<link
  href="https://fonts.googleapis.com/css2?family=Figtree:wght@300;400;500;600;700;800;900&display=swap"
  rel="stylesheet"
/>

Local Fonts

The body font, General Sans, is self-hosted as a single variable font file, public/fonts/GeneralSans-Variable.ttf. It’s declared with @font-face in orchid.css, which supplies --font-family--general-sans. To swap it, replace the file in public/fonts/ and update the @font-face rule. The same rule is declared at both the top and the bottom of orchid.css, so update both or delete one:

csssrc/styles/orchid.css
@font-face {
  font-family: 'Generalsans Variable';
  src: url('/fonts/GeneralSans-Variable.ttf') format('truetype');
  font-weight: 200 700;
  font-style: normal;
  font-display: swap;
}

Icon Libraries

Orchid doesn’t use an icon library package. Icons come in two forms. Small UI icons (link arrows, the five footer social icons) are inline <svg> markup inside their components. Larger illustrative icons (category icons, check marks, rating stars, tags) are SVG files in public/images/. base-framework.css also embeds a tiny base64 icon font (orchid-icons) for its built-in w-icon-* classes.

Replacing & Adding Icons

To change an inline icon, replace the <svg>…</svg> block in the component, and keep fill="currentColor" so it still picks up the theme color. To change a file-based icon, swap the SVG in public/images/ or point the src (or the icon field in Category.astro’s items array) at your new file. If you prefer a library such as Lucide or Heroicons, copy its SVG markup in the same way. No package is required.

10 · Beginner Friendly

Content Editing

The fastest, lowest-risk way to make the site say what you want it to say.

New to code?

Everything in this section is plain text or attribute changes — no logic to break. Save the file, and your dev server (from Getting Started) will refresh the browser automatically so you can see the change right away.

Headings, Paragraphs & Buttons

Home page text lives in the section components in src/components/. Login and signup text lives in src/pages/login.astro and src/pages/signup.astro. Locate the text between the tags and edit it directly:

astrosrc/components/Hero.astro
<!-- before -->
<h1 class="display-and-page-title">The Hassle-free world of fitness</h1>
<p class="body---variant-3">Orchid is the all‑in‑one fitness platform that supports members across all their goals — helps you to grow.</p>

<!-- after -->
<h1 class="display-and-page-title">Train smarter at Riverside Fitness</h1>
<p class="body---variant-3">Classes, coaching, and progress tracking in one membership.</p>

Keep the class attributes as they are, since they carry the typography styles. Button labels are plain text inside the <a> tags. Other one-off text to look for: the promo message in AnnouncementBar.astro, the CTA band in CtaBand.astro, and the app download copy in AppLinks.astro.

Navigation & Footer

Menu links are a small links array at the top of Nav.astro, and footer quick links are a quickLinks array at the top of Footer.astro. Edit a label or URL once there rather than hunting through every page. See Navigation for the full pattern.

Cards, Testimonials & Pricing

Blog Content & Contact Information

Orchid has no blog and no contact page. If you add a blog, Markdown files in src/pages/blog/ or a content collection in src/content/ are the usual approach. Brand and contact-related details are spread across a few files:

  • Social links (Facebook, Messenger, WhatsApp, Twitter/X, Dribbble): the hrefs in Footer.astro. They currently point at each network’s home page.
  • App store links: the two buttons in AppLinks.astro. They currently point at apple.com and play.google.com.
  • Hero video: the YouTube embed URL in the data-src attribute near the bottom of Hero.astro.

11 · Guide

Navigation

Header, mobile menu, and footer links, in one predictable place.

Header Navigation

Primary nav links are defined as a small array at the top of src/components/Nav.astro, so adding, removing, or reordering a link doesn’t require touching markup. Each link points at a section anchor on the home page. The anchor() helper makes it a same-page #hash on the home page and a /#hash link everywhere else:

javascriptsrc/components/Nav.astro
const links = [
  { label: 'Home', href: anchor('Home') },
  { label: 'Overview', href: anchor('Overview') },
  { label: 'Features', href: anchor('Features') },
  { label: 'Membership', href: anchor('Membership') },
  { label: "FAQ's", href: anchor('FAQs') },
];

The anchors are empty <div id="…" class="anchor-div"> elements inside the section components: Home and Overview in Hero.astro, Features in Overview.astro, Membership in Pricing.astro, and FAQs in Faq.astro. If you rename one, update both sides. The Login and Signup buttons are written directly in the nav markup below the array. global.css turns on smooth scrolling for these jumps unless the visitor prefers reduced motion.

Mobile Menu & Dropdown Menus

Below 991px the nav links collapse into a slide-over panel opened by the hamburger button. This is a vanilla inline <script> at the bottom of src/components/Nav.astro, not a framework component. It toggles an is-open class on the nav, locks page scrolling while open, and closes the menu when the overlay or any link is clicked. The slide animation itself is CSS in global.css. Orchid has no dropdown menus.

Footer Navigation

Footer quick links follow the same data-driven pattern in a quickLinks array at the top of src/components/Footer.astro. The “Others” column (Login, Signup, Powered by Astro) and the social icons are written directly in the footer markup.

Internal vs. External Links

Internal links should be root-relative (/about, not the full domain) so they keep working across environments. External links should open safely in a new tab:

html
<a href="/about">About</a>
<a href="https://partner-site.com" target="_blank" rel="noopener noreferrer">Partner</a>

Forms

What ships out of the box, and what still needs a backend.

Forms need somewhere to go

Orchid’s only forms are the login and signup forms, and they are front-end only. They capture and validate input in the browser, but they have no action, no submit handler, and no connected service. Submitting one just reloads the same page, and the browser’s default GET submission appends the field values to the URL. Real sign-in or account creation needs an authentication backend or third-party service, which is not included.

Contact Forms

Orchid has no contact form. The two forms live inline in src/pages/login.astro (username, password, terms checkbox) and src/pages/signup.astro (name, work email, password, confirm password, terms checkbox). Each <form> carries a data-static-form marker attribute but nothing else. To send submissions somewhere, add an action and method pointing at your endpoint:

astrosrc/pages/signup.astro
<!-- before -->
<form class="utility-form" data-static-form>

<!-- after -->
<form class="utility-form" action="https://your-backend.example.com/signup" method="POST">
Don’t send passwords to a generic form service

These are account forms with password fields. Wire them to a proper authentication provider or your own backend over HTTPS, not to an email-forwarding form service.

Newsletter Forms

Orchid has no newsletter form and isn’t pre-wired to any email provider. If you add one (for example in the footer), point its action at your provider’s embed endpoint (Mailchimp, ConvertKit, etc.).

Form Validation

Validation uses standard HTML attributes only. Every field is required with maxlength="256", the signup email field uses type="email", and the “I accept Terms of use” checkbox is required. The browser checks these before submission and gives users immediate feedback without a round trip to a server. Note that nothing checks that “Password” and “Confirm Password” match, so add that in your submit logic. The checkbox is a styled custom control (native input hidden, CSS in global.css) that stays keyboard-accessible.

Third-Party Form Services

If you add a contact or lead-capture form and would rather not run your own backend, services like Formspree, Getform, or Basin accept form submissions directly from static HTML and forward them to your email — typically a one-line change to the form’s action attribute.

API & Data

Orchid fetches no data from any API — this section only matters if you add one.

No external data out of the box

All content is static and lives in the .astro files themselves. The only third-party requests the built site makes are the Google Fonts stylesheet (Figtree) and the YouTube embed, which loads only when a visitor opens the hero video lightbox. There are no API keys, environment variables, or fetch calls to configure.

API Configuration

If you connect an API, read URLs and keys from environment variables (see Configuration) rather than hard-coded, so the same code can point at a staging or production API depending on environment:

env.env
PUBLIC_API_URL=https://example.com/api
PUBLIC_API_KEY=your_api_key
Never expose real credentials

The values above are placeholders. Keep real API keys out of version control, and prefer server-only variables (without the PUBLIC_ prefix) for anything sensitive.

Fetch Requests

javascript
const res = await fetch(`${import.meta.env.PUBLIC_API_URL}/products`, {
  headers: { Authorization: `Bearer ${import.meta.env.PUBLIC_API_KEY}` },
});
const data = await res.json();

Data Structures

The closest thing Orchid has to a data model is the arrays in its components (see Content Editing). If you move content to an API or CMS, have it return the same shapes so the existing markup keeps working:

javascript
// Reviews.astro — one testimonial card
{ rating: '4.7', ratingClass: '', avatar: '/images/reviewer-image.png', name: 'Alex Carter', role: 'Member since 2023' }

// Pricing.astro — one plan (modifier picks the card style: 'starter' | 'premium')
{ name: 'Starter Plan', modifier: 'starter', blurb: 'Our standard membership…', price: '19' }

// Faq.astro — one question
{ q: 'What are your opening hours?', a: '…' }

Error Handling

javascript
try {
  const res = await fetch(apiUrl);
  if (!res.ok) throw new Error(`Request failed: ${res.status}`);
  const data = await res.json();
} catch (err) {
  // show a fallback UI state instead of a blank page
  console.error(err);
}

SEO

Per-page metadata, social previews, and the machine-readable files search engines expect.

Page Title & Meta Description

Pass a unique title and description into Layout on every page — these drive both the browser tab and the snippet shown in search results. Each of Orchid’s three pages already does this:

astrosrc/pages/login.astro
<Layout
  title="Login — Orchid"
  description="Designed to optimize your wellness journey. …"
  bodyClass="with-body-color"
>

If you don’t want the login and signup pages indexed, add noindex to their <Layout> tag (<Layout noindex …>). It’s off by default on every page.

Canonical URL, Open Graph & Twitter/X Cards

Already set inside Layout.astro’s <head>, using the site value from astro.config.mjs to build absolute URLs. The share image defaults to /images/Hero-Image-with-shadow_1.webp. Override it per page with the ogImage prop:

astrosrc/layouts/Layout.astro
<meta property="og:title" content={title} />
<meta property="og:description" content={description} />
<meta property="og:image" content={new URL(ogImage, Astro.site)} />
<meta property="og:type" content="website" />
<meta property="og:url" content={canonicalURL} />
<meta name="twitter:card" content="summary_large_image" />
<meta name="twitter:title" content={title} />
<meta name="twitter:description" content={description} />
<meta name="twitter:image" content={new URL(ogImage, Astro.site)} />
<link rel="canonical" href={canonicalURL} />

Sitemap & Robots.txt

Orchid includes Astro’s official sitemap integration (@astrojs/sitemap), which generates sitemap-index.xml automatically at build time from the site value. Set that to your real domain first. Orchid doesn’t ship a robots.txt. To add one, create public/robots.txt to control crawler access and point it at the sitemap:

textpublic/robots.txt
User-agent: *
Allow: /
Sitemap: https://example.com/sitemap-index.xml

Structured Data & Semantic HTML

Use landmark elements (<header>, <nav>, <main>, <article>) and a single <h1> per page so both search engines and screen readers can parse the page’s structure. Each Orchid page has exactly one <h1>. No JSON-LD ships with the template. Add JSON-LD structured data in the layout’s <head> for rich results (e.g. Organization or Article schema) where relevant to your content.

Deployment

Platform-by-platform steps. Confirm your rendering mode first — it changes the build output you deploy.

Static vs. SSR — check this first

Orchid is a static Astro build. It uses no adapter, so npm run build produces plain HTML/CSS/JS in dist/ that any static host can serve. You only need a Node-capable host or a platform adapter if you later switch Astro to server-side rendering (SSR). Using the wrong instructions for your rendering mode is the most common deployment mistake.

Vercel

  1. Push the project to a GitHub, GitLab, or Bitbucket repository.
  2. In Vercel, choose Add New → Project and import that repository.
  3. Build command: npm run build · Output directory: dist (Astro static) — Vercel’s Astro preset detects this automatically in most cases.
  4. Orchid needs no environment variables. If you’ve added a .env file, copy its values under Project Settings → Environment Variables.
  5. Click Deploy.

Netlify

tomlnetlify.toml
[build]
  command = "npm run build"
  publish = "dist"

Connect the repository in the Netlify dashboard, confirm these build settings, add environment variables under Site configuration → Environment variables, and deploy.

Cloudflare Pages

Connect the repository, set the build command to npm run build and the output directory to dist. For SSR Astro sites, use the official @astrojs/cloudflare adapter instead of the static preset.

GitHub Pages

Set site and base in astro.config.mjs to match your repository URL, then build and publish the dist/ folder to the gh-pages branch (via the official astro build + a deploy action, or manually). GitHub Pages only serves static output — it cannot run an SSR adapter.

Traditional Hosting

Because Orchid builds to static files, upload the contents of dist/ to your host’s public web root via FTP/SFTP or your host’s file manager. Any shared host works, and no Node.js is needed on the server. Only if you later convert the site to SSR would the host need to run node continuously (a VPS or a Node-compatible host).

Build & Production

What happens when you run build, and a checklist before you ship.

bash
npm run build     # render pages, bundle assets, generate the sitemap, and write dist/
npm run preview   # serve dist/ locally, exactly as it will run in production

Build Output

The build writes one HTML file per route (index.html, login/index.html, signup/index.html), hashed CSS/JS bundles (including GSAP), sitemap-index.xml, and a copy of everything in public/ to dist/. This folder is disposable and regenerated by every build. Orchid’s .gitignore already keeps it out of Git.

Environment Variables in Production

Orchid uses no environment variables, so there’s nothing to set out of the box. If you add some, remember that variables from your local .env are not deployed automatically — each hosting platform requires you to set them again in its dashboard (see Deployment). A missing production variable is one of the most common causes of a build that works locally but fails, or behaves unexpectedly, once deployed.

Production Checklist

  • Run npm run build locally and confirm it completes with no errors.
  • Run npm run preview and click through the main pages.
  • Replace site: 'https://example.com' in astro.config.mjs with your real domain.
  • Set every environment variable from .env (if you added any) in your hosting platform’s dashboard.
  • Wire the login and signup forms to a real backend, or remove them. Out of the box they don’t submit anywhere.
  • Replace the placeholder FAQ answers, social links, app store links, and the hero YouTube video.
  • Verify the favicons (favicon.svg, images/favicon.png, images/webclip.png), the Open Graph image, and the meta descriptions are your own, not the template defaults.
  • Keep or remove the Freepik images that require attribution (see README.md → Credits).

Troubleshooting

The most common problems, in the order you’re likely to hit them.

npm install fails

Cause
Node.js older than 22.12.0 (required by Astro 7), a corrupted local cache, or a stale lockfile from a different package manager.
Solution
Confirm node --version meets the requirement in Requirements, then run rm -rf node_modules package-lock.json && npm install.

Port already in use

Cause
Another process (often a previous dev server that didn’t shut down cleanly) is already listening on the default port.
Solution
Stop the other process, or start this one on a different port: npm run dev -- --port 4322.

Module not found

Cause
A missing dependency (for example gsap, which the component scripts import), or a typo in a relative import path.
Solution
Re-run npm install; check that the import path casing matches the file exactly (Orchid has no path aliases, so every import is relative, e.g. ../scripts/scroll-reveal.js).

Images not loading

Cause
A wrong path or filename casing (case matters on most Linux hosts, e.g. Logo.svg vs logo.svg), or an image moved into src/ while still referenced by a /images/… URL.
Solution
Review Images & Assets. Orchid’s images live in public/images/ and need a root-relative URL like /images/Logo.svg. Files you move to src/assets/ need an import statement instead.

Styles not loading

Cause
The global.css import was removed from the layout, one of its @import lines was deleted, or a new page doesn’t use Layout.
Solution
Confirm import '../styles/global.css'; is at the top of src/layouts/Layout.astro, that global.css still imports normalize.css, base-framework.css, and orchid.css, and that your page is wrapped in <Layout>.

Animations, menu, or accordions not working

Cause
A required class or data-* attribute was removed while editing markup. The component scripts find their elements by attributes like data-nav-toggle, data-accordion-item, and data-marquee, and by classes like fade-in-200. A JavaScript error elsewhere on the page can also stop them.
Solution
Compare your edited markup against the original component and restore the missing attribute or class. Check the browser console for errors.

Build fails (but dev server works)

Cause
The dev server only renders the pages you open, while build renders every page at once, so an error in a page you didn’t visit only shows up at build time.
Solution
Read the full terminal output for the first error (later errors are often side effects of it); fix issues top to bottom and re-run.

Environment variables not working

Cause
Only applies if you’ve added a .env file, since Orchid uses none. Usually the PUBLIC_ prefix is missing for a client-side value, or the dev server wasn’t restarted after editing .env.
Solution
Rename the variable with the PUBLIC_ prefix if it’s used in browser code, then stop and restart npm run dev — env changes aren’t hot-reloaded.

Deployment problems

Cause
Wrong output directory configured on the host, the placeholder site URL still in astro.config.mjs (giving canonical, social, and sitemap URLs on example.com), or environment variables you added set locally but not in the platform’s dashboard.
Solution
Re-check the build command (npm run build) and output folder (dist) against Deployment for your platform, set site to your real domain, and confirm any .env variables are duplicated on the host.

FAQ

Quick answers to the questions we hear most.

How do I install the template?

Extract the ZIP, run your package manager’s install command, then start the dev server. The full walkthrough is in Getting Started.

Which Node.js version should I use?

Node 22.12.0 or later, as required by Astro 7 and the engines field in package.json — see Requirements. The current Node 22 LTS release is a safe default.

Can I use JavaScript instead of TypeScript?

Orchid is already plain JavaScript. There are no .ts files, and the component scripts and scroll-reveal.js are vanilla JS. If you’d like TypeScript, Astro supports it out of the box: add .ts files or lang="ts" scripts as you go.

How do I change colors?

Update the CSS custom properties in the :root block at the top of src/styles/orchid.css (e.g. --color--green, --color--midnight-blue) — see Styling.

How do I change fonts?

For headings, swap the Google Fonts <link> in Layout.astro and update --font-family--figtree. For body text, replace the General Sans file in public/fonts/ and its @font-face rule in orchid.css — see Fonts & Icons.

How do I replace images?

Swap the file in public/images/ or update the src path — see Images & Assets.

How do I add a new page?

Add a file to src/pages/; the route is created automatically — see Pages.

How do I deploy the template?

Orchid builds to a static site, so it runs on almost any host. Platform-specific steps for Vercel, Netlify, Cloudflare Pages, GitHub Pages, and traditional hosts are in Deployment.

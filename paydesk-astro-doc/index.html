01 · Overview

Introduction

Everything you need to know before you open your editor — what’s in the box, what it’s built with, and what it expects from your machine.

Welcome

Thanks for picking up Paydesk, a conversion-focused landing page template for billing, invoicing and payment SaaS products. This guide walks through installing the template, understanding how the project is organized, customizing content and styling, and shipping it to production. It’s written for developers who are comfortable with the command line but new to this specific codebase — if you already know Astro well, feel free to skip ahead using the sidebar.

What’s Included

Source files

The full, uncompiled project source — components, pages, styles, and configuration.

Self-hosted fonts

Onest (Medium, Bold) and Satoshi Medium font files in public/fonts/ — no external font requests. No pre-built dist/ is included; run npm run build to generate one.

Design assets

SVG logos, icons and decorative illustrations in public/images/, plus WebP/PNG product artwork in src/assets/images/. No Figma source file is included.

This documentation

A single offline HTML file — open it directly in any browser, no server required.

Features

  • A complete one-page marketing site with 10 home sections — hero with email capture, benefits, use cases, feature grid, integrations, “Why Paydesk” accordion, pricing, FAQ, reviews and call-to-action — plus Login, Signup, Changelog and License pages
  • Pricing section with an accessible monthly/yearly switch
  • Scroll-reveal animations, sticky navbar, accordions and an infinite logo marquee built with GSAP + ScrollTrigger — all respecting prefers-reduced-motion
  • Accessible markup: semantic landmarks, one <h1> per page, keyboard-operable mobile menu, tabs and accordions, visible focus states
  • SEO-ready: per-page titles and descriptions, canonical URLs, Open Graph / Twitter tags and an automatic sitemap
  • Fast static output with responsive images via astro:assets, self-hosted fonts, and no CSS framework or jQuery

Technology Stack

Paydesk is a plain Astro project — JavaScript and CSS only, with no UI framework, CSS framework, or TypeScript required.

Astro 7 GSAP 3 (ScrollTrigger) @astrojs/sitemap Vite Plain CSS

02 · Setup

Getting Started

From a downloaded ZIP to a running dev server in five steps.

Installation & Extraction

  1. Download paydesk-astro-package.zip from your purchase confirmation email or account downloads page. It contains the paydesk-astro/ project folder and a documentation.txt file.
  2. Extract it to a folder on your machine — avoid folder names with spaces or special characters.
  3. Open that folder in your terminal and in your code editor.
bash
# Extract on macOS / Linux
unzip paydesk-astro-package.zip
cd paydesk-astro-package/paydesk-astro

Node.js Setup

Check which version of Node.js is currently active:

bash
node --version
# v22.12.0 or later

If you manage multiple Node versions, tools like nvm or fnm make switching painless:

bash
nvm install 22
nvm use 22

Install Dependencies

From the project root, install packages with your preferred package manager:

npm
npm install
pnpm
pnpm install
yarn
yarn install

This reads package.json and downloads every dependency into a local node_modules/ folder. It only needs to be re-run when dependencies change.

Run the Development Server

npm
npm run dev
pnpm
pnpm dev

This starts Astro’s Vite-powered dev server with hot module reloading — edits to components, pages, and styles appear in the browser immediately without a manual refresh. By default it’s available at http://localhost:4321; the terminal output will confirm the exact address.

Build for Production & Preview

bash
# Compile an optimized production build into dist/
npm run build

# Serve that build locally to sanity-check it
npm run preview

build renders every page to static HTML, bundles and minifies CSS/JS, optimizes images, generates the sitemap, and writes everything to dist/. preview serves that exact output locally so you can verify it before deploying — it does not rebuild automatically, so re-run build after further changes.

Which command do I actually need?

Use dev while you’re customizing the template. Use build, then preview, once before you deploy — it catches issues (like a missing image file or a broken import path) that only surface when every page is rendered.

04 · Reference

Configuration

The files that control how the project builds, and where to set site-wide values.

package.json

Defines dependencies and the scripts you run from the terminal (dev, build, preview). Add your own script here if you introduce a new tool.

jsonpackage.json
{
  "name": "paydesk-astro",
  "type": "module",
  "version": "0.0.1",
  "engines": {
    "node": ">=22.12.0"
  },
  "scripts": {
    "dev": "astro dev",
    "build": "astro build",
    "preview": "astro preview",
    "astro": "astro"
  },
  "dependencies": {
    "@astrojs/sitemap": "^3.7.4",
    "astro": "^7.3.4",
    "gsap": "^3.15.0"
  }
}

astro.config.mjs

Controls integrations, the deployed site URL, and build behavior. Paydesk registers only the sitemap integration; replace site with your production URL — it’s used for canonical URLs, Open Graph image URLs and the generated sitemap.

javascriptastro.config.mjs
import { defineConfig } from 'astro/config';
import sitemap from '@astrojs/sitemap';

// Replace `site` with your production URL — it is used for canonical URLs,
// Open Graph image URLs and the generated sitemap.
export default defineConfig({
  site: 'https://example.com',
  integrations: [sitemap()],
});

jsconfig.json

Paydesk is written in plain JavaScript, so it ships a jsconfig.json instead of a tsconfig.json. It extends Astro’s base config so your editor gets IntelliSense for .astro files and Astro’s generated types. No path aliases are defined — components are imported with relative paths such as ../components/Footer.astro.

jsonjsconfig.json
{
  "extends": "astro/tsconfigs/base",
  "include": [".astro/types.d.ts", "**/*"],
  "exclude": ["dist"]
}

Environment Variables (.env)

Paydesk reads no environment variables out of the box — the site URL lives in astro.config.mjs. If you add an API or form service, create a .env file in the project root for values that differ between environments (API URLs, keys) or shouldn’t be committed to Git. Variables must be prefixed PUBLIC_ to be readable in client-side code.

env.env
# Exposed to the browser — never put secrets here
PUBLIC_SITE_URL=https://example.com

# Server-only — safe for secrets, not readable in browser code
API_SECRET_KEY=your_secret_key
Never commit .env

Paydesk’s .gitignore already excludes .env and .env.production. Anything without the PUBLIC_ prefix should stay off the client entirely.

05 · Guide

Pages

How routes are created, and how Paydesk’s pages are assembled.

Creating a New Page

Astro uses file-based routing: any .astro, .md, or .html file placed in src/pages/ automatically becomes a route matching its file path. Paydesk ships five routes:

text
src/pages/index.astro      →  /           (one-page home: all marketing sections)
src/pages/login.astro      →  /login
src/pages/signup.astro     →  /signup
src/pages/changelog.astro  →  /changelog
src/pages/license.astro    →  /license

To add a page, create a new file in src/pages/ using the layout and structure of an existing, similar page as a starting point:

astrosrc/pages/services.astro
---
import BaseLayout from '../layouts/BaseLayout.astro';
import Navbar from '../components/Navbar.astro';
import Footer from '../components/Footer.astro';
---
<BaseLayout title="Services | Paydesk" description="What we offer.">
  <Navbar />
  <main>
    <h1>Our Services</h1>
  </main>
  <Footer />
</BaseLayout>

Editing an Existing Page

Open the relevant file under src/pages/ and edit the markup directly. The home page (index.astro) is only a list of section components — its copy lives in files like src/components/Hero.astro and src/components/Pricing.astro. Anything imported from src/components/ lives elsewhere — edit the component file itself to change content that repeats across multiple pages (like a shared call-to-action block).

Dynamic Routes

Files wrapped in square brackets, such as [slug].astro, generate multiple pages from a single template — commonly used for blog posts or product pages. Paydesk doesn’t ship any dynamic routes, but if you add one, Astro requires a getStaticPaths() function for these on statically-generated sites:

astrosrc/pages/blog/[slug].astro
---
export async function getStaticPaths() {
  const posts = await import.meta.glob('./posts/*.md');
  return Object.keys(posts).map((path) => ({
    params: { slug: path.split('/').pop().replace('.md', '') },
  }));
}
---

Layouts

Paydesk has a single layout, src/layouts/BaseLayout.astro. It provides the <html> shell, <head> metadata, favicons, font preloads and the global stylesheet imports. The navbar and footer are not part of the layout — each page places <Navbar /> and <Footer /> itself, because the login/signup pages use a reduced navbar and no footer. Every page renders inside the layout via its <slot />:

astrosrc/layouts/BaseLayout.astro
---
import '../styles/normalize.css';
import '../styles/base-framework.css';
import '../styles/paydesk.css';
import '../styles/site.css';
import defaultOgImage from '../assets/images/Hero-Image.webp';

const {
  title = 'Paydesk — Online Billing and Payment Platform',
  description = 'Online Billing and Payment Platform. ...',
  bodyClass = 'main-body',
  ogImage: ogImageAsset = defaultOgImage,
} = Astro.props;
---
<html lang="en">
  <head>
    <title>{title}</title>
    <meta name="description" content={description} />
    <!-- canonical, Open Graph, Twitter, favicons, font preloads -->
  </head>
  <body class={bodyClass}>
    <slot /> <!-- page content is injected here -->
  </body>
</html>

Page Metadata & the 404 Page

Pass a title and description into your layout’s props on every page for correct browser tabs and search results (see also SEO). A file named 404.astro in src/pages/ is served automatically whenever no route matches — Paydesk doesn’t include one, so add src/pages/404.astro if you want a custom “not found” page.

06 · Guide

Components

The building blocks pages are assembled from, and how data flows into them.

Reusable Components

Components live in src/components/ and encapsulate one piece of UI — a button, a pricing card, a navigation bar — so it can be reused across pages without copy-pasting markup. Every Paydesk component is an .astro file:

GroupComponents
Home sectionsHero, Benefits, UseCases, MoreFeatures, Integrations, WhyPaydesk, Pricing, Faq, Reviews, Cta
Site chromeNavbar, AnnouncementBar, Footer, TemplatePageHeader (intro block on Changelog/License)
Shared UIAccordion, CheckList, AnimatedLink, LogoMarquee, SignupForm, AuthForm (login/signup)
icons/Inline-SVG icon components: FacebookIcon, InstagramIcon, PinterestIcon, TwitterIcon, WhyIcon1–WhyIcon3

Props

Props are the inputs a component accepts, similar to HTML attributes. Paydesk components are plain JavaScript: each one lists its props in a short comment at the top of the file and reads them from Astro.props with sensible defaults.

astrosrc/components/AnnouncementBar.astro
---
const {
  label = 'Announcement',
  href = '/signup',
  text = 'Join Paydesk and receive 75% discount on checkout',
} = Astro.props;
---

In plain language: all three props are optional. <AnnouncementBar /> renders the defaults above, while <AnnouncementBar text="Spring sale: 50% off" href="/#Pricing" /> overrides just the text and link. Other examples: Navbar takes variant ("inline" or "fixed") and showLinks; AuthForm takes mode ("login" or "signup"); AnimatedLink takes href plus its link text as a slot.

Component Composition

Larger sections are composed from smaller components rather than written as one long block of markup. The home page itself is just a stack of section components:

astrosrc/pages/index.astro
<BaseLayout>
  <Navbar variant="fixed" />
  <AnnouncementBar />
  <main>
    <Hero />
    <Benefits />
    <UseCases />
    <MoreFeatures />
    <Integrations />
    <WhyPaydesk />
    <Pricing />
    <Faq />
    <Reviews />
    <Cta />
  </main>
  <Footer />
</BaseLayout>

Passing Data to Components

In Astro, props are passed the same way as HTML attributes and read via Astro.props. Paydesk’s list components take arrays defined at the top of the parent component:

astro
---
import Accordion from './Accordion.astro';

const text = 'Managing subscriptions and recurring payments can be a daunting task. ...';
const faqs = [
  { title: 'Is there a free trial available?', text },
  { title: 'Can I change my plan later?', text },
];
---
<Accordion items={faqs} class="faq-accordions" id="faq">
  <!-- optional slot content, rendered after the items -->
</Accordion>
No UI framework required

Paydesk uses Astro components only — no React/Vue islands or client: directives. Interactivity (mobile menu, pricing switch, accordions, logo marquee, scroll reveals) is handled by a small <script> block inside each component, using GSAP where animation is involved.

07 · Guide

Styling

Where to change colors, type, and spacing without fighting the build.

Global Styles & CSS Variables

Paydesk is styled with plain CSS — no Tailwind or Sass. BaseLayout.astro imports four global stylesheets from src/styles/, in this order:

FilePurpose
normalize.cssCross-browser reset
base-framework.cssBase layout/utility classes (containers, buttons, forms) the design was built on
paydesk.cssThe theme: color tokens, typography classes, every section’s styles, responsive rules and @font-face declarations
site.cssBehaviour styles for interactive pieces (mobile menu, accordions, tabs, scroll-reveal pre-states); loaded last so its rules win

The brand colors are defined once as CSS custom properties at the top of paydesk.css. Change a value here and it updates everywhere it’s referenced:

csssrc/styles/paydesk.css
:root {
  --heading: #1c1e30;
  --body: #494c65;
  --white: white;
  --green: #01a66b;
  --blue-light: #e6eeff;
  --purple-light: #f0e8fd;
  --orange-light: #fceeed;
  --green-lite: #e6f7f1;
}

Component Styles

Paydesk’s components don’t use scoped styles — all styling lives in the global sheets above, so to restyle a section, search paydesk.css for the class names used in its component (e.g. .pricing-section). For new components of your own, Astro supports scoped <style> blocks — CSS written there only applies to that component, so class names never collide across files.

astro
<style>
  .card { padding: var(--space-md); border-radius: 0.5rem; }
</style>

Responsive Design, Typography & Spacing

Responsive rules live in paydesk.css under four media queries: max-width: 991px (tablet), 767px (large phone), 479px (phone) and min-width: 1280px (wide screens). The type scale is a set of reusable classes in the same file — .h1–.h6, .body-variant-2, .body-variant-3 and so on. Prefer adjusting these shared classes over overriding sizes on individual elements, so the site keeps a consistent rhythm as you edit it.

Avoid editing dist/

The dist/ folder is generated output — any change made there is overwritten on the next build. Always edit files under src/.

08 · Guide

Images & Assets

Two homes for static files, and when to use each.

LocationUse forBehavior
src/assets/images/Product artwork, screenshots and avatars (WebP/PNG) imported into componentsOptimized, resized into responsive srcsets, and content-hashed automatically by the build
public/Favicons, fonts, and the SVG logos/icons/illustrations in public/images/ (referenced as /images/Logo.svg etc.)Copied as-is, no processing

Replacing Images

Swap the file in place (keeping the same filename) or update the import/path to point at your new file. For example, the hero screenshot in src/components/Hero.astro:

astro
---
import { Image } from 'astro:assets';
import heroImage from '../assets/images/Hero-Image.webp';
---
<Image
  src={heroImage}
  alt="Paydesk dashboard showing invoices and payment activity"
  widths={[500, 800, 1080, 1600, 2000]}
  loading="eager"
/>

Supported Formats & SVGs

JPEG, PNG, WebP, AVIF, and GIF are supported through the optimized Image component. In Paydesk, most SVGs live in public/images/ and are referenced as plain <img src="/images/…"> tags; the social and “Why Paydesk” icons are inline-SVG components in src/components/icons/ so they can inherit color via currentColor.

Social preview image

BaseLayout uses src/assets/images/Hero-Image.webp as the default Open Graph image (converted to a 1200px PNG at build time). Pass a different import via the ogImage prop on any page — the login and signup pages pass Form-Image.webp.

Image Optimization

Images imported from src/assets/ are automatically resized and re-encoded at build time based on the width/height (or densities/widths) you specify — you generally don’t need a separate compression step before adding an image to the project.

Rule of thumb

If an image is part of the design (hero photos, thumbnails, icons), put it in src/assets/. If a URL needs to work regardless of the build (a favicon, a file linked from an email), put it in public/.

09 · Guide

Fonts & Icons

Swapping typefaces and icon sets without touching every component.

Google Fonts

Paydesk doesn’t load any Google Fonts — all of its fonts are self-hosted (see below). If you’d rather use a Google Font, add its <link> tags to the <head> in BaseLayout.astro, then update the font-family rules in paydesk.css:

htmlsrc/layouts/BaseLayout.astro
<link rel="preconnect" href="https://fonts.googleapis.com">
<link href="https://fonts.googleapis.com/css2?family=Inter:wght@400;600&display=swap" rel="stylesheet">

Local Fonts

Paydesk uses Onest (Medium and Bold) and Satoshi (Medium). The font files live in public/fonts/ and are declared with @font-face near the end of src/styles/paydesk.css:

csssrc/styles/paydesk.css
@font-face {
  font-family: 'Satoshi Medium';
  src: url('/fonts/Satoshi-Medium.woff') format('woff');
  font-weight: 500;
  font-style: normal;
}

To swap a typeface: add your font file to public/fonts/, point the matching @font-face rule at it, and update the font-family declarations that reference it in paydesk.css (e.g. find & replace Onest Medium). BaseLayout.astro also preloads Onest-Medium.ttf and Satoshi-Medium.woff — update those two <link rel="preload"> tags to match your new files.

Icon Libraries

Paydesk doesn’t depend on an icon library package. Icons come from three places: SVG files in public/images/ (feature icons, check marks, logos, decorations) used as <img> tags; inline-SVG Astro components in src/components/icons/ (Facebook, Instagram, Pinterest, X/Twitter, and the three “Why Paydesk” icons); and a tiny embedded paydesk-icons font in base-framework.css for its w-icon-* utility classes, which the components don’t currently use.

Replacing & Adding Icons

To replace an image-based icon, overwrite the SVG in public/images/ (keeping the filename) or change the path in the component’s data array — e.g. the icon fields in MoreFeatures.astro. The inline icon components take no props: each is a single <svg> using fill="currentColor", so they pick up the surrounding text color. To add one, create a new .astro file in src/components/icons/ containing your <svg> markup and import it the way Footer.astro imports FacebookIcon.

10 · Beginner Friendly

Content Editing

The fastest, lowest-risk way to make the site say what you want it to say.

New to code?

Everything in this section is plain text or attribute changes — no logic to break. Save the file, and your dev server (from Getting Started) will refresh the browser automatically so you can see the change right away.

Headings, Paragraphs & Buttons

For the home page, copy lives in the section components in src/components/ (the Login, Signup, Changelog and License pages keep theirs in src/pages/). Locate the text between the tags and edit it directly — for example, in Hero.astro:

astro
<!-- before -->
<p class="body-variant-3">Join with 5600+ User and grow your business online</p>
<span class="display-and-page-title">Online Billing</span>

<!-- after -->
<p class="body-variant-3">Trusted by 10,000+ finance teams worldwide</p>
<span class="display-and-page-title">Smart Invoicing</span>

Navigation & Footer

Menu links are a links array at the top of src/components/Navbar.astro; footer columns, social links and template links are the columns, socials and templateLinks arrays at the top of src/components/Footer.astro — so you edit the label and URL once rather than hunting through every page. See Navigation for the full pattern.

Cards, Testimonials & Pricing

Repeating content blocks are driven by a data array at the top of their component rather than hand-written per card, so adding or removing an item is a matter of editing the list. Reviews are in Reviews.astro (reviews), FAQs in Faq.astro (faqs), feature cards in MoreFeatures.astro (features), and pricing in Pricing.astro:

javascriptsrc/components/Pricing.astro
const plans = [
  { name: 'Starter', caption: 'For the professionals', monthly: 19, yearly: 59 },
  { name: 'Agency', caption: 'For the professionals', monthly: 59, yearly: 99, recommended: true },
  { name: 'Ultimate', caption: 'For the professionals', monthly: 99, yearly: 199 },
];

Blog Content & Contact Information

Paydesk doesn’t include a blog. Contact details live in src/components/Footer.astro: the placeholder company name and address in the <address> element, the copyright line, and the footer logo’s alt text. The FAQ’s “Support Team” link (mailto:support@example.com) is in src/components/Faq.astro, and the announcement text is a prop default in src/components/AnnouncementBar.astro. The Changelog entries are a releases array in src/pages/changelog.astro.

11 · Guide

Navigation

Header, mobile menu, and footer links, in one predictable place.

Header Navigation

Primary nav links are a small array in Navbar.astro, so adding, removing, or reordering a link doesn’t require touching markup. Each id is the id of a home page section: on the home page the link is #Pricing, on other pages it becomes /#Pricing. The Login and Signup buttons are separate, after the list.

javascriptsrc/components/Navbar.astro
const links = [
  { id: 'Feature', label: 'Features' },
  { id: 'Why-Paydesk', label: 'Why Paydesk?' },
  { id: 'Pricing', label: 'Pricing' },
  { id: 'FAQs', label: 'Faqs' },
  { id: 'Reviews', label: 'Reviews' },
];

Mobile Menu & Dropdown Menus

The mobile menu is a vanilla <script> inside src/components/Navbar.astro (no React island). Below 991px the links collapse behind a menu button; the drawer slides in from the right with GSAP and closes on link click, overlay click, or Esc. The same script slides in the sticky variant="fixed" navbar once the home page is scrolled, and highlights the link for the section in view (scroll-spy). There are no dropdown menus.

Footer Navigation

Footer link groups follow the same data-driven pattern in Footer.astro: a columns array (“Quick links” to home page sections, and “Products” — whose links are # placeholders for you to point somewhere real), templateLinks (Changelog, License Info) and socials.

Internal vs. External Links

Internal links should be root-relative (/about, not the full domain) so they keep working across environments. External links should open safely in a new tab:

html
<a href="/about">About</a>
<a href="https://partner-site.com" target="_blank" rel="noopener noreferrer">Partner</a>

12 · Guide

Forms

What ships out of the box, and what still needs a backend.

Forms need somewhere to go

Every form in Paydesk is front-end only and is not wired to any service. Forms carry a data-demo-form attribute; src/scripts/forms.js intercepts their submit, hides the form and shows its “Thank you” message without sending data anywhere. To collect real submissions you need a backend endpoint or a third-party service.

Signup & Login Forms

Paydesk has no contact form. Its forms are: SignupForm.astro (email capture in the hero and the call-to-action section), AuthForm.astro (name + email on /login and /signup), and the newsletter form in Footer.astro. To make one submit for real, set its action to your endpoint and remove data-demo-form:

htmlsrc/components/Footer.astro
<!-- before: demo only -->
<form name="newsletter-form" method="post" action="#" class="footer-form" data-demo-form>

<!-- after: posts to your service -->
<form name="newsletter-form" method="post" action="https://example.com/your-form-endpoint" class="footer-form">

The “Continue with Google” button on the login/signup pages is a placeholder link (href="#") — real authentication isn’t included.

Newsletter Forms

The footer’s “Subscribe Newsletter” form isn’t pre-wired for any email provider. To connect Mailchimp, ConvertKit or similar, copy the form action URL from your provider’s embedded-form code, rename the input’s name if the provider expects a specific field name, and remove data-demo-form.

Form Validation

Required fields and email format are checked in the browser before submission using standard HTML attributes only (required, type="email", maxlength="256") — there’s no custom validation script — giving users immediate feedback without a round trip to a server.

Third-Party Form Services

If you’d rather not run your own backend, services like Formspree, Getform, or Basin accept form submissions directly from static HTML and forward them to your email — typically a one-line change to the form’s action attribute.

API & Data

Paydesk fetches no external data — this section only matters if you add an API.

No API out of the box

All content is static: it’s written in the markup or in small arrays at the top of each component (see Content Editing), and there are no fetch calls or environment variables. The examples below show the recommended pattern if you connect one.

API Configuration

API URLs and keys are read from environment variables (see Configuration) rather than hard-coded, so the same code can point at a staging or production API depending on environment:

env.env
PUBLIC_API_URL=https://example.com/api
PUBLIC_API_KEY=your_api_key
Never expose real credentials

The values above are placeholders. Keep real API keys out of version control, and prefer server-only variables (without the PUBLIC_ prefix) for anything sensitive.

Fetch Requests

javascript
const res = await fetch(`${import.meta.env.PUBLIC_API_URL}/products`, {
  headers: { Authorization: `Bearer ${import.meta.env.PUBLIC_API_KEY}` },
});
const data = await res.json();

Data Structures

The in-component arrays use these shapes — if you move content to an API or CMS, return the same fields so the components keep working unchanged:

javascript
// Pricing.astro → plans
{ name, caption, monthly, yearly, recommended? }

// Reviews.astro → reviews  (avatar is an imported image)
{ title, text, name, avatar }

// Accordion items (Faq.astro → faqs, WhyPaydesk.astro → items)
{ title, text, icon? }   // icon: an Astro component

// CheckList → items
['Group Chat', 'Quick Report', ...]   // array of strings

Error Handling

javascript
try {
  const res = await fetch(apiUrl);
  if (!res.ok) throw new Error(`Request failed: ${res.status}`);
  const data = await res.json();
} catch (err) {
  // show a fallback UI state instead of a blank page
  console.error(err);
}

SEO

Per-page metadata, social previews, and the machine-readable files search engines expect.

Page Title & Meta Description

Pass a unique title and description into BaseLayout on every page — these drive both the browser tab and the snippet shown in search results. The home page uses the layout’s defaults; the other pages pass their own:

astro
<BaseLayout
  title="Login | Paydesk"
  description="Register an account to start your free trial"
  ogImage={formImage}
>

Canonical URL, Open Graph & Twitter/X Cards

Already set inside BaseLayout.astro’s <head>, using the site value from astro.config.mjs to build absolute URLs. The Open Graph image is generated from the ogImage prop as a 1200px PNG:

html
<link rel="canonical" href={canonical} />
<meta property="og:type" content="website" />
<meta property="og:title" content={title} />
<meta property="og:description" content={description} />
<meta property="og:url" content={canonical} />
<meta property="og:image" content={ogImageUrl} />
<meta name="twitter:card" content="summary_large_image" />
<meta name="twitter:image" content={ogImageUrl} />

Sitemap & Robots.txt

Paydesk includes Astro’s official sitemap integration (@astrojs/sitemap), which generates sitemap-index.xml at build time from the site value, and BaseLayout links to it. No robots.txt ships with the template — create public/robots.txt to control crawler access and point it at your sitemap:

textpublic/robots.txt
User-agent: *
Allow: /
Sitemap: https://example.com/sitemap-index.xml

Structured Data & Semantic HTML

Use landmark elements (<header>, <nav>, <main>, <article>) and a single <h1> per page so both search engines and screen readers can parse the page’s structure. Paydesk’s pages already follow this pattern. No JSON-LD is included, so add structured data to BaseLayout’s <head> yourself for rich results (e.g. Organization or Article schema) where relevant to your content.

Deployment

Platform-by-platform steps. Confirm your rendering mode first — it changes the build output you deploy.

Static vs. SSR — check this first

Paydesk is a fully static Astro build (no adapter): it produces plain HTML/CSS/JS in dist/ that any static host can serve. Only follow the SSR notes below if you later add an adapter for server-side rendering — using the wrong instructions for your rendering mode is the most common deployment mistake.

Vercel

  1. Push the project to a GitHub, GitLab, or Bitbucket repository.
  2. In Vercel, choose Add New → Project and import that repository.
  3. Build command: npm run build · Output directory: dist (Astro static) — Vercel’s Astro preset detects this automatically in most cases.
  4. Paydesk needs no environment variables; if you’ve added any in a .env file, set them under Project Settings → Environment Variables.
  5. Click Deploy.

Netlify

tomlnetlify.toml
[build]
  command = "npm run build"
  publish = "dist"

Connect the repository in the Netlify dashboard, confirm these build settings, add any environment variables you’ve introduced under Site configuration → Environment variables, and deploy. (Paydesk doesn’t ship a netlify.toml; create one with the contents above if you want the settings in code.)

Cloudflare Pages

Connect the repository, set the build command to npm run build and the output directory to dist. For SSR Astro sites, use the official @astrojs/cloudflare adapter instead of the static preset.

GitHub Pages

Set site and base in astro.config.mjs to match your repository URL, then build and publish the dist/ folder to the gh-pages branch (via the official astro build + a deploy action, or manually). GitHub Pages only serves static output — it cannot run an SSR adapter.

Traditional Hosting

For a static build, upload the contents of dist/ to your host’s public web root via FTP/SFTP or your host’s file manager. If you later switch to an SSR build that needs a Node process, the host must support running node continuously (a VPS or a Node-compatible host) — plain shared hosting without Node support cannot run it.

Build & Production

What happens when you run build, and a checklist before you ship.

bash
npm run build     # render pages, bundle CSS/JS, optimize images, write dist/
npm run preview   # serve dist/ locally, exactly as it will run in production

Build Output

The build writes static HTML for all five pages, hashed CSS/JS bundles, optimized responsive images and sitemap-index.xml to dist/. This folder is disposable and regenerated by every build — Paydesk’s .gitignore already excludes it, and it isn’t included in the downloaded package.

Environment Variables in Production

Paydesk itself needs none. If you add some, note that variables from your local .env are not deployed automatically — each hosting platform requires you to set them again in its dashboard (see Deployment). A missing production variable is one of the most common causes of a build that works locally but fails, or behaves unexpectedly, once deployed.

Production Checklist

  • Run npm run build locally and confirm it completes with no errors.
  • Run npm run preview and click through the main pages.
  • Confirm the site URL in astro.config.mjs matches your real domain.
  • If you’ve added environment variables, set each one in your hosting platform’s dashboard.
  • Point each form’s action at a real endpoint and remove data-demo-form (see Forms).
  • Replace the placeholder address, copyright name and # “Products” links in Footer.astro, and the support@example.com link in Faq.astro.
  • Verify public/favicon.svg/favicon.ico, the default Open Graph image (Hero-Image.webp), and the BaseLayout default title/description are your own.

Troubleshooting

The most common problems, in the order you’re likely to hit them.

npm install fails

Cause
Node.js version too old, a corrupted local cache, or a stale lockfile from a different package manager.
Solution
Confirm node --version meets the requirement in Requirements, then run rm -rf node_modules package-lock.json && npm install.

Port already in use

Cause
Another process (often a previous dev server that didn’t shut down cleanly) is already listening on the default port.
Solution
Stop the other process, or start this one on a different port: npm run dev -- --port 4322.

Module not found

Cause
A missing dependency, or a typo or wrong relative depth in an import path (Paydesk uses relative imports only — no path aliases).
Solution
Re-run npm install; check the import path casing matches the file exactly (e.g. Hero-Image.webp, not hero-image.webp — case matters on Linux hosts); count the ../ segments from the importing file.

Images not loading

Cause
An incorrect relative path, or an image placed in src/assets/ but referenced with a public/-style absolute path (or vice versa).
Solution
Review Images & Assets — imported assets need an import statement; public/ files need a root-relative URL like /images/Logo.svg.

Styles not loading

Cause
A stylesheet import was removed from the layout, or a new page doesn’t render inside BaseLayout.
Solution
Confirm BaseLayout.astro still imports normalize.css, base-framework.css, paydesk.css and site.css in that order, and that your page wraps its content in <BaseLayout>.

Sections stay invisible or don’t animate

Cause
Elements with data-reveal start hidden until GSAP animates them in. A new section that uses data-reveal but never calls initReveals() from src/scripts/reveal.js won’t animate; a 3-second safety net in BaseLayout then simply reveals everything.
Solution
Add a <script> to your component that imports initReveals and calls it for your section, as Benefits.astro does. If nothing animates at all, check whether your OS has “reduce motion” enabled — Paydesk deliberately skips animations then.

Build fails (but dev server works)

Cause
The dev server only renders the page you’re viewing, while build renders every page and processes every imported image — a missing image file or a broken import on another page only shows up at build time.
Solution
Read the full terminal output for the first error (later errors are often side effects of it); fix issues top to bottom and re-run.

Environment variables not working

Cause
Only applies if you’ve added variables (Paydesk uses none by default): missing the PUBLIC_ prefix for a client-side value, or the dev server wasn’t restarted after editing .env.
Solution
Rename the variable with the PUBLIC_ prefix if it’s used in browser code, then stop and restart npm run dev — env changes aren’t hot-reloaded.

Deployment problems

Cause
Wrong output directory configured on the host, or environment variables set locally but not in the platform’s dashboard.
Solution
Re-check the build command and output folder against Deployment for your platform, and confirm every variable from .env is duplicated there.

FAQ

Quick answers to the questions we hear most.

How do I install the template?

Extract the ZIP, run your package manager’s install command, then start the dev server. The full walkthrough is in Getting Started.

Which Node.js version should I use?

Node 22.12.0 or later, as required by Astro 7 — see Requirements. The current Node 22+ LTS release is a safe default.

Can I use JavaScript instead of TypeScript?

Paydesk already uses plain JavaScript — no TypeScript is required. If you’d like type checking, you can add a tsconfig.json (extending astro/tsconfigs/strict) in place of jsconfig.json and rename .js files to .ts as you go.

How do I change colors?

Update the CSS custom properties in :root at the top of src/styles/paydesk.css — see Styling.

How do I change fonts?

Add the new font file to public/fonts/, update the @font-face rules and font-family declarations in paydesk.css, and the font preloads in BaseLayout.astro — see Fonts & Icons.

How do I replace images?

Swap the file or update the import path — see Images & Assets.

How do I add a new page?

Add a file to src/pages/; the route is created automatically — see Pages.

How do I deploy the template?

Platform-specific steps for Vercel, Netlify, Cloudflare Pages, GitHub Pages, and traditional hosts are in Deployment.

02 · Setup

Getting Started

From a downloaded ZIP to a running dev server in five steps.

Installation & Extraction

  1. Download the template ZIP from your purchase confirmation email or account downloads page.
  2. Extract it to a folder on your machine — avoid folder names with spaces or special characters.
  3. Open that folder in your terminal and in your code editor.
bash
# Extract on macOS / Linux
unzip template-name.zip -d template-name
cd template-name

Node.js Setup

Check which version of Node.js is currently active:

bash
node --version
# v18.x or later

If you manage multiple Node versions, tools like nvm or fnm make switching painless:

bash
nvm install 18
nvm use 18

Install Dependencies

From the project root, install packages with your preferred package manager:

npm
npm install
pnpm
pnpm install
yarn
yarn install

This reads package.json and downloads every dependency into a local node_modules/ folder. It only needs to be re-run when dependencies change.

Run the Development Server

npm
npm run dev
pnpm
pnpm dev

This starts Vite’s local dev server with hot module reloading — edits to components, pages, and styles appear in the browser immediately without a manual refresh. By default it’s available at http://localhost:4321 (Astro) or http://localhost:5173 (Vite/React); the terminal output will confirm the exact address.

Build for Production & Preview

bash
# Compile an optimized production build into dist/
npm run build

# Serve that build locally to sanity-check it
npm run preview

build type-checks the project, bundles and minifies assets, and writes static output to dist/. preview serves that exact output locally so you can verify it before deploying — it does not rebuild automatically, so re-run build after further changes.

Which command do I actually need?

Use dev while you’re customizing the template. Use build, then preview, once before you deploy — it catches issues (like broken TypeScript types or missing imports) that the dev server tolerates but production won’t.

04 · Reference

Configuration

The files that control how the project builds, and where to set site-wide values.

package.json

Defines dependencies and the scripts you run from the terminal (dev, build, preview). Add your own script here if you introduce a new tool.

jsonpackage.json
{
  "name": "template-name",
  "scripts": {
    "dev": "astro dev",
    "build": "astro build",
    "preview": "astro preview"
  }
}

astro.config.mjs

Controls integrations, the deployed site URL, and build behavior. This is where you’d register the React or Tailwind integrations, or switch rendering modes.

javascriptastro.config.mjs
import { defineConfig } from 'astro/config';
import react from '@astrojs/react';
import tailwind from '@astrojs/tailwind';

export default defineConfig({
  site: 'https://example.com', // used to build absolute URLs for SEO tags
  integrations: [react(), tailwind()],
});

tsconfig.json

Sets TypeScript strictness and path aliases (e.g. importing @/components/Button instead of ../../components/Button).

jsontsconfig.json
{
  "compilerOptions": {
    "baseUrl": ".",
    "paths": { "@/*": ["src/*"] }
  }
}

Environment Variables (.env)

Create a .env file in the project root for values that differ between environments (API URLs, keys) or shouldn’t be committed to Git. Variables must be prefixed PUBLIC_ to be readable in client-side code.

env.env
# Exposed to the browser — never put secrets here
PUBLIC_SITE_URL=https://example.com

# Server-only — safe for secrets, not readable in browser code
API_SECRET_KEY=your_secret_key
Never commit .env

Add .env to .gitignore (it usually is by default). Anything without the PUBLIC_ prefix should stay off the client entirely.

05 · Guide

Pages

How routes are created, and where Astro pages differ from React components.

Creating a New Page

Astro uses file-based routing: any .astro, .md, or .tsx file placed in src/pages/ automatically becomes a route matching its file path.

text
src/pages/index.astro       →  /
src/pages/about.astro       →  /about
src/pages/blog/index.astro  →  /blog
src/pages/blog/[slug].astro →  /blog/:slug  (dynamic)

To add a page, create a new file in src/pages/ using the layout and structure of an existing, similar page as a starting point:

astrosrc/pages/services.astro
---
import BaseLayout from '../layouts/BaseLayout.astro';
---
<BaseLayout title="Services">
  <h1>Our Services</h1>
</BaseLayout>

Editing an Existing Page

Open the relevant file under src/pages/ and edit the markup directly. Anything imported from src/components/ lives elsewhere — edit the component file itself to change content that repeats across multiple pages (like a shared call-to-action block).

Dynamic Routes

Files wrapped in square brackets, such as [slug].astro, generate multiple pages from a single template — commonly used for blog posts or product pages. Astro requires a getStaticPaths() function for these on statically-generated sites:

astrosrc/pages/blog/[slug].astro
---
export async function getStaticPaths() {
  const posts = await import.meta.glob('./posts/*.md');
  return Object.keys(posts).map((path) => ({
    params: { slug: path.split('/').pop().replace('.md', '') },
  }));
}
---

Layouts

Layouts (in src/layouts/) wrap page content with shared structure — the <html> shell, <head> metadata, header, and footer. Every page should render inside a layout via a <slot />:

astrosrc/layouts/BaseLayout.astro
---
interface Props { title: string; }
const { title } = Astro.props;
---
<html lang="en">
  <head><title>{title}</title></head>
  <body>
    <Header />
    <slot /> <!-- page content is injected here -->
    <Footer />
  </body>
</html>

Page Metadata & the 404 Page

Pass a title and description into your layout’s props on every page for correct browser tabs and search results (see also SEO). A file named 404.astro in src/pages/ is served automatically whenever no route matches.

Astro Pages vs. React Components

If the template mixes both: Astro pages (.astro) define routes and render to static HTML by default — no JavaScript ships to the browser unless you ask for it. React components (.tsx) are for interactive UI (dropdowns, forms, sliders) and are dropped into an Astro page with a client: directive that controls when their JavaScript loads:

astro
<ReactCounter client:visible />
<!-- ships JS only once this component scrolls into view -->

06 · Guide

Components

The building blocks pages are assembled from, and how data flows into them.

Reusable Components

Components live in src/components/ and encapsulate one piece of UI — a button, a pricing card, a navigation bar — so it can be reused across pages without copy-pasting markup. Both .astro and .tsx components can live side by side in this folder.

Props & TypeScript Interfaces

Props are the inputs a component accepts, similar to HTML attributes. TypeScript interfaces document exactly what a component expects, and give you autocomplete and compile-time errors if you pass the wrong shape of data.

tsxsrc/components/Button.tsx
interface ButtonProps {
  label: string;
  href?: string;
  variant?: 'primary' | 'ghost';
}

export default function Button({ label, href, variant = 'primary' }: ButtonProps) {
  return (
    <a href={href ?? '#'} className={`btn btn--${variant}`}>
      {label}
    </a>
  );
}

In plain language: label is required and must be text; href is optional (the ?) and, if omitted, the button links nowhere in particular; variant is optional and limited to exactly two allowed values, so a typo like "primry" is caught before it ever reaches the browser.

Component Composition

Larger sections are usually composed from smaller components rather than written as one long block of markup:

tsx
<PricingSection>
  <PricingCard plan="Starter" price={19} />
  <PricingCard plan="Pro" price={49} featured />
</PricingSection>

Passing Data to Components

In Astro, props are passed the same way as HTML attributes and read via Astro.props:

astro
---
import Card from '../components/Card.astro';
---
<Card title="Fast by default" icon="bolt" />
Astro components vs. React components

Astro components (.astro) are ideal for static content and layout. React components (.tsx) are for anything that needs client-side state or interactivity — a mobile menu toggle, a form with validation, a filterable list.

Styling

Where to change colors, type, and spacing without fighting the build.

Global Styles & CSS Variables

Site-wide values — color palette, font families, spacing scale — are defined once as CSS custom properties in src/styles/global.css and referenced everywhere else. Change a value here and it updates across the whole site.

csssrc/styles/global.css
:root {
  --color-primary: #2563eb;
  --color-text: #1f2937;
  --font-body: 'Inter', sans-serif;
  --space-md: 1rem;
}

Component Styles

Astro components support scoped <style> blocks — CSS written there only applies to that component, so class names never collide across files.

astro
<style>
  .card { padding: var(--space-md); border-radius: 0.5rem; }
</style>

Tailwind CSS, if used

Utility classes are applied directly in markup. Shared design tokens (colors, spacing, fonts) are configured centrally in tailwind.config.mjs rather than hard-coded per component:

javascripttailwind.config.mjs
export default {
  theme: {
    extend: {
      colors: { primary: '#2563eb' },
    },
  },
};

SCSS, if used

Sass partials typically live in src/styles/ and are imported into a single entry stylesheet, letting you split variables, mixins, and component styles into separate files while shipping one compiled CSS file.

Responsive Design, Typography & Spacing

Breakpoints and the type scale are defined alongside the other tokens in global.css (or tailwind.config.mjs). Prefer adjusting these shared values over overriding sizes on individual elements, so the site keeps a consistent rhythm as you edit it.

Dark Mode, if supported

[Describe how your template implements dark mode — e.g. a data-theme attribute toggled by a script, or Tailwind’s dark: variant — or remove this subsection if the template is single-theme.]

Avoid editing dist/

The dist/ folder is generated output — any change made there is overwritten on the next build. Always edit files under src/.

08 · Guide

Images & Assets

Two homes for static files, and when to use each.

LocationUse forBehavior
src/assets/Images referenced inside components or pagesOptimized, resized, and content-hashed automatically by the build
public/Files that need a fixed, predictable URL (favicons, downloadable PDFs, og-image.jpg)Copied as-is, no processing

Replacing Images

Swap the file in place (keeping the same filename) or update the import/path to point at your new file:

astro
---
import { Image } from 'astro:assets';
import hero from '../assets/hero.jpg';
---
<Image src={hero} alt="Product screenshot" width={1200} height={630} />

Supported Formats & SVGs

JPEG, PNG, WebP, AVIF, and GIF are supported through the optimized Image component. SVGs are typically imported directly as components for icons that need to inherit color via currentColor, or referenced as plain <img> sources for static illustrations.

Image Optimization

Images imported from src/assets/ are automatically resized and re-encoded at build time based on the width/height (or densities/widths) you specify — you generally don’t need a separate compression step before adding an image to the project.

Rule of thumb

If an image is part of the design (hero photos, thumbnails, icons), put it in src/assets/. If a URL needs to work regardless of the build (a favicon, a file linked from an email), put it in public/.

Fonts & Icons

Swapping typefaces and icon sets without touching every component.

Google Fonts

If the template loads a font from Google Fonts, the <link> tag lives in the shared layout’s <head>. Replace it with your chosen font’s embed code, then update the matching --font-* variable in global.css:

htmlsrc/layouts/BaseLayout.astro
<link rel="preconnect" href="https://fonts.googleapis.com">
<link href="https://fonts.googleapis.com/css2?family=Inter:wght@400;600&display=swap" rel="stylesheet">

Local Fonts

Self-hosted fonts live in src/assets/fonts/ and are declared with @font-face in global.css, pointing at the file path:

css
@font-face {
  font-family: 'Custom Sans';
  src: url('/fonts/custom-sans.woff2') format('woff2');
  font-display: swap;
}

Icon Libraries

Replacing & Adding Icons

Most icon components accept the same props as a regular SVG (size, color, strokeWidth). To add a new icon not included in the library, drop an SVG into src/assets/icons/ and import it like any other component.

Content Editing

The fastest, lowest-risk way to make the site say what you want it to say.

New to code?

Everything in this section is plain text or attribute changes — no logic to break. Save the file, and your dev server (from Getting Started) will refresh the browser automatically so you can see the change right away.

Headings, Paragraphs & Buttons

Find the relevant page in src/pages/, locate the text between the tags, and edit it directly:

astro
<!-- before -->
<h1>Welcome to Our Studio</h1>
<p>We build things people love.</p>
<Button label="Get in touch" href="/contact" />

<!-- after -->
<h1>Welcome to Riverside Design</h1>
<p>We design and build small-business websites.</p>

Navigation & Footer

Menu links and footer content are usually kept in one place — either directly in the Header/Footer component, or as a list in src/data/ — so you edit the label and URL once rather than hunting through every page. See Navigation for the full pattern.

Cards, Testimonials & Pricing

Repeating content blocks are typically driven by a data array rather than hand-written per card, so adding or removing an item is a matter of editing the list:

typescriptsrc/data/testimonials.ts

  { name: 'Devon Marsh', quote: 'Exactly the redesign we needed.', role: 'Marketing Lead' },
];

Blog Content & Contact Information

Blog posts, if included, are typically Markdown files in src/pages/blog/ or src/content/ — edit the front matter (title, date) and body directly. Contact details (address, phone, email) usually live in a single shared component or data file so they only need updating once. [Point to the exact file for your template.]

Navigation

Header, mobile menu, and footer links, in one predictable place.

Header Navigation

Primary nav links are usually defined as a small array so adding, removing, or reordering a link doesn’t require touching markup:

typescriptsrc/data/navigation.ts
export const navLinks = [
  { label: 'Home', href: '/' },
  { label: 'About', href: '/about' },
  { label: 'Contact', href: '/contact' },
];

Mobile Menu & Dropdown Menus

The mobile menu toggle and any dropdown behavior require client-side JavaScript, so this piece is typically a React component (or a small inline <script> in Astro) rather than a static .astro file. [Note here whether your template’s mobile menu is a React island or vanilla script, and its file path.]

Footer Navigation

Footer link groups typically follow the same data-driven pattern as the header, defined alongside or near navLinks.

Internal vs. External Links

Internal links should be root-relative (/about, not the full domain) so they keep working across environments. External links should open safely in a new tab:

html
<a href="/about">About</a>
<a href="https://partner-site.com" target="_blank" rel="noopener noreferrer">Partner</a>

API & Data

Only relevant if your template fetches data from an external source — skip this section otherwise.

API Configuration

API URLs and keys are read from environment variables (see Configuration) rather than hard-coded, so the same code can point at a staging or production API depending on environment:

env.env
PUBLIC_API_URL=https://example.com/api
PUBLIC_API_KEY=your_api_key
Never expose real credentials

The values above are placeholders. Keep real API keys out of version control, and prefer server-only variables (without the PUBLIC_ prefix) for anything sensitive.

Fetch Requests

typescript
const res = await fetch(`${import.meta.env.PUBLIC_API_URL}/products`, {
  headers: { Authorization: `Bearer ${import.meta.env.PUBLIC_API_KEY}` },
});
const data = await res.json();

SEO

Per-page metadata, social previews, and the machine-readable files search engines expect.

Page Title & Meta Description

Pass a unique title and description into the layout on every page — these drive both the browser tab and the snippet shown in search results:

astro
<BaseLayout
  title="Services | Riverside Design"
  description="Web design and development for small businesses."
>

Canonical URL, Open Graph & Twitter/X Cards

Set inside the layout’s <head>, using the site value from astro.config.mjs to build absolute URLs:

html
<link rel="canonical" href={canonicalURL} />
<meta property="og:title" content={title} />
<meta property="og:description" content={description} />
<meta property="og:image" content={"[Replace with an absolute image URL]"} />
<meta name="twitter:card" content="summary_large_image" />

Sitemap & Robots.txt

Astro’s official sitemap integration generates sitemap-index.xml automatically at build time once the site value is set. public/robots.txt controls crawler access and typically points to that sitemap:

textpublic/robots.txt
User-agent: *
Allow: /
Sitemap: https://example.com/sitemap-index.xml

Structured Data & Semantic HTML

Use landmark elements (<header>, <nav>, <main>, <article>) and a single <h1> per page so both search engines and screen readers can parse the page’s structure. Add JSON-LD structured data in the layout’s <head> for rich results (e.g. Organization or Article schema) where relevant to your content.

15 · Guide

Deployment

Platform-by-platform steps. Confirm your rendering mode first — it changes the build output you deploy.

Static vs. SSR — check this first

A static Astro build (the default) produces plain HTML/CSS/JS in dist/ that any static host can serve. An Astro site using server-side rendering (SSR via an adapter) and a React/Vite single-page app both need a Node-capable host or the platform’s matching adapter. Using the wrong instructions for your rendering mode is the most common deployment mistake.

Vercel

  1. Push the project to a GitHub, GitLab, or Bitbucket repository.
  2. In Vercel, choose Add New → Project and import that repository.
  3. Build command: npm run build · Output directory: dist (Astro static) — Vercel’s Astro preset detects this automatically in most cases.
  4. Add any environment variables from your .env file under Project Settings → Environment Variables.
  5. Click Deploy.

Netlify

tomlnetlify.toml
[build]
  command = "npm run build"
  publish = "dist"

Connect the repository in the Netlify dashboard, confirm these build settings, add environment variables under Site configuration → Environment variables, and deploy.

Cloudflare Pages

Connect the repository, set the build command to npm run build and the output directory to dist. For SSR Astro sites, use the official @astrojs/cloudflare adapter instead of the static preset.

GitHub Pages

Set site and base in astro.config.mjs to match your repository URL, then build and publish the dist/ folder to the gh-pages branch (via the official astro build + a deploy action, or manually). GitHub Pages only serves static output — it cannot run an SSR adapter.

Traditional Hosting

For a static build, upload the contents of dist/ to your host’s public web root via FTP/SFTP or your host’s file manager. For an SSR build or a React/Vite app that needs a Node process, the host must support running node continuously (a VPS or a Node-compatible host) — plain shared hosting without Node support cannot run it.

16 · Guide

Build & Production

What happens when you run build, and a checklist before you ship.

bash
npm run build     # type-check, bundle, and write dist/
npm run preview   # serve dist/ locally, exactly as it will run in production

Build Output

The build writes static HTML, hashed CSS/JS bundles, and optimized images to dist/ (or build/, for some Vite/React setups). This folder is disposable and regenerated by every build — it’s conventional to keep it out of Git via .gitignore.

Environment Variables in Production

Variables from your local .env are not deployed automatically — each hosting platform requires you to set them again in its dashboard (see Deployment). A missing production variable is one of the most common causes of a build that works locally but fails, or behaves unexpectedly, once deployed.

Production Checklist

  • Run npm run build locally and confirm it completes with no errors.
  • Run npm run preview and click through the main pages.
  • Confirm the site URL in astro.config.mjs matches your real domain.
  • Set every environment variable from .env in your hosting platform’s dashboard.
  • Check that forms, if any, point at a real endpoint rather than a placeholder.
  • Verify favicon, Open Graph image, and meta descriptions are your own, not the template defaults.

Troubleshooting

The most common problems, in the order you’re likely to hit them.

npm install fails

Cause
Node.js version too old, a corrupted local cache, or a stale lockfile from a different package manager.
Solution
Confirm node --version meets the requirement in Requirements, then run rm -rf node_modules package-lock.json && npm install.

Port already in use

Cause
Another process (often a previous dev server that didn’t shut down cleanly) is already listening on the default port.
Solution
Stop the other process, or start this one on a different port: npm run dev -- --port 4322.

Module not found

Cause
A missing dependency, a typo in an import path, or a path alias not registered in tsconfig.json.
Solution
Re-run npm install; check the import path casing matches the file exactly; confirm the alias exists under compilerOptions.paths.

Images not loading

Cause
An incorrect relative path, or an image placed in src/assets/ but referenced with a public/-style absolute path (or vice versa).
Solution
Review Images & Assets — imported assets need an import statement; public/ files need a root-relative URL like /logo.svg.

Styles not loading

Cause
The stylesheet isn’t imported into the layout, or a Tailwind class isn’t being generated because the file isn’t covered by its content glob.
Solution
Confirm global.css is imported in BaseLayout; check tailwind.config.mjs’s content array includes the file you’re editing.

TypeScript errors

Cause
A component is receiving props that don’t match its declared interface, often after copy-pasting a component and changing its usage.
Solution
Read the error’s file and line number, compare against the component’s interface (see Props), and adjust whichever side is wrong.

Build fails (but dev server works)

Cause
The dev server is more forgiving than build, which fully type-checks the project — an issue tolerated in dev can fail the build.
Solution
Read the full terminal output for the first error (later errors are often side effects of it); fix issues top to bottom and re-run.

Environment variables not working

Cause
Missing the PUBLIC_ prefix for a client-side value, or the dev server wasn’t restarted after editing .env.
Solution
Rename the variable with the PUBLIC_ prefix if it’s used in browser code, then stop and restart npm run dev — env changes aren’t hot-reloaded.

Deployment problems

Cause
Wrong output directory configured on the host, or environment variables set locally but not in the platform’s dashboard.
Solution
Re-check the build command and output folder against Deployment for your platform, and confirm every variable from .env is duplicated there.

FAQ

Quick answers to the questions we hear most.

How do I install the template?

Extract the ZIP, run your package manager’s install command, then start the dev server. The full walkthrough is in Getting Started.

Which Node.js version should I use?

Node 18 or later — see Requirements. The current LTS release is a safe default.

Can I use JavaScript instead of TypeScript?

Generally yes — rename .ts/.tsx files to .js/.jsx and remove type annotations. You’ll lose compile-time type checking, so weigh that against the convenience.

How do I change colors?

Update the CSS custom properties in src/styles/global.css (or the palette in tailwind.config.mjs) — see Styling.

How do I change fonts?

Swap the font import and update the corresponding --font-* variable — see Fonts & Icons.

How do I replace images?

Swap the file or update the import path — see Images & Assets.

How do I add a new page?

Add a file to src/pages/; the route is created automatically — see Pages.

How do I deploy the template?

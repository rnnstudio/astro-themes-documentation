01 · Overview

Introduction

Everything you need to know before you open your editor — what’s in the box, what it’s built with, and what it expects from your machine.

Welcome

Thanks for picking up Oliver Bravo, a bold, animation-rich portfolio theme for creative directors, designers and studios. It pairs oversized editorial typography with a full-screen video hero, stacking project cards, an awards showcase with slide-in detail panels, a services accordion, client reviews and a contact form — all driven by GSAP scroll animations. This guide walks through installing the template, understanding how the project is organized, customizing content and styling, and shipping it to production. It’s written for developers who are comfortable with the command line but new to this specific codebase — if you already know Astro well, feel free to skip ahead using the sidebar.

All names, projects, testimonials and contact details in the demo are placeholder content — replace them with your own before launching.

What’s Included

Source files

The full, uncompiled project source — components, pages, styles, and configuration.

Production build

Not pre-built — the download contains source only. Run npm run build once to generate a deployable dist/ folder (see Build & Preview).

Design assets

Demo images (AVIF, PNG and SVG) in public/images/, the hero background video (MP4 + WebM) in public/videos/, the Creato Display font files in public/fonts/, and 12 inline SVG icons in src/components/Icon.astro. No Figma or other design source files are included.

This documentation

A single self-contained HTML page — the download’s documentation.txt links to it, and a saved copy opens in any browser with no server required.

Features

  • Home, About and Work pages, a case-study page per project (/project/[slug]), category archives (/category/[slug]), and a 404 page
  • Projects managed as plain Markdown files in a content collection — add a file and it appears on the Work page, its category page and its own URL
  • GSAP animations installed from npm: split-text reveals, a hero-to-About image transition (Flip), stacking work cards, a counter, a magnetic button, a marquee and more — each set up in its own component
  • Respects prefers-reduced-motion, and content stays visible when JavaScript is off
  • Responsive at desktop, tablet and mobile breakpoints, with an animated mobile menu
  • Per-page title and description, Open Graph and Twitter tags, canonical URLs and an XML sitemap
  • Self-hosted fonts: Creato Display (local files) and Playfair Display (Fontsource)
  • No UI framework and no TypeScript — just .astro components, plain CSS and vanilla JavaScript

Technology Stack

Oliver Bravo is a static Astro site written in plain JavaScript and CSS. Its only runtime library is GSAP.

Astro 7 GSAP (ScrollTrigger, SplitText, Flip) @astrojs/sitemap Fontsource Vanilla JS & CSS Vite

02 · Setup

Getting Started

From a downloaded ZIP to a running dev server in five steps.

Installation & Extraction

  1. Download the template ZIP from your purchase confirmation email or account downloads page.
  2. Extract it to a folder on your machine — avoid folder names with spaces or special characters.
  3. Open that folder in your terminal and in your code editor.
bash
# Extract on macOS / Linux
unzip oliver-bravo-astro-package.zip
cd oliver-bravo-astro

Node.js Setup

Check which version of Node.js is currently active:

bash
node --version
# v22.23.4 or later

If you manage multiple Node versions, tools like nvm or fnm make switching painless:

bash
nvm install 24   # any release from 22.23.4 up works
nvm use 24

Install Dependencies

From the project root, install packages with your preferred package manager:

npm
npm install
pnpm
pnpm install
yarn
yarn install

This reads package.json and downloads every dependency into a local node_modules/ folder. It only needs to be re-run when dependencies change.

Run the Development Server

npm
npm run dev
pnpm
pnpm dev

This starts Vite’s local dev server with hot module reloading — edits to components, pages, and styles appear in the browser immediately without a manual refresh. By default it’s available at http://localhost:4321; the terminal output will confirm the exact address.

Build for Production & Preview

bash
# Compile an optimized production build into dist/
npm run build

# Serve that build locally to sanity-check it
npm run preview

build renders every page (including one page per project and per category), bundles and minifies the CSS and JavaScript, generates the sitemap, and writes static output to dist/. preview serves that exact output locally so you can verify it before deploying — it does not rebuild automatically, so re-run build after further changes.

Which command do I actually need?

Use dev while you’re customizing the template. Use build, then preview, once before you deploy — because it renders every page, it catches problems on pages you never opened in dev, such as a missing import or a project file whose frontmatter doesn’t match the schema.

A tour of the folders you’ll actually touch, and the ones you generally shouldn’t.

04 · Reference

Configuration

The files that control how the project builds, and where to set site-wide values.

package.json

Defines dependencies and the scripts you run from the terminal (dev, build, preview). Add your own script here if you introduce a new tool.

jsonpackage.json
{
  "name": "oliver-bravo-astro",
  "type": "module",
  "version": "0.0.1",
  "engines": { "node": ">=22.23.4" },
  "scripts": {
    "dev": "astro dev",
    "build": "astro build",
    "preview": "astro preview",
    "astro": "astro"
  },
  "dependencies": {
    "@astrojs/sitemap": "^3.7.6",
    "@fontsource/playfair-display": "^5.3.0",
    "astro": "^7.4.13",
    "gsap": "^3.15.1"
  }
}

astro.config.mjs

Controls integrations, the deployed site URL, and build behavior. The template registers only the sitemap integration. Set site to your production domain before deploying — canonical URLs, Open Graph image URLs and the sitemap are all built from it.

javascriptastro.config.mjs
import { defineConfig } from 'astro/config';
import sitemap from '@astrojs/sitemap';

// Replace with your production URL — used for canonical/OG URLs and the sitemap.
export default defineConfig({
  site: 'https://example.com',
  integrations: [sitemap()],
});

tsconfig.json

The template contains no TypeScript. This is Astro’s standard default file, kept so your editor can offer autocomplete and hints inside .astro files. No path aliases are defined, so imports use relative paths such as ../components/Button.astro.

jsontsconfig.json
{
  "extends": "astro/tsconfigs/strict",
  "include": [".astro/types.d.ts", "**/*"],
  "exclude": ["dist"]
}

Environment Variables (.env)

The template doesn’t read any environment variables, so no .env file is needed. Its only external setting, the contact-form endpoint, lives in src/data/site.js. If you add something of your own (an API URL or key), create a .env file in the project root for values that differ between environments or shouldn’t be committed to Git. Variables must be prefixed PUBLIC_ to be readable in client-side code.

env.env
# Exposed to the browser — never put secrets here
PUBLIC_SITE_URL=https://example.com

# Server-only — safe for secrets, not readable in browser code
API_SECRET_KEY=your_secret_key
Never commit .env

Add .env to .gitignore (it usually is by default). Anything without the PUBLIC_ prefix should stay off the client entirely.

05 · Guide

Pages

How routes are created, and how the project and category pages are generated.

Creating a New Page

Astro uses file-based routing: any .astro or .md file placed in src/pages/ automatically becomes a route matching its file path. These are the template’s routes:

text
src/pages/index.astro            →  /                (hero, work, why, clients)
src/pages/about.astro            →  /about           (hero, services, awards, reviews)
src/pages/work.astro             →  /work            (all projects, reviews)
src/pages/project/[slug].astro   →  /project/:slug   (one page per project)
src/pages/category/[slug].astro  →  /category/:slug  (one page per category)
src/pages/404.astro              →  404 page

To add a page, create a new file in src/pages/ using the layout and structure of an existing, similar page as a starting point:

astrosrc/pages/services.astro
---
import BaseLayout from '../layouts/BaseLayout.astro';
import ServicesSection from '../components/ServicesSection.astro';
---
<BaseLayout
  title="Services | Oliver Bravo Creative Director"
  description="Brand identity, web design and digital marketing services."
  navVariant="dark"
>
  <ServicesSection />
</BaseLayout>

Editing an Existing Page

Open the relevant file under src/pages/ and edit the markup directly. The Home, About and Work pages are short: they mostly import section components from src/components/. Edit the component file itself to change a section’s content. For example, the hero text is in HeroAbout.astro, which both Home and About use.

Dynamic Routes

Files wrapped in square brackets generate multiple pages from a single template. The template has two. project/[slug].astro builds one case-study page for every Markdown file in src/content/projects/, using the file name as the slug. category/[slug].astro builds one archive page for every distinct category value. Astro requires a getStaticPaths() function for these on statically-generated sites:

astrosrc/pages/project/[slug].astro
---
import { getCollection } from 'astro:content';

export async function getStaticPaths() {
  const projects = (await getCollection('projects')).sort((a, b) => a.data.order - b.data.order);
  // "Go next" shows the first three projects
  const related = projects.slice(0, 3);
  return projects.map((project) => ({ params: { slug: project.id }, props: { project, related } }));
}
---

Layouts

Layouts (in src/layouts/) wrap page content with shared structure — the <html> shell, <head> metadata, header, and footer. Every page should render inside a layout via a <slot />:

astrosrc/layouts/BaseLayout.astro
---
import '../styles/global.css';
import Navbar from '../components/Navbar.astro';
import Footer from '../components/Footer.astro';
import { site } from '../data/site.js';

const {
  title = site.defaultTitle,
  description = site.defaultDescription,
  ogImage = site.ogImage,
  navVariant = 'light',
  footerVariant = 'base',
} = Astro.props;
---
<html lang="en">
  <head><title>{title}</title> <!-- + description, canonical, Open Graph & Twitter tags --></head>
  <body>
    <div class="page-wrap">
      <Navbar variant={navVariant} />
      <main class="main-wrap">
        <slot /> <!-- page content is injected here -->
      </main>
      <Footer variant={footerVariant} />
    </div>
  </body>
</html>

Page Metadata & the 404 Page

Pass a title and description into BaseLayout on every page for correct browser tabs and search results (see also SEO). When they’re omitted, the layout falls back to site.defaultTitle and site.defaultDescription from src/data/site.js. The layout also accepts:

  • ogImage: the social sharing image. Project pages pass their cover image.
  • navVariant: 'light' (white text, for dark heroes) or 'dark' (black text, for light pages).
  • footerVariant: 'base', or 'utility' (contact links only, no marquee or form), used by the 404 page.

A file named 404.astro in src/pages/ is served automatically whenever no route matches.

Components

The building blocks pages are assembled from, and how data flows into them.

Reusable Components

Components live in src/components/ and encapsulate one piece of UI, so it can be reused across pages without copy-pasting markup. All of the template’s components are .astro files:

ComponentUsed onWhat it renders

ServicesSectionAboutServices accordion with hover preview images
AwardsSectionAboutAward cards and their slide-in detail panels
ReviewsSectionAbout, WorkClient review cards

FreelancerCardInside HeroAboutThe portrait card with the “Available for work” badge

Props

Props are the inputs a component accepts, similar to HTML attributes. The template is plain JavaScript, so each component documents its props in a comment and sets defaults by destructuring Astro.props. Here is Button:

astrosrc/components/Button.astro
---
/**
 * Pill button with the animated arrow dot.
 * type: 'primary' (yellow) | 'secondary' (white) | 'tertiary' (black)
 * size: 'normal' | 'small'
 */
const { href = '#', label, type = 'primary', size = 'normal', target, class: extra = '' } = Astro.props;
---

In plain language:

  • label is the button text.
  • href defaults to #.
  • type picks the colour. Stick to the three listed values: anything else breaks the colour lookup and the page fails to render.
  • size="small" gives the compact version.
  • target="_blank" opens the link in a new tab and adds rel="noopener noreferrer" automatically.
  • class adds extra classes.

Component Composition

Pages are composed from section components rather than written as one long block of markup. This is the whole Home page:

astrosrc/pages/index.astro
<BaseLayout title="Oliver Bravo — Creative Director Portfolio">
  <HeroAbout workHref="#work" />
  <WorkSection projects={projects} heading='Selected <span class="secondary-font">Work</span>' showAll />
  <WhySection />
  <ClientsSection />
</BaseLayout>

Passing Data to Components

In Astro, props are passed the same way as HTML attributes and read via Astro.props:

astro
---
import { getCollection } from 'astro:content';
import Button from '../components/Button.astro';
import WorkSection from '../components/WorkSection.astro';

const projects = (await getCollection('projects')).sort((a, b) => a.data.order - b.data.order).slice(0, 6);
---
<Button href="/about" label="About Me" type="secondary" size="small" />
<WorkSection projects={projects} heading="Recent Work" headingTag="h2" />

WorkSection accepts these props:

  • projects: collection entries, already sorted and limited.
  • heading: heading HTML, which may contain a secondary-font span for the italic serif word.
  • headingTag: 'h1' or 'h2'.
  • flat: removes the rounded top corners. Use it when the section starts the page.
  • showAll: shows the “See All Work” button.
Interactivity without a UI framework

There are no React (or other framework) components. Each component’s interactivity and animation live in a <script> tag at the bottom of its .astro file, which Astro bundles and loads once per page. The GSAP plugins are registered once in src/scripts/gsap.js, and the shared text reveals are in src/scripts/reveal.js.

07 · Guide

Styling

Where to change colors, type, and spacing without fighting the build.

Global Styles & CSS Variables

All styling is plain CSS in src/styles/. BaseLayout imports global.css, which loads the other files in this order:

FilePurpose
normalize.cssBrowser reset
base-framework.cssLayout utility classes (.w-container, .w-layout-hflex, form classes…)
oliver-bravo.cssThe theme: @font-face rules, the :root variables, and every section’s styles and breakpoints
custom.cssSmall template additions: pre-animation states, focus outlines, form success/error states, the scroll lock

Site-wide values — colours, font families, the type scale and spacing — are CSS custom properties in the :root block at the top of src/styles/oliver-bravo.css. Change a value there and it updates across the whole site:

csssrc/styles/oliver-bravo.css
:root {
  --colors--white: white;
  --colors--black: #000;
  --colors--yellow: #fed532;            /* accent: buttons, badges */
  --fonts--primary: Creatodisplay, Verdana, sans-serif;
  --fonts--secondary: "Playfair Display", sans-serif;
  --_spacing---container--medium: 80rem;
  --_spacing---padding--section-padding: 10rem;
  /* …plus the --_typography---* type scale */
}

Component Styles

The template’s components share class names, so their styles live in src/styles/oliver-bravo.css rather than inside the components. Look there first when changing an existing section. For a new component you add, Astro supports scoped <style> blocks — CSS written there only applies to that component, so class names never collide across files.

astro
<style>
  .card { padding: var(--space-md); border-radius: 0.5rem; }
</style>
@@@END

Responsive Design, Typography & Spacing

Desktop styles are the default. oliver-bravo.css then overrides them in three max-width media queries: 991px (tablet, where the mobile menu takes over), 767px (large phones) and 479px (small phones). The type scale is the set of --_typography---* variables in :root. Prefer adjusting these shared values over overriding sizes on individual elements, so the site keeps a consistent rhythm as you edit it.

Avoid editing dist/

The dist/ folder is generated output — any change made there is overwritten on the next build. Always edit files under src/.

08 · Guide

Images & Assets

Two homes for static files, and when to use each.

LocationUse forBehavior
public/Where the template keeps all of its media: images/ (with images/projects/ for case studies), videos/, fonts/ and the faviconsCopied as-is, no processing; referenced as /images/…
src/assets/Not used by the template. Create it if you want new images run through Astro’s <Image> componentOptimized, resized, and content-hashed automatically by the build

Replacing Images

Swap the file in public/images/ in place, keeping the same filename, or update the path where it’s used. Project images are set in each project’s frontmatter:

yamlsrc/content/projects/time.md
coverImage: "/images/projects/project-28.avif"
coverAlt: "Describe the image for screen readers"
overviewImages:
  - "/images/projects/project-31.avif"
  - "/images/projects/project-34.avif"
  - "/images/projects/project-30.avif"

Images used in sections, such as the portrait, client logos, award photos and reviewer photos, are referenced by path inside the matching component. Some of them also have -500 or -800 width versions listed in a srcset. If you replace one of those, replace its smaller versions too, or delete the srcset attribute. The hero video is public/videos/hero-background.mp4/.webm, and its poster frame is public/images/hero-background-poster.jpg.

Supported Formats & SVGs

The demo images are mostly AVIF, plus one PNG and two SVG award logos. Because files in public/ are served as-is, any format the browser understands works: JPEG, PNG, WebP, AVIF, GIF or SVG. UI icons are inline SVG inside Icon.astro, so they inherit colour via currentColor. See Icon Libraries.

Image Optimization

The template doesn’t run images through Astro’s image pipeline. The demo files are already compressed AVIFs. Because public/ files are not processed, compress your own images before adding them (any image tool that exports AVIF or WebP works). Export them at roughly the size of the file you’re replacing. Alternatively, move an image into src/assets/ and render it with Astro’s <Image> component, which resizes and re-encodes it at build time.

Rule of thumb

Replacing a demo image? Keep the template’s convention: put the compressed file in public/images/ and reference it with a root-relative path. Anything that needs a fixed URL (a favicon, a file linked from an email) must stay in public/.

09 · Guide

Fonts & Icons

Swapping typefaces and icon sets without touching every component.

Google Fonts (via Fontsource)

Nothing is loaded from Google’s servers. The italic serif accent font, Playfair Display (a Google Font), is self-hosted from npm through @fontsource/playfair-display and imported at the top of global.css. Only the upright weights are loaded, and the browser renders the italic accent words from them, as in the original design. To use a different font, install its Fontsource package (npm install @fontsource/<font>), replace these imports, and update --fonts--secondary in oliver-bravo.css:

csssrc/styles/global.css
@import '@fontsource/playfair-display/400.css';
@import '@fontsource/playfair-display/500.css';
@import '@fontsource/playfair-display/600.css';
@import '@fontsource/playfair-display/700.css';

Local Fonts

The main typeface, Creato Display, ships as seven .otf files (Thin to Black) in public/fonts/. Each one is declared with @font-face at the top of src/styles/oliver-bravo.css and used through --fonts--primary. To swap it, drop your font files into public/fonts/, update the @font-face blocks, and change --fonts--primary:

csssrc/styles/oliver-bravo.css
@font-face {
  font-family: Creatodisplay;
  src: url('/fonts/CreatoDisplay-Thin.otf') format("opentype");
  font-weight: 100;
  font-style: normal;
  font-display: swap;
}

Icon Libraries

No icon library is installed. The template’s 12 icons are inline SVGs in src/components/Icon.astro, selected by name: arrow, link-arrow, mail, mail-dot, phone, dribbble, instagram, x, facebook, close, pause and play. They follow the text colour unless you pass a color:

astro
<Icon name="instagram" />
<Icon name="arrow" color="var(--colors--yellow)" />

Other artwork:

  • The navbar wordmark is in src/components/Logo.astro.
  • The Awwwards and Dribbble award logos are SVG files in public/images/.

Replacing & Adding Icons

To replace an icon, swap the <svg> for that name in Icon.astro. To add one, copy an existing block such as {name === 'x' && ( … )}, give it a new name, and paste in your SVG. In both cases, keep width="100%" and height="100%" so it fills its wrapper, and use fill="currentColor" so it follows the text colour.

10 · Beginner Friendly

Content Editing

The fastest, lowest-risk way to make the site say what you want it to say.

New to code?

Everything in this section is plain text or attribute changes — no logic to break. Save the file, and your dev server (from Getting Started) will refresh the browser automatically so you can see the change right away.

Headings, Paragraphs & Buttons

Find the relevant page in src/pages/, locate the text between the tags, and edit it directly:

astro
<!-- before (src/components/HeroAbout.astro) -->
<H data-anim="letters-split" class="giant-heading is-hero-heading">Oliver Bravo crafting <span class="secondary-font">brands</span> that inspire</H>
<p data-anim="letters-split" class="paragraph-large">A lifestyle revolution for a sustainable fulfilling future</p>

<!-- after -->
<H data-anim="letters-split" class="giant-heading is-hero-heading">Nora Vale designing <span class="secondary-font">spaces</span> that last</H>
<p data-anim="letters-split" class="paragraph-large">Interior and brand design for independent hotels</p>

Keep the data-anim attribute and the classes; they drive the animation and the styling. A secondary-font span renders that word in the italic serif. Button text is the label prop, for example <Button href="/about" label="About Me" />.

Navigation & Footer

Menu links (navLinks), social links, email, phone and copyright line all live in src/data/site.js. Edit the label and URL once there rather than hunting through every page. See Navigation for the full pattern.

Cards, Testimonials & Pricing

The template has no pricing section. Repeating blocks are driven by a data array at the top of their component, so adding or removing an item is a matter of editing the list:

  • services in ServicesSection.astro.
  • awards in AwardsSection.astro.
  • clients in ClientsSection.astro.
  • blocks in WhySection.astro.
  • reviews in ReviewsSection.astro. Its array sets each card’s colour, alignment and photo alt text, and the quote and name are in the markup below it.
javascriptsrc/components/ServicesSection.astro
const services = [
  { title: 'Website Design Development', image: images.hof },
  { title: 'Brand Identity Design', image: images.portrait },
  { title: 'Search Engine Optimization', image: images.london },
  { title: 'Social Media Marketing', image: images.freelancer },
];

Portfolio projects are Markdown files in src/content/projects/. To add one, duplicate an existing file, rename it (the file name becomes the URL, e.g. /project/my-project) and edit its frontmatter. order sets its position, and the Home page shows the first six.

Blog Content & Contact Information

The template has no blog. Contact details live in src/data/site.js, so they only need updating once:

  • email.
  • phone, plus phoneHref for the tel: link.
  • socials and dribbble.
  • copyright.

The footer reads them on every page. The text around them, such as the “Talk to me” marquee and the form labels, is in src/components/Footer.astro.

11 · Guide

Navigation

Header, mobile menu, and footer links, in one predictable place.

Header Navigation

Primary nav links are defined as a small array in src/data/site.js, so adding, removing, or reordering a link doesn’t require touching markup. Navbar.astro renders them and marks the current page with the is-current class. The yellow Contact button after the links is part of Navbar.astro itself:

javascriptsrc/data/site.js
export const navLinks = [
  { label: 'Home', href: '/' },
  { label: 'Work', href: '/work' },
  { label: 'About', href: '/about' },
];

Mobile Menu & Dropdown Menus

The mobile menu toggle needs client-side JavaScript. Here it is a vanilla <script> using GSAP at the bottom of src/components/Navbar.astro, not a React island. Below 992px the links collapse behind the hamburger button. Opening it turns the lines into a cross, slides the panel in from the right and blurs the page behind it. Pressing Escape, clicking a link or clicking the button again closes it. The button’s aria-expanded attribute is updated as it opens and closes. The template has no dropdown menus.

Footer Navigation

The footer follows the same data-driven pattern: Footer.astro renders the socials array (Instagram, X and Facebook) and the email, phone and copyright from src/data/site.js, followed by a “Built with Astro” link.

Internal vs. External Links

Internal links should be root-relative (/about, not the full domain) so they keep working across environments. External links should open safely in a new tab. The Button component adds the rel attribute for you when you pass target="_blank":

html
<a href="/about">About</a>
<a href="https://partner-site.com" target="_blank" rel="noopener noreferrer">Partner</a>

Forms

What ships out of the box, and what still needs a backend.

Forms need somewhere to go

The contact form at the bottom of every page (in src/components/Footer.astro) is not connected to any service. Until you set formEndpoint in src/data/site.js, it runs in demo mode: submitting shows the success message, but nothing is sent anywhere.

Contact Forms

The form collects four fields:

  • name (required).
  • email (required).
  • project-query: a free-text message.
  • budget: one of four radio options, set in the budgets array at the top of Footer.astro.

To make it send, point formEndpoint at your service:

javascriptsrc/data/site.js
// Left empty, the contact form runs in demo mode and just shows the success message.
formEndpoint: 'https://formspree.io/f/your-form-id',

The submit handler in Footer.astro then posts the fields as FormData. A 2xx response shows the success message, and anything else shows the error message:

javascriptsrc/components/Footer.astro
const res = await fetch(endpoint, {
  method: 'POST',
  body: new FormData(form),
  headers: { Accept: 'application/json' },
});
ok = res.ok;

Newsletter Forms

The template has no newsletter form. If you add one, a provider’s embedded form (e.g. Mailchimp or Kit) or the same fetch pattern as the contact form both work on a static site.

Form Validation

Validation uses the browser’s built-in checks, with no custom validation code. Name and email carry required, the email field is type="email", and every field has a maxlength. Users get immediate feedback without a round trip to a server, but your form service should still validate on its side.

Third-Party Form Services

If you’d rather not run your own backend, services like Formspree, Getform, or Basin accept form submissions directly from static HTML and forward them to your email. In this template that’s a one-line change to formEndpoint, which also becomes the form’s action attribute. Any service that accepts a multipart/form-data POST and returns a 2xx status on success will work.

API & Data

Oliver Bravo doesn’t fetch data from any external API — all content is local and built into static pages. This section covers the local data model, and what to do if you add an API of your own.

API Configuration

No API is configured and no environment variables are needed. If you connect an API later, read its URLs and keys from environment variables (see Configuration) rather than hard-coding them, so the same code can point at a staging or production API depending on environment:

env.env
PUBLIC_API_URL=https://example.com/api
PUBLIC_API_KEY=your_api_key
Never expose real credentials

The values above are placeholders. Keep real API keys out of version control, and prefer server-only variables (without the PUBLIC_ prefix) for anything sensitive.

Fetch Requests

The only network request the template makes in the browser is the contact-form POST (see Contact Forms). A request to an API of your own would look like this:

javascript
const res = await fetch(`${import.meta.env.PUBLIC_API_URL}/products`, {
  headers: { Authorization: `Bearer ${import.meta.env.PUBLIC_API_KEY}` },
});
const data = await res.json();

Data Structures

The template’s structured data is the projects content collection. Every Markdown file in src/content/projects/ must match this schema. If a required field is missing, or there aren’t exactly three overview or solution images, the build stops with an error naming the file:

javascriptsrc/content.config.js
schema: z.object({
  title: z.string(),
  order: z.number(),                        // sort position (Home shows the first six)
  category: z.string(),                     // also creates /category/<slug>
  client: z.string(),
  services: z.string(),
  website: z.string().url(),                // the "Website" button
  seoTitle: z.string(),
  seoDescription: z.string(),
  coverImage: z.string(),
  coverAlt: z.string().default(''),
  titleColor: z.string().default(''),      // title colour on the "Go next" cards
  overviewImages: z.array(z.string()).length(3),
  solutionImages: z.array(z.string()).length(3),
  overview: z.string(),                     // HTML
  solution: z.string(),                     // HTML
}),

Site-wide settings (site, navLinks) are plain JavaScript objects exported from src/data/site.js.

Error Handling

The contact form already wraps its request in try/catch and shows the form’s error message on failure. Use the same pattern for any request you add:

javascript
try {
  const res = await fetch(apiUrl);
  if (!res.ok) throw new Error(`Request failed: ${res.status}`);
  const data = await res.json();
} catch (err) {
  // show a fallback UI state instead of a blank page
  console.error(err);
}

SEO

Per-page metadata, social previews, and the machine-readable files search engines expect.

Page Title & Meta Description

Pass a unique title and description into the layout on every page — these drive both the browser tab and the snippet shown in search results:

astro
<BaseLayout
  title="About | Oliver Bravo Creative Director"
  description="Services, awards and client reviews from an award-winning creative director."
>

Project pages build theirs from each project’s seoTitle and seoDescription frontmatter. Pages that pass nothing fall back to defaultTitle and defaultDescription in src/data/site.js.

Canonical URL, Open Graph & Twitter/X Cards

These are set inside the <head> of src/layouts/BaseLayout.astro. The layout uses the site value from astro.config.mjs to build absolute URLs. The share image defaults to site.ogImage (/images/freelancer-image.avif), and project pages use their cover image. Replace the default with your own image, ideally a 1200×630 JPG or PNG, since some social networks don’t display AVIF previews:

astrosrc/layouts/BaseLayout.astro
const canonical = new URL(Astro.url.pathname, Astro.site);
const ogImageUrl = new URL(ogImage, Astro.site);
---
<link rel="canonical" href={canonical} />
<meta property="og:title" content={title} />
<meta property="og:description" content={description} />
<meta property="og:image" content={ogImageUrl} />
<meta name="twitter:card" content="summary_large_image" />

Sitemap & Robots.txt

The template uses Astro’s official sitemap integration (@astrojs/sitemap). It generates sitemap-index.xml automatically at build time from the site value, and the layout links to it. The template doesn’t ship a robots.txt. To control crawler access, add one at public/robots.txt that points to the sitemap:

textpublic/robots.txt
User-agent: *
Allow: /
Sitemap: https://example.com/sitemap-index.xml

Structured Data & Semantic HTML

Each page renders inside a <main> element and has a single <h1>, so both search engines and screen readers can parse the page’s structure. Keep it that way when editing. The template ships no JSON-LD structured data. Add it in the layout’s <head> if you want rich results, for example a Person or Organization schema for the portfolio owner.

Deployment

Platform-by-platform steps. Confirm your rendering mode first — it changes the build output you deploy.

Static vs. SSR — check this first

Oliver Bravo is a fully static build with no adapter, so the static instructions below are the ones to follow. A static Astro build (the default) produces plain HTML/CSS/JS in dist/ that any static host can serve. An Astro site using server-side rendering (SSR via an adapter) and a React/Vite single-page app both need a Node-capable host or the platform’s matching adapter. Using the wrong instructions for your rendering mode is the most common deployment mistake.

Vercel

  1. Push the project to a GitHub, GitLab, or Bitbucket repository.
  2. In Vercel, choose Add New → Project and import that repository.
  3. Build command: npm run build · Output directory: dist (Astro static) — Vercel’s Astro preset detects this automatically in most cases.
  4. Add any environment variables from your .env file under Project Settings → Environment Variables. The template needs none by default.
  5. Click Deploy.

Netlify

tomlnetlify.toml
[build]
  command = "npm run build"
  publish = "dist"

Connect the repository in the Netlify dashboard, confirm these build settings, add environment variables under Site configuration → Environment variables, and deploy.

Cloudflare Pages

Connect the repository, set the build command to npm run build and the output directory to dist. For SSR Astro sites, use the official @astrojs/cloudflare adapter instead of the static preset.

GitHub Pages

Set site and base in astro.config.mjs to match your repository URL, then build and publish the dist/ folder to the gh-pages branch (via the official astro build + a deploy action, or manually). GitHub Pages only serves static output — it cannot run an SSR adapter.

Traditional Hosting

Run npm run build locally, then upload the contents of dist/ to your host’s public web root via FTP/SFTP or your host’s file manager. This template needs no Node process on the server, so plain shared hosting works. Only an SSR setup, which this template doesn’t use, would need a Node-capable host.

Build & Production

What happens when you run build, and a checklist before you ship.

bash
npm run build     # render every page, bundle CSS/JS, generate the sitemap, write dist/
npm run preview   # serve dist/ locally, exactly as it will run in production

Build Output

The build writes the following to dist/:

  • Static HTML for every route, including one folder per project and per category.
  • Hashed CSS/JS bundles in dist/_astro/.
  • sitemap-index.xml and sitemap-0.xml.
  • Everything from public/ (images, video, fonts, favicons), copied unchanged.

This folder is disposable and regenerated by every build. The template’s .gitignore already keeps it out of Git.

Environment Variables in Production

The template itself uses no environment variables, so there is nothing to set out of the box. If you add a .env, remember that its variables are not deployed automatically. Each hosting platform requires you to set them again in its dashboard (see Deployment). A missing production variable is one of the most common causes of a build that works locally but fails, or behaves unexpectedly, once deployed.

Production Checklist

  • Run npm run build locally and confirm it completes with no errors.
  • Run npm run preview and click through the main pages.
  • Confirm the site URL in astro.config.mjs matches your real domain.
  • Set formEndpoint in src/data/site.js. Otherwise the contact form stays in demo mode and messages go nowhere.
  • Replace the placeholder name, email, phone, social links and copyright in src/data/site.js, and the demo projects in src/content/projects/.
  • Verify the favicon (public/favicon.svg / favicon.ico, currently Astro’s default), the Open Graph image (site.ogImage) and the meta descriptions are your own, not the template defaults.
  • If you added environment variables, set each one in your hosting platform’s dashboard.

Troubleshooting

The most common problems, in the order you’re likely to hit them.

npm install fails

Cause
Node.js version too old, a corrupted local cache, or a stale lockfile from a different package manager.
Solution
Confirm node --version meets the requirement in Requirements, then run rm -rf node_modules package-lock.json && npm install.

Port already in use

Cause
Another process (often a previous dev server that didn’t shut down cleanly) is already listening on the default port.
Solution
Stop the other process, or start this one on a different port: npm run dev -- --port 4322.

Module not found

Cause
A missing dependency, or a typo in an import path. The template uses relative imports only, with no path aliases.
Solution
Re-run npm install. Check that the relative path (e.g. ../components/Button.astro) is correct from the importing file, and that its casing matches the file exactly. Linux hosts are case-sensitive even if your machine isn’t.

Images not loading

Cause
A wrong path or filename. Template images live in public/images/ and must be referenced as /images/…, not public/images/… or a relative path. A replaced image whose -500/-800 srcset versions were deleted will also break.
Solution
Review Images & Assets. Check the browser’s Network tab for the 404, and confirm the filename (including casing and extension) matches the path in the component or project frontmatter.

Styles not loading

Cause
A page that doesn’t render inside BaseLayout (which imports global.css), or a stylesheet removed from the @import list in global.css.
Solution
Wrap new pages in <BaseLayout>. Confirm global.css still imports normalize.css, base-framework.css, oliver-bravo.css and custom.css, in that order.

Project frontmatter errors

Cause
A file in src/content/projects/ doesn’t match the collection schema. Typical causes: a missing required field, an invalid website URL, a non-numeric order, or not exactly three overviewImages/solutionImages.
Solution
The error names the file and the field. Compare that file against the schema in Data Structures, or against another project file that works, and fix the field.

Build fails (but dev server works)

Cause
The dev server only renders the pages you open, while build renders every page, including every project and category page. An error on a page you never visited in dev only shows up at build time.
Solution
Read the full terminal output for the first error (later errors are often side effects of it); fix issues top to bottom and re-run.

Text or images stay invisible / animations don’t play

Cause
Animated elements (anything with a data-anim attribute) are hidden by CSS until GSAP reveals them. A JavaScript error earlier on the page stops that from happening. If animations are missing but content is visible, the device probably has “reduce motion” turned on, which deliberately switches animations off.
Solution
Open the browser console and fix the first error, often a mistyped selector in a component’s <script>. If you add your own data-anim element outside the existing sections, make sure a script runs initReveals from src/scripts/reveal.js on its section.

Deployment problems

Cause
Wrong output directory configured on the host, a Node version below 22.23.4 in the build environment, or site still set to https://example.com, which leaves canonical and share URLs pointing at the wrong domain.
Solution
Re-check the build command (npm run build) and output folder (dist) against Deployment for your platform. Set the platform’s Node version to 22.23.4 or later, and update site in astro.config.mjs.

FAQ

Quick answers to the questions we hear most.

How do I install the template?

Extract the ZIP, run your package manager’s install command, then start the dev server. The full walkthrough is in Getting Started.

Which Node.js version should I use?

Node 22.23.4 or later — see Requirements. The template was built and tested on Node 24.

Can I use JavaScript instead of TypeScript?

The template is already plain JavaScript: there are no .ts files or type annotations to remove. If you’d like to add TypeScript later, Astro supports .ts files and typed props out of the box.

How do I change colors?

Update the --colors--* custom properties in the :root block of src/styles/oliver-bravo.css. The yellow accent is --colors--yellow (#fed532). See Styling.

How do I change fonts?

Swap the font files or Fontsource import and update --fonts--primary or --fonts--secondary — see Fonts & Icons.

How do I replace images?

Swap the file in public/images/ or update the path in the component or project frontmatter — see Images & Assets.

How do I add a new page?

Add a file to src/pages/; the route is created automatically — see Pages.

How do I add a new project?

Duplicate a file in src/content/projects/, rename it and edit its frontmatter. It appears on the Work page, its category page and at /project/<file-name> — see Content Editing.

How do I turn off or change an animation?

Each section’s animations are in the <script> at the bottom of its component, and the shared text reveals are in src/scripts/reveal.js. Removing an element’s data-anim attribute stops it animating.

How do I deploy the template?

Platform-specific steps for Vercel, Netlify, Cloudflare Pages, GitHub Pages, and traditional hosts are in Deployment.
